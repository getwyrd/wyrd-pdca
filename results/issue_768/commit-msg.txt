core, s3: keep Last-Modified from going backwards across overwrites

Each gateway stamps a file's modified time from its own clock. Behind a
round-robin balancer, a gateway running a few seconds fast followed by an
accurate one made Last-Modified go backwards while the content moved
forwards. Sync tools that compare size and time (aws s3 sync) then skipped
the newer file when the size matched, so a mirror silently kept old bytes.
The same fast stamp was also served as a Last-Modified in the future, which
RFC 9110 forbids.

An overwrite now records max(publishing clock, prior + 1 ms), so a file's
stored time strictly increases across overwrites, whichever gateway does
them. The rule never steps a stored time backwards on its own: a prior left
by a badly wrong clock is still ordered after (a warning is logged when it
is more than a day ahead), because a backwards step is what loses data.

An overwrite that carries no time over a version that has one is refused
with a typed error (UnstampedOverwrite) and nothing is written, so the order
cannot reset. Both gateway PUT paths always stamp, so no production write
changes; an unstamped overwrite of an unstamped legacy record is still
allowed.

The S3 gateway now shows the earlier of the stored time and its own clock,
in whole seconds, for the Last-Modified header (200, 206 and 304), the
listing's LastModified and the If-Modified-Since / If-Unmodified-Since
checks, and sets the response's Date from that same clock reading. No
response shows a time later than its own Date.

Known limits, documented in the building-block view: an overwrite in the
same second can show the same Last-Modified (compare ETag to see every
change); a mirror that already copied a future time sees later overwrites
as older until real time catches up, and needs an ETag or full re-sync.
The millisecond skew window relies on host clock sync (#902).

The new test crates/server/tests/last_modified_monotonic.rs drives the real
gateway, both core overwrite commits and the S3 wire; it fails on main and
passes with this change.
