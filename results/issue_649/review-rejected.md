## Class 1 — the byte-materialisation bound (BUG). **Settled at Plan; tracked as getwyrd/wyrd#674.**

Iteration 7's four blocking findings were all of this class: "`scan_page` materializes the
owned page / each full value before the per-value ceiling is checked, so an oversized
`seg:` row can exhaust the heap". The re-plan settled the question rather than re-litigating
it: **the byte ceiling is the store seam's, not the resolver's** — and this slice ships the
bounds that *are* the reader's instead (criterion 2: the segment-count ceiling refused
before any row is read, a group- and epoch-scoped prefix, and a **fixed page bound this
reader chooses**, `SEGMENT_PAGE_LIMIT`, never the root's claim).

Three reasons, each citable:

1. **The caller physically cannot check earlier.** `scan_page` returns
   `Vec<(Vec<u8>, Bytes)>` and `get` returns `Option<Bytes>` — values arrive **already
   materialised** (`crates/traits/src/lib.rs:1105`, `:1017`). There is no byte budget and no
   streaming value at the seam, so "check the size as each row streams in" is not a resolver
   change at all: it is a trait change plus five backends plus the shared conformance suite.
2. **The trait already assigns it.** *"The trait sets no key/value/batch size limits of its
   own; a backend's native limits are inherited and surface as `Err`"*
   (`crates/traits/src/lib.rs:995-999`). FoundationDB (100 000 B) and TiKV enforce that on
   write; only the embedded redb store can hold an over-ceiling value at all, and the only
   writer of `seg:` rows (#653's committer) sizes them to fit — so such a row means
   corruption, not traffic.
3. **The exposure is generic, so a guard here fixes nothing.** No reader anywhere in the tree
   checks a value's length — `high_water_marks`' `inode:` walk, GC's `orphan:` ledger and
   every `get` have the identical property — so a check in this one function guards one call
   site while the same hole stays open in every other: the single-module symptom guard
   `docs/principles.md` §1.2 rules out.

**What changed in the code, rather than only in this file:** every doc comment and error text
that claimed a `MAX_ROOT_SEGMENTS × MAX_VALUE_BYTES` *memory* bound is gone. What
`ChunkMapError::SegmentValueOverCeiling` now says is exactly what it does — this resolver
will neither **decode** nor **retain** an over-ceiling row — with the byte question named and
assigned to the seam (`crates/core/src/metadata.rs:523 | BUG | materializ | Class 1 above: values arrive already materialised at the seam (crates/traits/src/lib.rs:1105, :1017), the trait assigns the byte bound to the backend (crates/traits/src/lib.rs:995-999), and a guard here is the single-module symptom guard docs/principles.md 1.2 rules out.
