Add a shared resolver so segmented objects can be read

#648 taught InodeRecord.chunk_map to hold a Segmented table, but every
reader still pulled the inline chunk list off the record and failed
closed with SegmentedMapUnsupported, so a segmented object could be
committed but never read back. Each of the three read call sites was
about to grow its own way of walking a segment table, which is exactly
how #508's fourth attempt let GC delete a live object's fragments.

Add one resolver in crates/core/src/metadata.rs that every store-aware
reader shares: resolve_chunk_map for a caller holding its own snapshot,
resolve_current_chunk_map for one that must re-read the live root. Both
route through a single resolve-retry arbiter, so a generation retired
mid-read either restarts onto its live successor (overwritten) or
answers "no such object" (deleted) — never a torn half-map, and never a
delete misreported as an unsettled resolve on the reader's last retry
attempt. A root naming more segments than the resolver's ceiling is
refused before a single row is read, and each page of a segment's own
range is capped at a fixed size the reader sets, never the size the
root's table claims.

crates/core/src/read.rs (read_object, read_path) and
crates/server/src/lib.rs (streaming and ranged gateway reads) now
resolve through this shared path instead of failing closed. The
store-less read_object_from entry is unchanged: it has no production
caller and still can't resolve without a MetadataStore.

Two new test files drive every assertion through the public read
entry points over objects seeded as raw segment records, proving
byte-identical reads across a segment boundary, that the resolver's
own request log bounds the work a segment table can demand of it, and
both arms of the resolve-retry rule including the case where a delete
lands on the reader's final allowed attempt.

Fixes #649
