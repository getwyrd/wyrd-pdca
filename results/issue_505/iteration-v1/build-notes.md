# Build notes — issue 505 / sigv4-aws-chunked-trailer-framing

## What changed, and why (cite path:line on `origin/main` for the ADDED code; base-line
citations point at the pre-fix code being replaced)

1. **`crates/gateway-s3/src/checksum.rs` (new file).** The three checksum algorithms the
   brief requires at minimum: `ChecksumAlgorithm` (`crc32.rs:30-38`), a table-driven
   in-tree CRC-32 IEEE (`CRC32_IEEE_TABLE` + `crc32_ieee_append`, generated by the standard
   CRC-32 table-construction algorithm and pinned against the canonical `"123456789"` →
   `0xCBF43926` check value in `tests::crc32_ieee_check_value`), a `crc32c`-crate wrapper
   (already a workspace/`deny.toml`-allowed dependency, `Cargo.toml:83` on the base — used
   by `wyrd-chunk-format` already, so no new ADR-0003 audit), and `crypto::Sha256` reuse for
   `sha256`. Also a minimal in-tree base64 **decoder** (`base64_decode`), pinned against the
   RFC 4648 §10 vectors and the AWS `aws-c-auth` published `crc32c` trailer example
   (`wdBDMA==` decodes to `crc32c(b"a")`'s big-endian bytes). No `encode` — production never
   needs to encode, only decode the client's declared value.

2. **`crates/gateway-s3/Cargo.toml`** — add `crc32c.workspace = true` (base `Cargo.toml:83`
   already declares the workspace version; this crate simply wasn't consuming it yet).

3. **`crates/gateway-s3/src/sigv4.rs`**:
   - `StreamingContext` gains `pub trailer: Option<TrailerDeclaration>` (sigv4.rs:97) and
     the new `TrailerDeclaration` struct (sigv4.rs:104-115) — the declared checksum
     algorithm + trailer name + optional `x-amz-decoded-content-length`.
   - `streaming_variant` (base `sigv4.rs:510-515`, now `sigv4.rs:547-561`) is widened from a
     closed `sentinel -> Option<bool>` (only `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`, `Some(true)`)
     to `Option<(bool signed, bool has_trailer)>`, admitting
     `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER` (`true,true`) and
     `STREAMING-UNSIGNED-PAYLOAD-TRAILER` (`false,true`) — the two sentinels the base
     refused unconditionally (base `sigv4.rs:484-490`/`:510-515`, pinned refused by the
     tests at base `sigv4.rs:1013-1023`).
   - `parse_trailer_declaration` (sigv4.rs:564-585, new) reads and validates `x-amz-trailer`
     / `x-amz-decoded-content-length` **before any body is read** — a missing declaration, a
     multi-name declaration, or an unrecognised checksum algorithm (including the
     out-of-scope `x-amz-checksum-crc64nvme`) is refused right here, `AuthError::Malformed`
     → 403, the same fail-closed posture `verify` already has for the seed signature.
   - `verify`'s classification branch (base `sigv4.rs:498-516`) now calls
     `parse_trailer_declaration` when `has_trailer` and carries the result on
     `StreamingContext.trailer`.
   - Tests: base `sigv4.rs:1088-1098` (the two blanket `-TRAILER` refusal assertions) are
     REMOVED and replaced by two new tests —
     `verify_admits_the_trailer_sentinels_with_a_declared_trailer` (acceptance, both
     sentinels, asserting the parsed `TrailerDeclaration`) and
     `verify_rejects_an_unverifiable_trailer_declaration` (the declaration-level fail-closed
     edges: missing `x-amz-trailer`, `crc64nvme`, multi-name) — satisfying the brief's "flip
     the `:1013-1023` refusal tests into acceptance tests" instruction without dropping the
     fail-closed coverage those old assertions existed for (it moves to the new declaration
     test, since the REASON for refusal changed from "sentinel unsupported" to "declaration
     unverifiable").

4. **`crates/gateway-s3/src/streaming.rs`** — the actual trailer-consuming decoder work
   (brief scope item (a)):
   - `StreamingError` gains `ChecksumMismatch` (streaming.rs:88, doc at :77-87) — distinct
     from `ChunkSignature` because the unsigned `-TRAILER` variant has no signature to fail,
     only a checksum to mismatch; maps to 400 `BadDigest` in `lib.rs`'s `classify`
     (lib.rs:884-891), mirroring `GatewayError::PayloadMismatch`'s existing 400 arm
     (base `lib.rs:880-884`).
   - `sign_trailer` (streaming.rs:132-166) — AWS's trailing-header string-to-sign
     (`"AWS4-HMAC-SHA256-TRAILER\n" + date + "\n" + scope + "\n" + prev_sig + "\n" +
     Hash(canonical_trailer_headers)`), the same structural discipline as the existing
     `sign_chunk` (streaming.rs:98-108, unchanged). Pinned by
     `tests::aws_published_trailing_headers_example`
     (streaming.rs, mod tests) against a **published worked example** — see "Provenance of
     the trailer signature algorithm" below, since this is the one piece the brief flags as
     needing an anchor and the module's existing docs (base `streaming.rs`) had none for it.
   - `Decoder` gains `checksum: Option<RunningChecksum>` and `decoded_len: u64`
     (streaming.rs, struct fields) and updates them on every consumed chunk (including the
     empty terminal one, a no-op).
   - `next_chunk`'s step 2 (base `streaming.rs:280-290`, the chunk-data + trailing-CRLF
     read) is now conditional: `is_trailer_terminator = size == 0 && ctx.trailer.is_some()`
     (streaming.rs:304-305) skips the data+CRLF read entirely for the terminating chunk of a
     `-TRAILER` framing — because that framing's wire shape for the terminator is
     `0[;chunk-signature=…]\r\n<trailer lines>\r\n`, i.e. the trailer section follows
     directly after the chunk-header's own CRLF (exactly HTTP/1.1 chunked-transfer trailer
     syntax), NOT a second blank-line CRLF as the plain no-trailer sentinel's
     `0[;chunk-signature=…]\r\n\r\n` terminator has. Getting this framing shape right — not
     "requires an immediate CRLF" as the base's own doc at `sigv4.rs:501-509` correctly
     diagnosed as the blocker — is the crux of "make the trailer framing fully consumable."
   - `next_trailer_line` / `consume_trailer` (streaming.rs:357-479, new) read the trailer
     section line-by-line (bounded by `MAX_TRAILER_SIZE = 8 KiB`, streaming.rs:66, the same
     bounded-buffering discipline `MAX_CHUNK_SIZE` already applies to a chunk's declared
     size, base `streaming.rs:51-57`), refusing: an undeclared/duplicate trailer name, a
     malformed base64 value, a missing declared trailer, an unsigned framing carrying
     `x-amz-trailer-signature`, a forged trailer signature (signed variant — checked via
     `sign_trailer`, BEFORE the checksum comparison, same "signature first" order as the
     header request), a checksum mismatch against what was **actually streamed**
     (`RunningChecksum`, never the client's claim), a `x-amz-decoded-content-length`
     mismatch, and any bytes left over after the closing blank line ("garbage after the
     trailer block" — caught by pulling one more source frame and checking `buf` is still
     empty).
   - `aws_example_ctx()` (base `streaming.rs:509-523`) gets `trailer: None,` (the new struct
     field) — the ONE forced edit to an unrelated-looking existing test helper, needed only
     because `StreamingContext` grew a field.

5. **`crates/server/tests/s3_http_wire.rs:1012-1020`** — `StreamingContext` literal
   construction (the `streaming_interop` module) gets `trailer: None,` added, for the same
   reason. This is the ONE line touched in that file; every existing test/assertion in it is
   otherwise unchanged and still passes (see "Existing tests stay green" below) — no
   behavioural or narrative edit.

6. **`crates/server/Cargo.toml`** — `crc32c.workspace = true` under `[dev-dependencies]`,
   for the new test file's independent CRC-32C oracle (see below).

7. **`crates/server/tests/s3_streaming_trailer.rs` (new file, the brief's named test)** — the
   wire-level red→green proof. 9 tests, covering the Success criterion's positive cases
   (both sentinels, all three checksum algorithms, byte-identical round trip) and every
   named fail-closed edge (forged trailer signature, tampered checksum, unrecognised
   algorithm, bad base64, undeclared trailer name, garbage after the trailer block, decoded-
   content-length mismatch).

## Provenance of the trailer signature algorithm (why I'm confident `sign_trailer` is
AWS-correct, not self-consistent)

The brief says: "verify the trailer signature for the signed variant (per AWS's published
trailing-header string-to-sign, anchored to a published worked example where available —
the module already pins chunk signing to AWS's published example, keep that discipline)."
AWS's own S3 API docs page for this (`sigv4-trailing-header-streaming.html`) is a
client-side-rendered SPA shell in this environment (fetches redirect through a JS loader
that never resolves server-side), so I could not scrape a canonical text copy of the
worked example directly from it. Instead I found AWS's **own open-source reference
implementation's test suite** — `awslabs/aws-c-auth` (Apache-2.0, the C library AWS's own
SDKs use for SigV4), `tests/test_chunked_signing.c`, whose header comment says: "The
chunked signing test is built using the complete chunked signing example in the s3 docs" —
i.e. it IS the same published example, just captured as a conformance-test fixture rather
than prose. Its `s_sigv4_trailing_headers_signing_test` chains off the EXACT SAME
credentials/date/scope/seed/chunk signatures our own `aws_published_streaming_example`
already pins (`4f232c43…`, `ad80c730…`, `0055627c…`, `b6c6ea8a…` — all four already in
`streaming.rs` before this change), three trailer headers `first:1st`/`second:2nd`/
`third:3rd`, and asserts the trailer signature `df5735bd9f3295cd9386572292562fefc93ba94e80a
0a1ddcbd652c4e0a75e6c`. I independently reproduced this in Python (HMAC-SHA256 ladder, the
same shape as `sigv4.rs`'s `signing_key`) before writing any Rust, confirmed the exact match,
and only then implemented `sign_trailer` and pinned
`tests::aws_published_trailing_headers_example` against it. This is the same "published
worked example" discipline the module's docs already keep for `sign_chunk`
(`streaming.rs`'s `aws_published_streaming_example`) — same source family (AWS's official
SigV4 streaming example), same non-self-referential guarantee (an independent artifact,
not this patch's own code, produced the expected value).

I also independently confirmed `x-amz-checksum-crc32c` is `base64(big-endian
u32(crc32c(data)))` against the SAME `aws-c-auth` test file's `wdBDMA==`/`crc32c-of-"a"`
pairing (also cross-checked with a from-scratch Python CRC-32C implementation), and that
plain `x-amz-checksum-crc32` is the standard CRC-32 IEEE check value (`"123456789"` →
`0xCBF43926`) similarly base64-encoded big-endian.

## What I ruled out (and the cost, so the trade is checkable)

- **A new `crc32fast`-style crate for plain CRC-32.** Rejected per the brief's own
  instruction: the `crc32c` crate (already vetted) computes a DIFFERENT polynomial and
  cannot be reused for plain `crc32`. A new crate would need ADR-0003's three-test audit +
  a `deny.toml` allowlist entry, a human-only sign-off item (INTEGRATION §4). Cost of the
  alternative I took instead: `checksum.rs`'s `CRC32_IEEE_TABLE` (256 `u32`s, generated
  once by the standard construction, pasted as a `const`) + `crc32_ieee_append` (9 lines) —
  no new crate, no ADR-0003 item, pinned by a known-answer test. I did **not** invoke this
  NEEDS-HUMAN path; flagging it here only because the brief asked me to declare it loudly if
  I ever considered it.
- **Requiring `x-amz-trailer` to be a SigV4-*signed* header** (in `SignedHeaders=`), so an
  on-path attacker couldn't inject/alter the trailer declaration post-signature. I left it
  unsigned-but-read, matching how `x-amz-content-sha256` itself and
  `x-amz-decoded-content-length` are already read regardless of `SignedHeaders` membership
  in the base `verify` (`sigv4.rs:422-423` reads `x-amz-content-sha256` unconditionally).
  For the SIGNED trailer sentinel this is moot: `x-amz-trailer`'s value name is baked into
  the trailer-signature's canonical line (`consume_trailer`, streaming.rs) — a request whose
  `x-amz-trailer` was altered post-signing has the decoder look for a DIFFERENT declared
  name than the trailer signature actually covers, so it is refused (fail-closed) either as
  "trailer not declared" or a trailer-signature mismatch, not silently accepted. For the
  UNSIGNED sentinel, `x-amz-trailer` tampering has the same blast radius as tampering ANY
  unsigned framing header on that variant (the variant's whole design posture, per its own
  doc at `sigv4.rs:82-86` on base, is "integrity rides the seed signature + transport" — no
  stronger guarantee is claimed for it anywhere in the existing module). Making
  `x-amz-trailer` mandatory-signed would be a STRICTER floor than the base module already
  holds for this sentinel family, and the brief's Scope doesn't ask for it — so I left it
  matching the existing posture rather than inventing a new one.
- **A single combined `StreamingError::TrailerSignature` vs reusing `ChunkSignature`.** I
  reused `ChunkSignature` for a forged trailer signature (both are "a signature in the
  chunk-signature chain didn't verify", same 403 `SignatureDoesNotMatch` S3 code) rather
  than adding a fourth enum variant + a fourth `classify()` arm for a distinction the wire
  contract doesn't need (S3 has no separate code for this). `ChecksumMismatch` DOES get its
  own variant because it is a genuinely different failure class needing a different HTTP
  status (400, not 403) — the checksum comparison has no signature analog when the stream
  is the unsigned `-TRAILER` variant.

## Self-refutation (the three forced questions)

- **(a) Genuine red?** Yes — verified two ways. (1) I stashed every production file this
  patch touches (`sigv4.rs`, `streaming.rs`, `checksum.rs`, `lib.rs`, both `Cargo.toml`s,
  `s3_http_wire.rs`'s one-line field addition) and re-ran
  `cargo test -p wyrd-server --test s3_streaming_trailer` — it fails to COMPILE against
  `origin/main` (unresolved `wyrd_gateway_s3::checksum`, `TrailerDeclaration`,
  `streaming::sign_trailer`, the `crc32c` dev-crate, and `StreamingContext.trailer`), which
  is a stronger red than a runtime assertion failure: the test literally cannot exist
  without the new production surface. (2) I additionally applied `patch.diff` to a FRESH
  worktree checked out at `origin/main`'s tip (`0b01454`, an isolated
  `$PDCA_SCRATCH/pdca-builder-505-verify` worktree, removed after) and ran the same tests
  there — green, confirming the patch is self-contained and the red→green transition is the
  patch itself, not some other uncommitted state in my dev worktree.
- **(b) Production path?** Yes. `s3_streaming_trailer.rs` drives the real loopback HTTP
  listener (`S3Gateway::serve` over a real `TcpListener`) with hand-built TCP bytes, exactly
  as `s3_http_wire.rs` does — no mock gateway, no stand-in decoder. The signing/framing
  helpers (`streaming_seed`, `frame_trailer_body`) call the PRODUCTION `sigv4::sign_with_
  payload_hash`, `streaming::sign_chunk`, and the NEW `streaming::sign_trailer` directly (not
  a copy) — the same functions `sigv4::verify` / `streaming::decode` use to verify, so the
  test is driving the real signer against the real verifier over the real wire path, the
  same non-self-referential structure `s3_http_wire.rs` already established for the
  no-trailer sentinel.
- **(c) Fixture includes the fault?** Yes, for every fail-closed test: the corruption is
  applied to the ACTUAL wire bytes sent (a byte flip in the live `x-amz-trailer-signature:`
  line, a checksum value computed over `b"not the real object"` instead of the real payload,
  a wire trailer name that diverges from the declared one, literal garbage bytes appended
  within the declared `Content-Length`, a `x-amz-decoded-content-length` header set to a
  wrong value) — never a hand-curated "already-safe" fixture. And the checksum computations
  in the test use an INDEPENDENT `crc32c` crate call (not the gateway's `checksum` module)
  plus a bit-by-bit (not table-driven) CRC-32 for the positive-path tests, so a shared bug
  between production and test checksum code could not manufacture a false green.
