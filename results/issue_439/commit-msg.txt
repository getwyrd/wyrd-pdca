Add CI conformance signal and preflight doctor for the fdb backend

FoundationDB is the chosen production metadata backend, but it had no
automated coverage: the conformance driver added in
22d39b6035573d9b999a95430e62ae68a859bd29 existed yet nothing ran it, so
the backend could break on any change and no one would notice until a
release. Anyone building the feature locally
without the FoundationDB client library or a running cluster also got a
raw linker error or a hung transaction instead of a message telling them
what to install.

This wires the backend into CI and gives it an actionable local
preflight, without making the ordinary merge gate require Docker or the
system client library:

- a scheduled-plus-on-PR job runs the existing conformance driver
  against a throwaway single-node cluster, and type-checks the feature
  arms that no default build compiles;
- `cargo xtask fdb-doctor` probes the client library, the cluster file,
  and cluster health, and prints for each failure the exact package,
  environment variable, or command that fixes it — and the conformance
  job runs this same preflight so it fails fast with guidance rather
  than a link error minutes into a container run;
- the whole-tree gate gains opt-in type-checks for the feature, gated on
  their own environment flag so they never couple to the unrelated TiKV
  toolchain, and the merge gate stays green offline and container-free.

The audit-policy note in deny.toml records what dependency scanning can
and cannot see for a Rust crate that binds a system library.

Fixes #439
