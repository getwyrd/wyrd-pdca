custodian: contain unreadable chunk maps in restore and drain reports

Post-restore reconciliation and the drain status used to go dark the
moment one committed object's chunk map could not be read: a single
segmented or damaged object made `wyrd custodian
--reconcile-after-restore` return no report at all — not even the
stranded count or the dangling/misplaced chunks of every other object
it could read — and made the drain status answer a bare "still
waiting", indistinguishable from a server that genuinely still holds
referenced fragments. An operator had no report to act on in the
first case, and no way to learn which record was blocking a stalled
decommission in the second.

Both surfaces now contain the damaged object instead of erroring or
silently certifying: `reconcile_after_restore` keeps reporting every
object it *could* read, names the ones it could not, and marks the
run not clean; `reconciliation_status` gains a `PendingUnresolvable`
variant that names the blocking record instead of returning `Pending`.
Marking is only ever authorized from a single, complete reading of the
committed namespace, so a record that changes between this pass's two
reads can never license an unsafe mark. The `wyrd custodian` CLI's
exit code is now derived directly from the report, so an incomplete
reading can no longer be printed as a caveat and exit 0.

This builds on 11aa85f, which introduced the underlying containment
vocabulary (`gc::ReferenceSet::unresolvable`, `protects`) for GC and
scrub and deferred these two reporting surfaces here by name.

Fixes #651
