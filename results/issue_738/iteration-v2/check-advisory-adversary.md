# Adversarial review — issue 738 (`wyrd s3 --chunk-size`)

Verdict: the core fix holds. I re-ran the evidence and could not break the flag itself.
The weak spots are in the gRPC message-limit change this round added, not in the flag.

## Evidence re-run (all done on a scratch copy of `$PDCA_TARGET`)

- Green reproduced: `cargo test -p wyrd-server --test s3_chunk_size_flag` passes 6 of 6 on the patched tree. The frozen red log (`gate-logs/C4-verify.log`) agrees with the test file: each panic line matches an assertion in `crates/server/tests/s3_chunk_size_flag.rs` (`:385`, `:405`, `:462`, `:502`). The test drives the built binary (`:42`, `env!("CARGO_BIN_EXE_wyrd")`), so it runs the production `cmd_s3` → `serve_s3_dispatch` path, not a copy.
- The C4-verify red for the gRPC test fails on the chunk count (32 vs 1), not on the transport, so the gate never proved the message-limit half had its own red. I checked that by hand. With only the D-server limit removed (`crates/server/src/dserver.rs:1210-1214`), the 32 MiB PUT returns `500 InternalError`. With only the client limit removed (`crates/chunkstore-grpc/src/client.rs:254-259`), GET returns 200 with 0 body bytes and fails at `s3_chunk_size_flag.rs:518`. The test catches both halves.
- Last round's template finding is fixed. I deleted ` --chunk-size 1048576` from the live `WYRD_S3_ARGS=` line and kept the comment. `env_examples_name_every_load_bearing_flag` now fails at `xtask/tests/dist_templates.rs:196`.
- No gate compiled the two `fdb` arms. `cargo check -p wyrd-server --features fdb,etcd` passes, so all six `with_chunk_size` arms (`crates/server/src/cli.rs:2414-2453`) type-check.

## What I tried that did not break it

- Parse edge cases (`crates/server/src/cli.rs:2301-2316`): `+1`, `-1`, `""`, `1MiB`, and a value past `u64` are refused. Leading zeros (`0065536`) are accepted as 65536, which is harmless. `--chunk-size` with no value is already refused by `ParsedArgs::parse` (`cli.rs:2618-2620`). The refusal at `cli.rs:2202` runs before the listener bind further down in `cmd_s3`.
- Test strength: the default case (2 chunks) and the flag case (4 chunks) both catch an off-by-one or a wrong default. Both backends are now pinned with flags (`s3_chunk_size_flag.rs:93-98`). Every child process is killed on drop, and every wait has a time limit.
- The compile-time check (`crates/server/src/lib.rs:73-82`) uses `DEFAULT_DURABILITY`. The `s3` role never calls `with_durability`, so for this role it is the right scheme.

## Findings

- NEEDS-HUMAN [human] — **The 192 MiB message limit applies to every D server, even when the fleet runs 1 MiB chunks.** `crates/chunkstore-grpc/src/lib.rs:50` sets `MAX_MESSAGE_BYTES = 192 << 20`, and `crates/server/src/dserver.rs:1210-1214` applies it with no configuration. The D server admits `DEFAULT_MAX_CONCURRENT_REQUESTS = 64` requests at once (`dserver.rs:61`), and tonic holds each whole message in memory before decoding it. So the worst-case request memory per D server goes from 64 × 4 MiB = 256 MiB to 64 × 192 MiB = 12 GiB, on every deployment, whether or not any gateway sets `--chunk-size`. `docs/design/architecture/08-crosscutting-concepts.md:111` states the limit for one request but not this total. The brief's fixed 1 GiB ceiling forced this, and the brief never considered the transport. A human should pick one: accept the 12 GiB worst case, make the D-server limit a d-server setting that follows the fleet's chunk size, or lower the `s3` ceiling to fit a smaller transport limit.
- NEEDS-HUMAN [human] — **"Every accepted value is transportable to a D server" (`crates/server/src/lib.rs:62-64`) only checks message size, not time.** The D server cuts any request after `DEFAULT_REQUEST_TIMEOUT = 30 s` (`dserver.rs:72`, applied at `:1199`), and that includes receiving the request body. The custodian's per-request timeout is 10 s by default (`cli.rs:863`). At `--chunk-size 1073741824`, one PUT sends 9 × ~171 MiB ≈ 1.5 GiB. On a 1 Gb/s gateway link (~119 MiB/s), three PUTs at once take about 39 s to send, so every fragment is cut at 30 s. A custodian rebuild reads 6 × 171 MiB ≈ 1 GiB, about 8.6 s of transfer time against a 10 s limit. At the least, the doc claim should say "fits one gRPC message". Whether 1 GiB is still the right ceiling is a sign-off question.
- NEEDS-HUMAN [impl] — **DST D-server models no longer match production (rubric: *Test fidelity*).** Only `DServer::serve` raises the server-side limit (`dserver.rs:1210-1214`). The DST D-server models still mount a bare `ChunkStoreServer::new(...)` (`crates/dst/tests/network.rs:234,662,843,987`), which keeps tonic's 4 MiB limit. Their clients go through `GrpcChunkStore::new` (`client.rs:254`), which now sends up to 192 MiB. So a DST scenario with a chunk over ~24 MiB would get `OUT_OF_RANGE` where production succeeds. No current DST scenario uses fragments that large, so the gap is latent. The cause is the design choice in `crates/chunkstore-grpc/src/lib.rs:41-42` that every host must remember to apply the limit itself. Fix: export a constructor from `wyrd-chunkstore-grpc` that returns the bounded server, and use it in `dserver.rs` and the DST mounts.
- NEEDS-HUMAN [impl] — **The rolling-upgrade order is not documented.** I reproduced both failure modes. With a new gateway (`--chunk-size 33554432`) and an old-limit D server, PUT returns `500 InternalError`. With an old-limit client reading those chunks, GET returns 200 with an empty body. So every D server, custodian and gateway must run the new binary before any gateway sets `--chunk-size` above ~24 MiB. Neither `08-crosscutting-concepts.md:111` nor the `--chunk-size` comment in `deploy/dist/env/s3.env.example:12-16` says so. The neighbouring W_write entry (`08-crosscutting-concepts.md:110`) already records its own mixed-version caveat, so adding one sentence here follows the doc's existing style.
- NEEDS-HUMAN [impl] — **The T4 blocking finding is real but cannot cause a false pass.** `dechunk` (`s3_chunk_size_flag.rs:307`) accepts a truncated terminator, but it only runs on chunked error bodies. The success checks are status 200 plus exact byte equality (`:518`). The real gap sits next to it: `signed_request` ignores the declared `Content-Length` (`:295-297`). In my client-only revert, a truncated GET therefore showed up as "GET returned 0 bytes that differ" instead of being reported as a truncation. Cheap fix: assert that the body length equals `Content-Length`, and make `dechunk` require the final CRLF. T4 is a blocking gate, so this has to be handled either way.
- NEEDS-HUMAN [human] — **Do not count the C4-diff-cov FAIL (34.8%) for or against the fix.** Its MISS lines do not match the patched source at `$PDCA_TARGET`. `crates/server/src/cli.rs:2199-2200` and `:2333-2337` are comment lines, and `:2316-2317` are a `}` and a blank line. This is the same position mismatch flagged last round. Separately, the serving paths run in a child process that `Role::drop` kills with SIGKILL (`s3_chunk_size_flag.rs:67-72`), so llvm-cov never receives their profile. The partial-revert runs above are better evidence of reach than this row.
