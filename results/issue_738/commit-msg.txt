server: honour `wyrd s3 --chunk-size N`, refuse values it cannot carry

An operator could not choose the chunk size of an S3 gateway. Every
gateway split objects into 1 MiB chunks whatever its fleet or workload.
Worse, `wyrd s3 --chunk-size 65536` started without complaint, ignored
the flag and still wrote 1 MiB chunks, so a deployment could believe it
ran a value it never did.

`wyrd s3` now reads `--chunk-size N` and applies it on every backend
combination, for both the local data directory and the `--endpoints`
cluster path. Leaving the flag out keeps today's 1 MiB default.

The accepted range is 1 to 16777216 bytes (16 MiB). Anything else, or a
value that is not a plain byte count, is refused at startup, naming the
flag, before the listener binds. The ceiling comes from the cluster
transport: each chunk is erasure-coded into six data fragments, and each
fragment travels in one gRPC message under the 4 MiB receive limit, so a
24 MiB chunk already fails its first PUT. 16 MiB leaves about 1.3 MiB of
headroom. The reason is written beside the constant for whoever next
wants to raise it. The transport itself is unchanged.

`serve_s3_role` gains a `chunk_size: Option<usize>` parameter and checks
the same range, so a library caller cannot start a role with a value the
transport cannot carry. Its one external caller passes `None`.

The usage text lists the flag. The dist env example, the M4 blueprint
invocation and the small-multi-node-fdb compose gateways now state
`--chunk-size 1048576` explicitly, so a deployment records its value
without changing behaviour, and the template test checks that the live
`WYRD_S3_ARGS=` line carries it.

Gateways in one fleet may run different chunk sizes: reads follow each
object's own chunk map, not a process-wide setting.

Fixes #738
