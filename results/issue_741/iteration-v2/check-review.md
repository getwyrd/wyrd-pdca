Two fixes are warranted; these are advisory findings, not reviewer-controlled acceptance gates. The batch log's four findings reduce to these same two defects: three reports of F1 and one of F2.

1. **F1 — Reject incomplete XML before treating its code as an S3 fact.** `target/crates/validate/src/client.rs:345` checks only the opening root element, and `target/crates/validate/src/client.rs:327` then trusts SDK metadata. A loopback endpoint returned HTTP 503 with an exact `Content-Length`, `x-amz-request-id: scripted-request-741`, and body `<Error><Code>SlowDown</Code>`. Both GET and DELETE produced `Service(ServiceError { status: 503, code: Code("SlowDown"), ... })`; neither produced `Unreadable` (`reviewer-probes.log:8`, `reviewer-probes.log:9`). Thus HTTP framing is complete while the XML is incomplete. This contradicts the unreadable-response contract (`target/crates/validate/src/error.rs:26`) and the protocol-input rubric (`target/AGENTS.md:161`). Validate the complete document before accepting its parsed fields, preserving status and request ID on failure. The existing invalid-entity and short-HTTP-body cases do not cover this input (`target/crates/validate/tests/s3_client_roundtrip.rs:732`, `target/crates/validate/tests/s3_client_roundtrip.rs:772`).

2. **F2 — Require positive source completion before reporting PUT success.** `target/crates/validate/src/client.rs:184` checks for a recorded source fault, but an empty fault slot does not prove that the source reached EOF at its declared length. The only EOF observation is inside `SizedBody::poll_frame` (`target/crates/validate/src/client.rs:467`); completion is not recorded for the success path. A loopback endpoint sent HTTP 200 with a zero-length response immediately after reading the request head. The source yielded 64 KiB and then stayed pending, against a declared 32 MiB. PUT nevertheless returned `Ok(Receipt { request_id: Some("scripted-request-741"), e_tag: None })` (`reviewer-probes.log:14`). A faulty endpoint can therefore turn an incomplete transfer into reported success. Track successful EOF/exact-length completion separately from faults and require it for a successful receipt, while preserving legitimate early service errors. Add the early-acknowledgement regression; the current real-gateway bad-source cases cannot exhibit this premature success (`target/crates/validate/tests/s3_client_roundtrip.rs:985`).
