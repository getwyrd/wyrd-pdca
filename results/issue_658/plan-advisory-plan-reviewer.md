- NEEDS-HUMAN — **The error contract has no outcome for a known fence whose release fails.** `brief.md:138` permits only the in-doubt error to leave Complete's own fence standing, while `brief.md:324-329` requires that error to carry an unknown commit outcome. Consider D2's definite successful fence and invalid frozen part list, followed by release commits that all return definite `Conflict` without changing the session. This is a supported store behavior: `crates/core/src/multipart/abort.rs:245-247` explicitly handles conflicts caused by locks with nothing moved. Complete must terminate with its fence still standing, but there is no unknown outcome to supply: the proposed model's `InDoubt.outcome` is a mandatory `CommitUnknownResult` (`crates/core/src/multipart/abort.rs:121-134`). Define the error and recovery contract for a known, unfinished fence, including definite store failures after fencing; reconcile the invariant and add a bounded release-failure test with no unknown commit injected.

- NEEDS-HUMAN — **“Retire the prior whenever the key existed” is incompatible with a valid empty prior.** `brief.md:307` requires a generation obligation “if the key existed,” and criterion F repeats that rule (`brief.md:78-79`). The target supports empty objects: `crates/core/src/write.rs:166-168` specifies an empty plan, and `:277-281` publishes that plan as a committed inode with an empty map. But retirement of a flat generation passes its chunks through `checked_chunks` (`crates/core/src/multipart.rs:3427`), which rejects an empty list as `RetireObligationOwesNothing` (`:3272-3277`). Following the brief literally either rejects a legitimate overwrite or writes an obligation the decoder refuses. Specify that an empty flat prior needs no generation retirement obligation, and require Complete-over-empty to publish the next version successfully without that obligation. This avoids silently expanding scope into a retirement-format change.

Removing the flip's bucket guard should make this new leg fail.
