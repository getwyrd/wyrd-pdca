metadata-fdb: fail closed on a client/cluster version mismatch

A FoundationDB client binds a shared C library (libfdb_c) whose wire
protocol is exactly coupled to the cluster's: a client built against one
FDB version cannot talk to a cluster running another, at all, ever. When
an operator got that pairing wrong, Wyrd gave them no way to tell. Since
every transaction gained a deadline
(576fc15a9a7cd9b257c6f2decd61aa1612e9d6b0), a mismatched client no longer
hung — but it failed with the same anonymous "transaction timed out" a
genuinely down or unreachable cluster produces. Version coupling is the
single most common FoundationDB misconfiguration, and it was reported as
if the cluster were simply unavailable, sending operators to debug the
wrong thing.

`wyrd --metadata-backend fdb` now runs a bounded readiness probe when it
connects. If the client and cluster disagree on protocol version, the
connect fails immediately with a message that names the cluster's own
protocol version and points at the multi-version-client upgrade
procedure — instead of the anonymous timeout. A genuinely unreachable
cluster is still reported as unreachable, never as a guessed mismatch, so
the two failures are no longer confused for each other.

For lockstep cluster upgrades, a new WYRD_FDB_EXTERNAL_CLIENT_DIR points
the client at a directory of additional libfdb_c versions
(FoundationDB's multi-version client), so bridging an upgrade is a
configuration change rather than a rebuild. Unset, behaviour is
unchanged. The default (redb) build is untouched: no new dependency, no
libfdb_c demand, no behaviour change. The deployment guide gains the
packaging contract — container and bare-metal paths, the upgrade dance,
and the single-binary trade.

Fixes #441
