custodian: contain backfill's chunk-map read per object

Backfill inlined the chunk-map read at two sites in
crates/custodian/src/backfill.rs (reconcile, emit_remaining), each
refusing outright on a segmented record. That meant a single
segmented object anywhere in the store stopped the fill pass for
every other object and silenced the drain gauge entirely, even
though the flat records around it were otherwise fine.

Route both sites through wyrd_core::metadata::resolve_chunk_map, the
same shared resolver GC and restore already use, so a segmented
object is read and judged like any other. An object this pass
cannot read (undecodable bytes, or the resolver refusing its
generation) is now contained to itself: named on the audit seam,
counted, and skipped, while the walk continues over the rest of the
store. A committed object whose fill this pass may not perform
(chunks living in seg: records) is declined rather than mutated or
aborted -- nothing is written for it, and it stays on the
remaining-placements gauge until a later pass (or #682's segmented
write path) fills it. The pass now refuses to certify Satisfied over
a reading that skipped or declined any object, returning
Reconciled::Blocked instead, and the drain gauge is counted in the
same walk that fills rather than by a second, redundant scan.

Key-identity parsing and the CAS key derivation are left
byte-identical to origin/main (tracked separately as #698); a
generation-restart comparison is deliberately not added, since a
flat snapshot resolves by borrow and can never be superseded
(crates/core/src/metadata.rs:2585), so the write path needs no
comparison of its own (tracked as #699).

Fixes #695
