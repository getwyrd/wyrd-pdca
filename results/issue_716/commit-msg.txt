multipart: validate session/slot/part lifecycle records at decode

An upload's in-flight lifecycle now has stored record types of its own:
SessionRecord (mpu:<id>), SlotRecord (slot:<id>:<k>), and PartRecord /
PartSummary (part:/psum:<id>:<n>). Each type validates its own shape and
cross-field invariants inside its Deserialize impl and round-trips through
the store's existing generic metadata::encode/decode codec — no new wire
envelope, mirroring the pattern InodeRecord and SegmentRecord already use
and the one landed for Budget/AdmissionRecord in 5eeca16.

Without structural validation at decode, a torn or hand-written record
could reach production code unnoticed: a session whose publish_target
names a different bucket/object or a different fence epoch than the
session's own would let one attempt publish under another attempt's
identity; a part accepting a raw, unvalidated chunk reference would let
untrusted stored geometry (an unsupported erasure scheme) reach the read
path; a slot record could be born with its lease already lapsed and be
reclaimed the instant it is written; and an unknown or silently-defaulted
field inside a record or its nested chunk values would make decode->encode
non-identical, which is unsafe for a value that a compare-and-swap
transition checks against its exact stored bytes.

This change adds the typed decode rejections for all of those cases,
closes the wire shape of every new record type (including a closed mirror
of the chunk reference type, scoped to this module so the store's more
permissive chunk-map codec is untouched), and extends the metadata-model
documentation with the four new persisted key prefixes this adds.

Deliberately left liberal, per ADR-0045: a chunk's placement length is a
contextual check, not a structural one, so a placement vector whose length
disagrees with its erasure scheme's fragment count still decodes; and no
non-zero-length rule is imposed where the target's own erasure coder does
not require one.
