fix(metadata-tikv): map a lost write-write race to Conflict

The TiKV metadata backend's commit contract promises callers a clean
distinction: a losing writer gets Ok(Conflict) — a normal, expected
outcome under concurrency — while Err is reserved for a genuine backend
fault. When two clients raced to update the same key, though, the loser
surfaced as Err instead of Conflict, so callers that correctly handle a
conflict (re-read and retry) were instead forced to treat an ordinary
concurrent update as a hard failure.

The cause was that commit() routed every backend error through the
rollback-then-propagate path, which turns all errors into Err. A real
TiKV write-write conflict — reported by get_for_update at lock time or
by commit() at prewrite — was therefore mislabelled a fault.

commit() now classifies those two error arms: a rolled-back transaction
whose error carries a TiKV write-conflict signal returns Ok(Conflict);
everything else (network, region-unavailable, PD timeout, lock
resolution, deadlock, undetermined) still returns Err. Only a
KeyError bearing conflict information counts, recursing through the
batched/pessimistic-lock wrappers it can arrive inside; no other error
shape is folded, so faults stay faults. The MetadataStore trait is
untouched.

A new endpoint-gated property suite fans eight concurrent writers at one
shared key and asserts exactly one Committed, the rest Conflict, zero
Err, and a final stored value equal to the winner's write — for both a
value precondition and an absent-key precondition. It runs under
`cargo xtask tikv-conformance` against a throwaway single-node cluster
and skips cleanly where no cluster is configured, so the default gate
stays green without TiKV.
