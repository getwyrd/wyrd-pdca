server: make gateway id allocation safe for active-active gateways

The M4 front door is meant to run several gateway processes at once over
one shared fleet ("one shared front door, N gateways, plain round-robin").
Until now each gateway minted inode and chunk ids from private in-process
counters seeded from the same persisted high-water mark, so two gateways
started against the same store both handed out the same next inode and,
worse, the same next chunk id. The colliding inode was caught by the
create commit, but the fragments for a chunk were written to the D servers
*before* that commit, so the second gateway's fragments overwrote a
committed object's fragments under the shared chunk id — silent data loss.

Gateways now allocate inodes from the shared store's meta:next_inode CAS
allocator, the same scheme the CLI cluster path already uses, so two
active-active gateways can never mint the same inode. Chunk ids become
coordination-free: each gateway draws a random 64-bit epoch for the high
bits of every id it mints, so two processes occupy disjoint id ranges with
no shared counter, and a per-process monotonic sequence in the low bits
keeps an overwrite from re-minting (and clobbering) a prior version's ids.
Startup recovery seeds the persisted inode floor above everything already
on disk, so a restart — or an in-place upgrade from a store an older
single-process gateway left without the counter — never replays a
committed id. This preserves the single-process restart guarantee while
extending it to the multi-process case.
