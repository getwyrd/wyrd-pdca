core: refuse a multipart Complete whose part sets exceed one value

Core's part-number format allows numbers up to 999,999. When the numbers are
spread out, the set of published parts, or of staged parts the request left
out, can encode past the store's 100,000-byte value limit. The commit that
publishes the object writes each of those sets as one value, so the store
refused it every time: Complete took the fence, failed, released it and
returned a stopped error on every retry. The upload could only be aborted.

Complete now measures both sets as the exact bytes it would store and answers
Refused(SessionTooLarge { bytes, limit }) when either is past the limit. The
check runs before the fence, so an oversize request writes nothing, and again
against the set frozen behind the fence, so a part that lands between the two
reads is caught too. In that second case the fence is released and the
session is left Open with its attempt count restored. The publishing commit
now installs the same obligations the check measured, so what is checked is
what is written. A value exactly at the limit still publishes.

Within 1 to 10,000 part numbers the widest set is 58,909 bytes, so a session
in that range is never refused. The SessionTooLarge doc now says Complete can
answer it and what bytes means there. The part-set doc no longer claims the
worst case fits in one value.

Nothing calls Complete in production yet; the S3 verb comes with #670.
