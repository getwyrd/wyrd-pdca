read: enqueue repair when reading around a permanent block fault

A foreground Reed-Solomon read that hit a permanent block-layer read fault
(a dead sector) on one shard read around it and returned the object, but
recorded no repair obligation — the cluster silently carried avoidable
durability debt until a later scrub happened upon the same fault. Commit
1d2a46990631f8392b8d85579f8713ba9d41155f added telemetry for that error arm
and explicitly deferred the repair question to this issue.

The read path now recognises the fault through the system's single decision
point for permanence, wyrd_traits::is_block_read_fault, still reads around
it, and lands the affected chunk on the same shared repair queue scrub
feeds — with its own detected_by reason, "read-block-fault", and its own
telemetry counter. A block fault is permanent damage but not checksum
corruption: the corruption-specific counters and the "read" reason are
untouched, so the durability audit trail can tell a dead sector from bit
rot. Other non-integrity errors (timeouts, unavailable) stay transient and
un-enqueued, as before.

Regression test: crates/core/tests/read_block_fault_repair.rs — an RS(2,1)
read over a store whose block layer cannot read one fragment still returns
the correct bytes, and the repair queue now holds the chunk with the
non-corruption reason. Red before the fix (the queue stayed empty), green
after.

Fixes #431
