Add a deployable data-repair custodian with durability metrics

Running Wyrd in production had no operational-visibility floor: the
background data-repair worker existed only as a library with no runnable
caller, no process installed a telemetry handle, and nothing exported the
signal that says whether stored data is losing redundancy. An operator who
killed a storage node had no metric to watch to confirm the system noticed
the loss and repaired it.

This ships `wyrd custodian` as a first-class, deployable process. It
campaigns for single-active leadership over its zone, installs the shared
telemetry handle at startup, and runs the reconstruction loop against the
configured metadata backend and D-server fleet. The durability-telemetry
seam is lifted out of the custodian library into a shared, backend-agnostic
telemetry crate so no leaf crate anchors the export path; existing callers
that name DurabilityTelemetry / ExporterConfig keep compiling through a
re-export.

The under-replicated signal is now a level that rises when a node is killed
and returns to zero once redundancy is restored, so it is meaningful on a
populated store. Conditions that are worse or different in kind are routed
to their own signals instead of being folded into that level and pinning it
above zero forever: confirmed data loss (a chunk below its recoverable
fragment count), a transiently unreachable node during a rolling restart or
partition, a repair with no free failure domain to land on, and a malformed
placement. Distinguishing an unreachable node from confirmed loss keeps a
routine restart from raising a false data-loss alarm, and an all-unreachable
fleet at startup now fails loud rather than exiting silently.

The change is purely additive instrumentation and wiring: no commit
protocol, consistency contract, or on-disk format is touched.
