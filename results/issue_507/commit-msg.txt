s3 gateway: bucket listings (ListObjectsV2 + v1) for stock clients

Every stock S3 browsing client fails against the gateway today: aws s3
ls, aws s3 sync, boto3, rclone, restic and s3fs all start with a bucket
listing, and the gateway answers every bucket-scoped GET with 400
InvalidRequest. Listing is the largest gap after multipart in the
0.1-Alpha S3 epic.

Bucket-scoped GETs (/{bucket}, /{bucket}/) now route to a listing
handler instead of the object-path guard. ListObjectsV2 (?list-type=2)
supports prefix, delimiter (CommonPrefixes), max-keys, start-after and
opaque continuation-token pagination; a thin v1 ListObjects shim
(marker-based, NextMarker = the last returned item) covers older
clients. encoding-type=url is implemented rather than rejected —
botocore injects it into every ListObjects request, so it is
load-bearing for the exact clients above. Encoding is render-time only:
filtering, grouping, resume comparison and token payloads all operate
on raw keys.

Semantics follow AWS: max-keys counts Contents and CommonPrefixes
combined; a client-chosen start-after equal to a common prefix still
returns the rollup (start-after applies to the raw keyspace before
rollup); a continuation-token overrides a co-sent start-after;
max-keys=0 is an empty untruncated page; an invalid token answers 400
InvalidArgument. Per ADR-0046 the listing reads the bucket:{name}
record first, so an absent bucket answers 404 NoSuchBucket while an
empty bucket with a record lists as an empty 200. Bucket subresource
GETs (?acl, ?versioning, ...) still answer 501, matched on
percent-decoded query keys so an encoded subresource name cannot be
answered with a listing document; a path with an empty bucket segment
(//bucket) is rejected, not listed.

The listing crosses a protocol-neutral list_container seam:
gateway-core stays free of S3 vocabulary, wyrd-server scans the
per-bucket dirent prefix and returns one sorted view, and the S3 layer
computes grouping, the combined max-keys slice, pagination and the XML
(string-built — no new dependency). CreateBucket and the bucket:{name}
marker writes remain #511, so a live stack answers NoSuchBucket until
markers exist — the stated Alpha stance.
