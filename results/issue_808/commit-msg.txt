custodian: count staged multipart bytes in drain status

reconciliation_status certified a draining server Satisfied from
committed placements alone, so a server holding only a live upload's
staged bytes (a committed part's fragments, or an in-flight part's
owned entry with no part: record yet) could be told safe to wipe.
Wiping it loses bytes a later part-commit or Complete then publishes
a chunk map over.

reconciliation_status now reads the existing StagedSet class
(crate::gc::staged_fragments) beside the committed reference set, in
the same staged-before-committed order gc::reconcile already uses, so
a staged fragment on the server answers Pending. An unreadable staged
record blocks every drain (PendingUnresolvable); one that decodes but
carries an untrustworthy placement blocks every drain the same way an
untrustworthy committed placement does (PendingMalformed), sharing
one sorted, deduplicated list of chunk ids with the committed class.

Rebalance is unchanged: plan_evacuations scans the committed inode:
namespace only, so a draining server holding just staged bytes gets
no plan and the pass reports Reconciled::Satisfied about its own
question. That is not the operator's drain verdict, which is
reconciliation_status, and the two are now covered by one test
proving they agree per proposal 0016 decision 2. A doc comment on
plan_evacuations records that staged bytes are out of its scan by
construction, and the drain-status paragraph in
docs/design/architecture/06-runtime-view.md is corrected to match.

staged_protection.rs's guard leg narrows to scrub only, since drain
status no longer answers identically with and without upload records
by design; the new coverage lives in the new
crates/custodian/tests/staged_drain_status.rs.
