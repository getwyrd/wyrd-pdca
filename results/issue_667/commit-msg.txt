s3: stop encoded multipart queries overwriting or deleting objects

A client that percent-encoded a multipart query key could destroy an
object while believing it had sent a multipart request. A signed
PUT /b/k?part%4Eumber=1 answered 200 and overwrote k, and a signed
DELETE /b/k?upload%49d=<id> answered 204 and deleted k.

The object route refused these keys by matching the raw query, but SigV4
decodes the query once before checking the signature. The encoded key was
therefore valid to sign and invisible to the refusal, and the request ran
as a plain PUT or DELETE. Encoded denylisted keys such as t%61gging did
the same.

Decode the query once, as SigV4 does, and choose every route from those
decoded keys. No multipart upload operation is served yet. What clients
see now:

- A well-formed multipart request answers 501 NotImplemented, naming the
  operation, in any percent-encoded spelling.
- A malformed one answers 400 InvalidArgument where it used to answer 501
  or reach the plain verb: a key missing or repeated, a partNumber that is
  not canonical digits, or a method and path no operation takes.
- A multipart request whose decoded bucket name contains / answers 400
  InvalidBucketName.
- GET or HEAD with only partNumber still answers 501.
- POST /b?d%65lete now runs the bulk delete, as POST /b?delete does. It
  used to answer 501 and delete nothing.
