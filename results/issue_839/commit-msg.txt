custodian: restore reports staged skips and untrusted staged records

After a metadata restore, `wyrd custodian --reconcile-after-restore` kept
fragments that belong to in-progress multipart uploads without saying so,
and a damaged upload record it could not trust showed up only in the audit
log. The run could still be reported clean, even though such a record
blocks every drain in the cluster until someone removes it.

The report now carries two new fields:

- `staged_skipped` counts the fragments kept because an upload's own
  records name them. Each kept fragment is counted once, under the first
  protection that keeps it, so it is never also counted under
  `displaced_kept` or `pending_skipped`.
- `staged_untrusted` names each upload record the pass read but could not
  trust about where its chunk's fragments are (for example a placement of
  the wrong length). Any such record makes `is_clean()` false.

`needs_human()` and the command's exit status are unchanged. Its doc comment
now explains why an untrusted staged record is left out: once the session
is fenced (#841, #842) its bytes are garbage whatever the record says, so
what remains is cleanup, not a judgement. No client can create an upload
session in production yet, so the unfenced window is not reachable.

The CLI summary line prints both counts. Untrusted records get their own
informational line that names them, says the pass marked none of their
fragments and did not check that the staged bytes survived, and does not
promise any cleanup, since whether the retire drain removes them is still
open (#659). The m4 deployment blueprint's restore step describes the new
output.

Fixes #839
