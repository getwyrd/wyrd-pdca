server: select redb or TiKV metadata backend by configuration

Until now the `wyrd` server always stored its metadata in the embedded redb
store, with no supported way for an operator to run against a production TiKV
cluster — the backend was fixed in the binary. It now honours a
`--metadata-backend redb|tikv` flag (or the `WYRD_METADATA_BACKEND` env var),
defaulting to redb so existing single-binary and dev usage is unchanged. Both
backends drive the identical store paths, so choosing one is a configuration
choice, not a code change.

The local-disk put/get paths now run on the same tokio runtime the cluster
paths already used, so a runtime-bound TiKV client can run there instead of
being incompatible with the previous blocking executor.

Inode allocation previously retried a lost metadata race in an unbounded loop.
Over a distributed backend every attempt is a network round-trip, so a
persistent conflict could spin indefinitely. It now retries with capped
exponential backoff and returns a clear exhaustion error after a bounded number
of attempts.

TiKV is wired behind an off-by-default `tikv` build feature, so the default
build, its dependency graph, and its audit are unchanged.

Fixes #255
