fix(504): refuse CopyObject PUTs before they erase the destination

A CopyObject request is a `PUT /dst-bucket/key` carrying an
`x-amz-copy-source` header, and its body is empty: the payload is the
copy-source reference, not object bytes. The gateway never read that
header — dispatch is by method only — so the PUT arm streamed the empty
body into the destination key and answered 200. A client issuing a copy
(`aws s3api copy-object`, any SDK) got a success response and a
destroyed destination object: silent data loss.

Refuse that form up front. If a PUT carries `x-amz-copy-source`, return
`501 NotImplemented` (S3 error body) before any body byte is consumed,
leaving the destination untouched. This mirrors the existing subresource
guard and its rationale: a request form the gateway does not implement
is refused, never silently mishandled. The header is detected on the raw
request headers, so the guard applies whether or not the client included
it in its SigV4 signed-header set. Ordinary PUTs (no such header) are
unaffected.

Actual server-side copy (resolving the source object, aliasing its
chunks, returning the source ETag) is the follow-up step of #504 and
depends on the object-metadata model (#503); this change is only the
data-loss guard.

The regression test drives the real wire path (loopback TCP listener,
production SigV4 signing): pre-fix the copy-form PUT returns 200 and the
destination reads back empty; post-fix it returns 501 and the
destination's prior bytes survive identically.

Fixes #504
