custodian: record whether the post-restore upload fence completed

After a metadata restore, the post-restore pass fences every upload
session the restore brought back, so none can publish over data that was
already reclaimed. Nothing durable said whether that pass had finished.
An operator only had the console output of one run, and a gateway would
have nothing to check before serving multipart requests on the restored
store.

The pass now keeps one small record, "mpufence", holding a run number
(the restore-fence generation, counted from 1) and whether that run
completed. Each run first writes the next generation as not complete,
and marks or fences nothing until that write is acknowledged. After its
last write it marks the generation complete, but only if every write it
made was acknowledged and no upload session is left for a human. Both
writes are conditioned on the bytes last read, so a completion that
lands late never covers a newer run.

Every run judges already-fenced sessions again from their own records.
A session that an earlier run fenced but could not clear keeps every
later run from completing until someone repairs it, including after a
run that was cut short. Findings about committed objects, such as a
lost chunk, do not hold the generation back.

The CLI verdict now says which generation the run left and whether it
completed. A failed mark commit is now an error rather than being
silently counted as done.

A restore rewinds this record with everything else, so an image taken
after an earlier run completed reads "complete" until the next run
starts. Nothing reads the record yet. Until the gateway check lands, the
runbook's order keeps multipart safe: run the pass with writers stopped
and re-enable no gateway until a run says COMPLETE. The building block,
runtime and m4 runbook docs say so.
