Add the opt-in checked consistency run with real Elle verdicts

Wyrd's "no data loss under failure" claim was checked only by Wyrd's own
code, which is worth exactly as much as the reader's trust in us. This adds
the credibility artifact #329 asks for (DoD item 2): a checked run whose
consistency verdict comes from Elle — a checker we did not write and the
distributed-systems community recognizes — over a history recorded while a
real fault bit a live cluster.

`WYRD_TIER1=1 cargo xtask consistency-run` brings up the 3-node FDB cluster
(deploy/fdb-multi-replica), drives register and directory workloads under
the #407 partition leg (merged as
e0e39c1e120e3106a3adbb76ca5e583d35d56179), exports Elle-EDN histories,
invokes elle-cli per model, and renders the run report. `cargo xtask ci`
stays unprivileged, container-free, and JVM-free; the runner hard-errors
when opted in without docker, java, unzip, or the elle-cli jar — never a
silent skip.

The run refuses to overstate itself:

- The verdict is keyed on the checker's output token (`true` / `false` /
  `:unknown`), never on the exit code alone — `:unknown` exits 0.
- No verdict is reported unless the run summary attests a genuinely
  concurrent history AND a materialized fault (the nemesis leg's typed
  evidence, not a hard-coded boolean) AND a determinate composed final
  read; otherwise the run fails as inconclusive.
- The committed golden fixtures are real elle-cli samples (both models,
  both polarities, plus a captured degraded shape), and every live run
  re-feeds them through the same jar before trusting its verdicts.

The #406 EDN serializers are amended in place: the landed vocabulary was
rejected by the real checker (scalar `:value` for `rw-register`;
`:remove`/`:contains` for `set`). The register history now emits
transaction micro-ops and the directory a create-only integer `set` with
one composed post-heal read; unrepresentable ops (register DELETE,
directory remove/probe) are excluded by workload-pool construction, never
per-op filtering. Indeterminacy stays honest in both directions: a
transport failure is recorded as `:info` (never omitted, never a definite
`:ok`), the delete pool is single-writer-per-key so the version-tag checks
cannot fabricate violations on a correct system, and an unresolved
final-read member degrades the composed read to `:info` instead of reading
as a fabricated lost element.

The first witnessed run's report is committed at
docs/design/reviews/m4-checked-consistency-run.md: Elle returned `true`
for both models under a materialized partition. Its first carve-out names
the run's limit honestly — FDB absorbed the fault (the client saw zero
errors), so the verdict attests correctness under an absorbed partition,
not under client-visible disruption.
