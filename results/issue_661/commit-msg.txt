gc: page the orphan-ledger walk instead of one unbounded scan

GC and the post-restore repair pass each read the orphan-fragment
ledger with a single `scan`. That call fails outright, with no partial
result, once the ledger holds more entries than the store's scan cap.
A single large delete can install far more orphan marks than that cap,
so from that point on every GC pass fails before it can reclaim
anything, and the pass that would shrink the ledger back down is the
one that can no longer run at all. The post-restore repair pass hits
the identical wall and can never finish either.

GC and restore now read the ledger a bounded page at a time, resuming
where the previous pass left off and wrapping back to the start once
they reach the end, so the ledger is readable at any size. A pass
draws only safe conclusions from a partial read: a fragment whose own
mark falls outside the window it read is treated as unknown, not
absent, so an expired pending lease can no longer reclaim it out from
under a mark still in its grace period. A mark whose stored value does
not parse still counts as a mark and is kept and logged rather than
silently treated as unmarked. Only a key spelled exactly as the mark
writer spells it can license a reclaim. Restore's "already marked"
check now walks the whole ledger in the same bounded pages rather than
one scan, so it never re-stamps a mark it failed to read and resets
that mark's grace clock by mistake.

GC's own cleanup deletes, which previously committed in one batch
sized by the whole pass, now commit in fixed-size batches, so a large
reclaim can no longer hand the store a transaction that grows past its
size budget.

Fixes #661
