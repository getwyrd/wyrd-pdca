core: recover a multipart Complete from unknown commit outcomes

When the metadata store could not say whether one of Complete's commits
landed, Complete gave up with the in-doubt error every time. That was safe
but too coarse: a client whose object had in fact been published got an
error, and a Complete that could have carried on stopped instead.

Complete now reads the upload session again after an unknown outcome and
answers only from what that read proves:

- a flip that landed answers Published, once;
- a segment write resumes from the recorded cursor at the same epoch and
  writes no segment twice;
- an initial fence that did not land is sent again, a bounded number of
  times.

Two cases stay in doubt on purpose. A commit that may still be applied
keeps the request in doubt until a read shows it can no longer land. A
fence whose bytes are found in the session is never taken as proof of
ownership, because a rival Complete with the same timestamp builds
byte-identical bytes. A failed re-read, or a session record that does not
decode, also ends in doubt and never in an answer. If a re-read finds the
session rolled back to Open, Complete answers OperationAborted so the
client retries with a fresh timestamp.

The test wrapper gains a hold step that keeps a batch which may still
commit and lands it later. New tests cover each outcome, and the
architecture building-block view describes the recovery rules.
