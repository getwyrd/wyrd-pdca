# Adversarial review — issue 653 (staged segment publication committer)

**Evidence re-run.** In a scratch copy of `$PDCA_TARGET`, the 12 core tests and the 3 DST tests (built with `--cfg madsim`) pass. I re-made four of the builder's claimed red edits, and each one turns its named leg red: a pre-flip check over `0..resume_from` only fails D2; with the owned-key check removed, C fails; dropping the caller's preconditions from the flip fails F-r, D3 and F; with the fence-cycle check removed, the A→B→A test fails. C4-verify's UNVERIFIABLE result was declared in the brief (the module is new, so the test cannot compile on the old base). It is not a refutation. The fix holds on the paths the brief named. The bullets below are places where the tests cannot tell a correct committer from a broken one, plus one API gap #658 will hit.

- NEEDS-HUMAN [impl] — `crates/core/tests/segmented_publication.rs:429` / `:447`: leg (B)'s "within the operations budget" can never fail. With `BUDGET = 12_000` each segment batch holds one full row, so it carries 4–6 operations against `OPS = 64`. I removed both segment-phase operations checks (`crates/core/src/staged_publication.rs:640` refusal and `:651` `ops > budget_ops` break), and all 12 core tests still pass. C5's surviving mutants `640:16` and `651:44` say the same. The check matters in production: with default budgets (5 MB, 500 operations), a 300-segment map (47,400 one-placement chunks, within `MAX_STAGED_CHUNKS`) planned **602 operations in one batch** with the check removed. The real code splits it 500 + 104. That scratch test is **not** in the patch. Fix: add a (B) case where the operations budget binds and bytes do not, e.g. `ops_budget = Some(5)` with the default byte budget.
- NEEDS-HUMAN [impl] — `crates/core/src/staged_publication.rs:853` and `:857`: the brief's Design says the flip "pins the target dirent and inode on both branches" (`0016:663`, the iteration-9 rename race). No test checks either dirent pin. I deleted `.require_absent(dirent.clone())` from the Fresh flip, and separately `.require(dirent, encode(&DirentRecord { inode: id }))` from the Supersede flip. All 15 tests (core and DST) stayed green both times. cargo-mutants cannot generate a deleted builder call, so C5 could not have caught this. Concrete failing case: `RootTarget::Fresh { id: 9 }` for a name already bound to inode 8 rebinds the name and orphans inode 8, where the pinned flip returns `Conflict`. Fix: one Fresh-over-a-bound-name case and one Supersede-after-rename case, each asserting `Conflict` and an unchanged dirent.
- NEEDS-HUMAN [impl] — `crates/core/src/staged_publication.rs:416-417`: the brief's (D) says the pre-flip check covers all of `0..segment_count`. The tests only check half of that. I replaced the pre-flip check with one that checks only `resume_from..count`, keeping absolute indices. All 15 tests pass. D1 (`:632`) damages a row below the cursor *before* `publish` runs, so the first range read catches it. D2 (`:660`) deletes a row *at or past* the cursor. Nothing deletes a row below `resume_from` *during* the segment phase. Concrete failing case for such a committer: `resume_from = 2`, and a delete of `seg:…:0` after the last segment commit leaves a root naming a missing record. The fence obligation would also stop this; the brief asks for the check as a separate layer and says D2 is what tells implementations apart. Fix: a D2 twin that deletes index `< resume_from` in the same `Action::After` hook.
- NEEDS-HUMAN [impl] — `crates/dst/tests/segmented_publication.rs:234`: the (G) property "at most one root names the group" cannot fail in this scenario. The only inode ever published is `ID = 8` (`:45`), so `scan(b"inode:")` returns 0 or 1 rows whatever the committer does. This is the same blind spot as the dirent bullet: with either dirent pin deleted, the DST stays green. Fix: have the recovering publisher mint a fresh inode id per attempt, as a re-resolving Complete may, so that only the dirent pin prevents a second root. The other two (G) properties do mean something. My instrumented sweep reached `resume_from = 1` 58 times and `resume_from = 2` 22 times after landed `CommitUnknownResult`s, and the drain-on-read red fires.
- NEEDS-HUMAN [impl] — `crates/core/src/staged_publication.rs:557-560` (and the `:155-157` / `:400` API): the doc says that at the sizing scheme's widest ref the byte rule and the count rule agree, "so the plan is `⌈chunks / MAX_SEG_CHUNKS⌉` segments". That is the formula `0016:2346-2348` gives #658. But the byte rule at `:576` does bind for refs wider than the RS(6,3) sizing ref. 316 chunks under `rs(10,4)` with 20-digit placement ids encode to 408 B each, and the committer plans **3** segments where the formula says 2. The caller must pin the final cursor in its `flip_contribution`, and only `publish` is public. So #658 has to copy `split_segments`' arithmetic (80-byte envelope, +1 comma) or get the count wrong. A flip pinned at `cursor(2)` gave `Ok(Conflict)` after the segment rows were already written. A retry from `resume_from = 3` is then refused as `FenceCycled`, so the object can never publish. The tests hide this by hard-coding `SEGMENTS = 5` (core `:39`, DST `:50`). Fix: expose the plan's segment count (e.g. `pub fn planned_segments(&[ChunkRef]) -> Result<u32, PublicationError>`, reusing `split_segments`) and correct the doc. Separate question for #658, not this slice: the committer reads the compile-time `MAX_MAP_CHUNKS`/`MAX_SEG_CHUNKS`, while `KnobSet` (`crates/core/src/multipart.rs:5430`) makes them per-deployment knobs.
- NEEDS-HUMAN [impl] — `crates/core/src/staged_publication.rs:474-488`: I agree with T4's blocking finding: rebuilding a resumed prefix from one-row batches can raise a false `FenceCycled`. The same assumption also fails in the open direction. If a pure hook's *pin* depends on `written` (allowed by the contract at `:56-58`), the singleton rebuild can miss a value a coarser earlier batch really required, and a later return to it goes unflagged. Neither direction can happen with #658's cursor-shaped hook. No test exercises a resumed cycle at all: C5 mutant `481:28` (`i + 1` → `i * 1`) survived. Whatever fix answers T4 should state, or check, the hook shape the rebuild relies on (pin a function of `first_index` only, put of `written` only) and add a resume-then-cycle test.
- Agreeing with T4's third finding (`crates/core/tests/segmented_publication.rs:342`, `:440`): (B) measures mutation bytes only. That matches the brief's wording, so a reviewer could reject the finding by citing the brief. But `batch_bytes` (`staged_publication.rs:666-668`) says it counts "the whole transaction", and the row and precondition accounting mutants (`598:8`, `673:30`) survive. The test does not check the accounting the module documents.
- Smaller branches with no test (C5 survivors, not NEEDS-HUMAN): `FenceDeleted` (`:468`), the delete-the-fence branch of `check_fence_moved` (`:751`), contribution `ValueOverCeiling` (`:731`), and the `MAX_ROOT_SEGMENTS` boundary (`:586`, exactly 512 segments must be accepted).

**Attempted to refute, could not:**
- every input-decidable refusal runs in `prepare` before any read or commit (`:404`);
- E's atomicity holds, and its second half would catch a split contribution;
- F-r and F-p hold;
- the epoch ranges cannot collide, because `seg_range_prefix` ends in `:` (`metadata.rs:1507`);
- the `read_group` guard mutants (`:929`) are equivalent, since any key that parses under the prefix carries the group's nonce and epoch;
- the off-by-one at the absolute widest ref (80 + 158×316 > 50,000) is unreachable, because 158 refs with 20-digit `len` overflow the u64 object size;
- the module reads no clock (ADR-0009);
- the docs-currency paragraph is present (`08-crosscutting-concepts.md:91`).
