multipart: define protocol capacity knobs and knob_clamps_hold

Add the multipart upload protocol's capacity numbers to
crates/core/src/multipart.rs: one named constant per knob (chunk
caps, session and in-flight limits, batch byte/op ceilings, the
memory budget, and the retry/backoff bounds), each with its
derivation recorded in its own doc comment, plus knob_clamps_hold,
a function that checks a whole set of these numbers against the
inequalities that must hold between them and reports which one
failed.

This closes a real failure class already seen in production: when
one number is picked in isolation without checking it against the
others, a session can be admitted with a workload that later can
never be cleaned up (never fenced, never deleted), because the
batch needed to undo it exceeds the transaction budget. That
happened once before (see docs/principles.md's storage lifecycle
invariant, added after the 2026-07-25 incident). This change gives
every future consumer of these numbers (the reaper, the gateway,
the rest of the multipart protocol) one authoritative, self-
consistent set to read instead of each re-deriving its own, and a
single check that catches a value set that doesn't hold together.

Nothing in this change is wired up yet: no code enforces these caps
on real uploads, and no existing behavior changes. That comes in
later, separate changes. This one only ships the numbers and proves
they are mutually consistent.

Two constants are still assumptions rather than measurements
(W_REF, the reconcile memory budget, and the 5ms-per-operation
estimate behind MAX_BATCH_OPS) and are documented as such; the
doc comments name the follow-up work that must calibrate them
against a real backend before they're relied on for correctness.
