dst: pin MetadataStore by driving both backends in the simulator

Wyrd is gaining a second production metadata backend (TiKV) alongside
redb. A store trait's concurrency semantics are only trustworthy once two
implementations run the identical property suite — until now the
deterministic simulator drove only redb, whose commit is a single atomic
write transaction. TiKV's commit awaits on network I/O mid-flight, which
opens interleavings redb can never produce: a second writer can be
scheduled inside another writer's in-progress commit. That whole class of
schedules had no automated coverage, and the concurrency module comment
even claimed "no await inside" as the ground of determinism — untrue of a
commit that awaits on the network.

Drive the identical shared trait-contract suite and the exactly-one-winner
race through both backends inside the simulator: the deterministic redb
backend and a deterministic simulated-TiKV model whose commit awaits
mid-flight (a test-only model, never a real or containerized TiKV). Rest
the determinism rationale on madsim's seed-reproducible scheduler instead
of on atomic commits, and commit a fixed seed that reproduces the
mid-commit interleaving forever — with a synchronous twin proving that
schedule is unreachable without the await boundary, so the new coverage is
load-bearing rather than a tautology. Exactly one writer still wins across
the interleaving, because the winner is decided at an atomic prewrite
lock-grab, not spread across the await.

The MetadataStore trait is unchanged and all new code is test-scope; the
Tier-0 redb simulator suite stays green and seed-reproducible.

Fixes #258
