core: move, don't copy, the chunk list on every streamed GET

A streamed GET of a flat (non-segmented) object copied the object's whole
chunk list, every chunk reference and its placement vector, before handing
it to the reader task. The comment above that line said it was a move. The
cost was one allocation plus a copy that grows with the chunk count, on
every flat-object GET, the hottest read path. The bytes served were always
correct.

Commit bbdb7c51382ade669d07f0580a3f3e343c28c34d made this read move the
list out of the inode it owns. Commit
99c7fcf11a95f4d3aa5718ebc6865ce70621bd4b routed the read through the shared
chunk-map resolver, which only borrows the inode, so taking an owned list
from it went back to a copy.

Add resolve_chunk_map_owned beside resolve_chunk_map. It applies the same
resolution, restart and deletion rules, but takes the committed record by
value. For a flat map on a live snapshot it destructures the record and
moves the list out, along with the framing fields the GET needs (size,
etag, content type, modified time), so nothing on that path clones the
record or the list. Segmented maps share one table-order assembly helper
with the borrowing path. A generation superseded mid-resolve still
restarts through resolve_current_chunk_map, unchanged.

The streamed GET now calls the owning entry. The ranged GET, the
whole-object read and the maintenance passes keep borrowing through
resolve_chunk_map. ChunkMap::into_flat, which had no caller left, is
removed, and the doc comments that named the old path are corrected.

A new test, crates/core/tests/streamed_read_chunk_map_ownership.rs, checks
that the resolved list and its first placement vector are the record's own
allocations, and that the segmented, superseded and deleted cases answer
as before.

Fixes #686
