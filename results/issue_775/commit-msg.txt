xtask: fail CI if wyrd-validate can reach a Wyrd crate

wyrd-validate is only useful if it judges Wyrd from the outside. If its
binary ever linked a wyrd-* crate, it would be checking Wyrd's types
against Wyrd's own types, and a bug shared by both sides would pass.
Until now only habit kept that from happening.

`cargo xtask ci` now runs a third repo guard, next to the gitlink and
unsafe-code guards. It reads `cargo metadata --locked --all-features`,
walks the normal dependency edges of wyrd-validate transitively, and also
checks its declared dependency list, so a Wyrd crate behind an optional,
off-by-default feature is still caught. Dev-dependencies stay allowed,
because the validator's test fixtures need them. Metadata the guard
cannot fully read is a failure, never a pass. `--locked` keeps the guard
from rewriting the Cargo.lock it audits.

The guards are now listed as data in `xtask::repo_guard::CI_GUARDS`, and
`run_ci` runs them through one dispatcher. `cargo xtask ci-dry-run
[--workspace DIR]` runs that same guard phase for real on any workspace
and only prints the cargo steps, so the tests can prove the gate itself
stops on a forbidden dependency. `cargo xtask blackbox-guard [--metadata
FILE]` runs the new guard alone. The two existing guards give the same
verdicts as before.

This needs the wyrd-validate crate (#774) on main first; without it the
guard refuses to pass and `cargo xtask ci` fails.

Fixes #775
