Add etcd coordination backend for multi-node clusters

Until now the cluster coordination layer (peer discovery, custodian
leader election, distributed locks, and fencing) had a single
implementation: a process-local, in-memory one whose registrations,
elections, and locks were visible only inside one process. A real
multi-node deployment therefore could not discover its peers, elect a
single custodian leader, or fence a stale holder across machines —
cross-process L5 coordination simply did not exist.

This adds a networked, etcd-backed implementation of the existing
Coordination trait: leased registration with discovery, campaign-based
leader election with a monotonically rising fencing token, mutually
exclusive fenced locks, and revisioned config. The backend is chosen by
server configuration; the trait and every caller are unchanged, so
selecting it is a composition swap, not a code change for consumers.
The in-memory backend remains the default for local and dev use.

One shared conformance suite pins the trait for both backends, so the
in-memory and etcd implementations are held to identical semantics
rather than each asserting its own. Running that suite against a live
etcd surfaced a genuine defect a simulator had masked — a lock guard
phrased as "value absent" never fires on real etcd, so a free lock was
refused — now corrected by testing for the held state instead.

The etcd client is gated behind an off-by-default feature; its
dependency review and TLS/auth posture are tracked as follow-up before
production exposure.
