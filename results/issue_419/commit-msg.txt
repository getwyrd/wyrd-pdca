test(metadata-conformance): read-consistency properties, redb (#419)

The metadata store's read-consistency contract — a read observes the most
recently committed value, a mutation landing between a read-then-commit's
read and its commit loses cleanly rather than tearing the binding, and a
single listing observes one consistent cut — was captured only in prose.
Nothing executable pinned it, so a backend that served a stale read, let a
stale writer's commit through, or leaked a deleted key from a listing would
pass the existing suite unnoticed, and the upcoming second backend had no
shared baseline to preserve.

Add three backend-agnostic conformance properties to the shared suite —
read-after-commit, rename-race-yields-conflict, and scan-is-consistent-cut —
covering the snapshot/temporal dimension the four existing sequential
contracts leave untested, and run all three against the redb store. Each
property ships with a deliberately-broken store that the property catches
while the existing contracts still pass it, so every new property is shown to
add coverage the suite lacked rather than restate a check already present. A
second backend driving the same trait inherits the properties unchanged.

Test and suite code only; no production behaviour changes.

Fixes #419
