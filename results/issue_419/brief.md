## Invariants to hold (from the design corpus)

- **No production behaviour change:** `metadata-redb/src`, `metadata-tikv/src`, `core`, `traits` are untouched — #419 adds test/suite code only. If a property fails on redb, that is a *finding* to raise, not a license to change production code in this slice.
- **Backend-agnostic:** the properties use only the `MetadataStore` trait surface (no `Database`/redb or `tikv-client` API), so both backends' suites drive the same code — the point of a shared suite (a fork would let the contracts drift).
- **Deterministic on redb:** reuse the existing `pollster::block_on` + `wyrd_testkit::Sim(seed)` pattern so the redb run is deterministic and un-containerized (ADR-0009 spirit).
- **Non-vacuous AND non-redundant:** each property is demonstrated red against a violating store — a green that can never turn red is not a pin, and would give #254 a false baseline. In particular **read-after-commit** must add discriminating power *beyond* the existing sequential `contract_commit_and_get:24-37` (its point is the fresh-TSO / cross-handle read-your-writes semantics that bites on TiKV, not the sequential single-handle case already covered), and **rename-race** beyond the sequential `contract_require_value_gates:83-111` (its point is the *interleaved* mutation). On redb (atomic/local) these may look identical to the sequential tests; their value is the TiKV inherit and the documented pin.
