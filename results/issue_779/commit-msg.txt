gateway-s3: name the build on every response with a Server header

The S3 gateway sent no version on the wire. A client could not tell one
deployment from another, a captured HTTP exchange did not say which build
produced it, and a version-keyed client capability matrix had nothing to key
on except an operator-supplied value that can silently be wrong.

Every response the gateway service produces now carries
`Server: wyrd/<build identity>`: successes, client errors (including the
403 for an unsigned request), server errors, and the head of a streamed GET.
The identity is the one the binary already logs as the `version` field of
the s3 role's `role started` event, so the wire and the log name one build.

The header is stamped in `handle`, next to `x-amz-request-id`, which every
request reaches through the router's single fallback, so no handler can
forget it. The gateway crate owns the header and its `wyrd/` shape; the
composition root supplies the version through a new
`S3Config::server_version`. A library caller that never sets it advertises
`wyrd/unknown`, and a value that is not a valid RFC 9110 token falls back to
the same with a warning, so the header is always present and well-formed.
Responses hyper sends before the service runs (a malformed request line, an
oversized header section) still carry no Server header.

This tells unauthenticated callers the exact build. That is intended, since
the point is to key client behaviour and bug reports to the build, and the
threat model now records it, including that a release cut from a modified
tree says so. An operator who must hide it can rewrite or strip the header
at a fronting proxy.

The release workflow's installer smoke step now starts the installed
`wyrd s3`, sends one unsigned request, and fails unless the single Server
value equals `wyrd/` plus the `version:` line of the tarball's VERSION file.

Fixes #779
