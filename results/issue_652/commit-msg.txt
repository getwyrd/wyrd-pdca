fix(server): make startup recovery total over unreadable records

Startup recovery ran before the gateway served anything and refused
to finish over content it could not read: one undecodable `inode:`
value, or one structurally valid segmented root, made
`Gateway::recover` return `Err`, costing every healthy object its
availability (docs/principles.md §5 C-1). `high_water_marks` now
derives the inode floor from each row's key, attributes a row it
cannot fully account for on the `wyrd.metadata.recovery.audit` seam,
and walks on instead of stopping — the same containment the
custodian's GC walk already gives this namespace
(crates/custodian/src/gc.rs:378-382). `seed_next_inode_floor` is
total over the persisted `meta:next_inode` counter's bytes the same
way, repairing it under the existing compare-and-set rather than
failing recovery outright.

The chunk-id half of the old mark is deleted rather than wired. Its
consumer was removed deliberately by fdd34f1 (#487, 2026-07-08),
which changed both halves at once: before it, `mint_chunk_id` was a
plain counter from 0 and `recover` consumed the floor; after it, ids
are `(chunk_epoch << 64) | seq` with the epoch's top bit set, so
every minted id is >= 2^127, drawn from a random per-process epoch,
and `next_chunk_seq` is never seeded from it. The cluster-path
minter never needed it either: `chunk_id_minter` yields
`(inode_id << 64) | seq` with `inode_id >= 1`, so every cluster id
is >= 2^64. Nothing in the tree mints below 2^64 any more, so wiring
the old mark would mean inventing a consumer for a number nobody
reads.

The standing test that reasoned about that dead mark is replaced by
one that asserts totality instead: a healthy record, a segmented
root, an undecodable value, and a row whose key names no id all
contribute to the recovered floor rather than ending the walk, and
each unaccountable row is attributed exactly once.
