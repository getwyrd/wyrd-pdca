custodian: refuse oversized flat placement writes, don't certify them

Two related defects on the flat repair/evacuation write path:

1. Every placement mutation is a full-value CAS
   (`require(key, encode(prior))` + `put(key, encode(next))`) and
   nothing weighed the re-encoded record against the backend value
   ceiling (`MAX_VALUE_BYTES`, crates/core/src/metadata.rs:327). A
   repair or drain that repoints a fragment onto a large D-server id
   can grow the record past that ceiling. On a backend that enforces
   it, the write surfaces as a raw error indistinguishable from a
   transient fault; on one that doesn't, it commits a record that no
   later repair can ever overwrite again — an object whose placement
   can never be maintained.

2. A move that did not persist could still certify: rebalance's
   `EvacOutcome::Aborted => {}` arm was silent, so a pass that moved
   nothing still answered `Reconciled::Satisfied`, telling an
   operator a draining server was safe to remove while it still held
   a fragment.

This adds a single ceiling check (`flat_value_ceiling_crossed` in
crates/core/src/metadata.rs) that both write paths call on the
already-encoded record before writing anything at all, refusing the
write and leaving the obligation queued rather than committing an
unrepairable record or an opaque error. A refused, aborted, or
lost-CAS move now withholds `Reconciled::Satisfied` for the pass,
and the new refusal is added to the reconstruction/rebalance
success-accounting identity (`repaired - conflict - aborted -
ceiling_refused`) so it is never counted as a success.

Fixes #710
