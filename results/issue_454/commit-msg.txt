s3 gateway: select cluster backends by config, not hardcoded

The `wyrd s3` gateway ignored the backend-selection flags that every other
cluster-facing role honours. It always built a private local metadata store,
a local-disk chunk store, and in-process coordination, so passing
--metadata-backend, --coordination-backend, or --endpoints had no effect.
Running several gateways therefore gave several independent single-node object
stores: an object uploaded through one gateway was invisible to the others,
and nothing was stored across the cluster's storage servers.

The gateway now resolves its metadata and coordination backends through the
same helpers the put/get, custodian (#255), and d-server (#449) roles use. When
--endpoints is given it fans each object's chunks out to the configured storage
servers over gRPC instead of writing them to local disk. Omitting --endpoints
preserves the existing single-node local-disk front door. All four backend
combinations (redb or tikv metadata, mem or etcd coordination) are wired
through the production helpers, not stubbed.

The multi-node deploy compose file now points its three gateways at the shared
cluster metadata, coordination, and storage servers, so they act as one pool
rather than three independent islands.

Fixes #454
