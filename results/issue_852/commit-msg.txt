validate: add the S3 client wyrd-validate talks through

wyrd-validate could parse its flags and resolve credentials, but it had no
way to talk to an S3 endpoint. This adds the client every later validator
slice calls through: aws-sdk-s3 pointed at the user's --endpoint, with
path-style addressing, static SigV4 credentials, plain HTTP, and retries and
stalled-stream protection turned off so each result reflects one real
request.

Failures come back as one typed error with a variant per place a call can
fail: an S3 error response (HTTP status, <Code>, <Message> and the
x-amz-request-id header as fields), a response that cannot be read as S3,
no response, a deadline naming its phase (connect, operation or body-idle),
a request the SDK refused to build, and a broken object body. The request
id is read from x-amz-request-id itself, because the SDK's own accessor
prefers x-amzn-requestid when both are present.

Bodies stream both ways and are never held whole. A PUT forwards the
caller's pieces as they are pulled and checks them against the declared
length, so a source that ends short, runs long or fails is an error and
nothing is stored. A GET hands back pieces as they arrive, and a cut
connection is an error, never a shorter object. An always-ready source of
empty pieces yields to the scheduler, so the operation deadline still fires
on a current-thread runtime.

aws-sdk-s3 moves from a dev-dependency into the shipped graph, with a
>= 1.144.0 floor. That release is the first to require lru ^0.18.2, and the
lock resolves lru 0.18.4, so the RUSTSEC-2026-0253 waiver in deny.toml and
deny-all-features.toml is deleted: the advisory is no longer in the graph.

The tests run the real client against an in-process S3 gateway on loopback
through a byte-counting relay. No container and no network are needed.
