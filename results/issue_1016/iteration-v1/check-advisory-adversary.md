# Adversarial review — issue 1016 (625.2: the multipart reaper on every custodian startup shape)

I re-ran the evidence on a scratch copy of `$PDCA_TARGET` (cargo 1.96.0; scratch build, then removed). G2a and G2c do run the real `wyrd` binary with no one-shot flag, and they do go red on the base for the store assertion (see `gate-logs/C4-verify.log`). The panic text and exit status 101 are unchanged. Everything below was reproduced unless it says otherwise.

## Findings

- NEEDS-HUMAN [impl] — **`--reconcile-after-restore` on a dead fleet now changes the store before it fails.** `crates/server/src/cli.rs:1251-1296` (the empty-fleet reaper pass) runs before the restore one-shot's own branch at `cli.rs:1329`. The no-endpoints branch refuses the restore one-shot *before* reaping (`cli.rs:1164-1175`); the empty-fleet branch has no such guard. Reproduced: I seeded leg A and ran `wyrd custodian --reconcile-after-restore --endpoints http://127.0.0.1:1 --ids 1 --failure-domains domain-1 --connect-timeout-secs 1`. It exited 101 with the usual diagnostic, but `mpu:` went from `Open@0` to `Aborting@1`, 3 `orphan:` marks were written and a `retire:bytes:` obligation was created. On the base, the same command panics and leaves the store untouched. The restore pass is "explicit, never automatic" and fences resurrected sessions itself under its own restore-fence generation (`crates/custodian/src/restore.rs:64-69`, `:94-100`). Now the reaper acts on a just-restored store before that generation is opened, under a command that then fails. The brief scopes the pass to "the ordinary role". Fix: skip the pass when `reconcile_after_restore` is set, and add a test that the store stays byte-identical.

- NEEDS-HUMAN [human] — **G2b was never red, because the defect the brief describes for the fleet shape does not exist on this base.** In the base, `HEAD:crates/server/src/custodian.rs:680` already hands `Some(&reaper)` to the reconstruction pass, which runs every interval. The GC gate is further down, at `HEAD:…/custodian.rs:749`. I ran the new test `deployed_loop_reaps_an_idle_upload_on_a_degraded_fleet_while_gc_is_deferred` (`crates/server/tests/custodian_gc.rs:1748`) with `cli.rs` and `custodian.rs` reverted to HEAD: **it passes**. So two lines in the brief are wrong: the Defect line ("That call sits behind GC's whole-fleet gate… `custodian.rs:680-713`") and the Falsifiability line ("G2b reds because the reaper sits behind the whole-fleet gate"). The fleet-path edit at `custodian.rs:755` is a refactor that changes no behavior. G2b only guards against a future regression (negation 11), and the green ci row is not red→green evidence for it. This isn't a defect in the patch, but one of the three claimed defects was not real, and the human should know that before sign-off.

- NEEDS-HUMAN [impl] — **G2a does not prove that the role reaps "every interval".** `run_until` restarts the role up to `CONVERGE_RUNS = 6` times (`crates/server/tests/multipart_reaper_deployed.rs:66`, `:234`). The restarts do the work that later intervals should do. I tried a mutant where the no-endpoints branch runs one pass (`std::future::ready(())`) and then idles on `shutdown.await` forever. G2a **passes** (3 restarts, 9.1 s). With `CONVERGE_RUNS = 1`, the mutant fails ("did not converge within 1 runs") and the real fix passes in 3.1 s. The brief's G2a also asks for a single bounded run. Fix: give G2a a single window, with no restarts.

- NEEDS-HUMAN [impl] — **G2c does not pin the "exactly one pass" rule** (brief Scope: "Run exactly one reaper pass"). I tried a mutant where the empty-fleet call passes `tokio::time::sleep(3s)` as its shutdown, so the role runs several passes before it panics. G2c **passes**. After one real pass, the session is still present as `Aborting@1` and its `retire:bytes:` obligation is still standing (I saw this in the restore repro above). So asserting after run 0 that `mpu:` still exists and is `Aborting` would catch the mutant. The brief's literal G2c (one run, then all three asserts) can't be met, because teardown takes 2–3 passes. The restart loop is a reasonable workaround, but the test doc at `multipart_reaper_deployed.rs:530` should say so.

- NEEDS-HUMAN [impl] — **`EMPTY_FLEET_REAPER_PASS_BOUND` does nothing on redb, the default backend.** The comments at `cli.rs:908-913` and `cli.rs:1267-1269` say the pass is bounded "the store open included". But `open_local_meta_redb` (`cli.rs:2251-2256`) is synchronous, and the redb adapter's `get`/`scan`/`scan_page`/`commit` (`crates/metadata-redb/src/lib.rs:200-342`) never await. So the whole pass finishes inside the first poll of `tokio::time::timeout` (`cli.rs:1270`), and the timer can never fire. The bound only works for tikv/fdb. (Dropping a TiKV transaction on timeout is safe: `crates/metadata-tikv/src/lib.rs:1142` uses `CheckLevel::Warn`.) Fix: either say the bound covers only the networked backends, or run the redb arm on a blocking thread. Not reproduced, since I can't make redb hang; this comes from reading the code. Low practical risk.

- NEEDS-HUMAN [impl] — **The new subprocess tests take the backend from the caller's environment.** `role()` (`multipart_reaper_deployed.rs:152-158`) neither passes `--metadata-backend redb` nor clears `WYRD_METADATA_BACKEND`, and `resolve_backend` falls back to that variable (`cli.rs:292`). On a build with `--features tikv` and that variable set to `tikv`, this destructive pass would run against the configured cluster instead of the temp redb store. Fix: pass the flag explicitly or clear the variable.

- NEEDS-HUMAN [human] — **The no-endpoints role now creates a store if none exists, then reaps it forever and reports nothing wrong.** Before this patch the no-endpoints role opened nothing. Now `run_reaper_over_backend` uses the store-creating open (`cli.rs:1875-1880`, `:2251-2256`). With a mistyped `--data-dir`, or the shipped systemd unit run without `--metadata-backend fdb` (`deploy/dist/systemd/wyrd-custodian.service:28` pins `--data-dir ${STATE_DIRECTORY}`), the role creates an empty redb store and prints "Running the multipart reaper alone every Ns" for as long as it runs. That is the false all-clear the one-shot was built to refuse (`cli.rs:2258-2270`; the rubric's "never silent success"). The fleet role opens its store the same way, and the doc comment calls this deliberate, so it's a design decision, not a slip.

## Attempted, could not refute

- **Production path:** G2a/G2c spawn `CARGO_BIN_EXE_wyrd` and assert the one-shot flag is absent. The red leg fails on the store assertion (exit 0 on the base for G2a, 101 for G2c), not on a mocked defect.
- **Panic contract:** the message and exit code 101 are unchanged, and a pass error is logged rather than returned (`cli.rs:1285-1296`). A partly reachable fleet still takes the unchanged degraded-start path.
- **Loop error handling:** `run_reaper_until` (`custodian.rs:541`) covers both `ReconcileError` variants (`crates/custodian/src/reconciliation.rs:100-103`). A `Fenced` error stops the loop and a store error is retried, the same as the fleet loop. `biased;` (`custodian.rs:575`) makes a ready shutdown end the loop after exactly one pass.
- **Clock (ADR-0009):** each loop uses one `LoopClock`, and the reaper, the drain and `now_millis` all read it.
- **File ownership:** the patch stays inside the files the brief assigns; nothing under `crates/custodian/`, `crates/core/` or `crates/dst/` changed.
- **Ctrl-C during a stalled pass (raised by T4):** shutdown is only checked between passes, but that matches the existing fleet loop (`custodian.rs:868-871`). It is not new to this diff, so I'm not raising it.
