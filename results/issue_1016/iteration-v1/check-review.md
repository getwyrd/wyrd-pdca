The core startup fix reproduces red→green, but the restore-command side effect, scheduling tests, backend isolation and redb exit bound need correction. The single-start G2c acceptance criterion and unavailable prior-art history need human decisions. These are advisory judgments; they do not replace the deterministic gates. Source citations are relative to `$PDCA_TARGET`; evidence-log citations are relative to this review directory.

- **Restore refusal now changes upload state.** An isolated reviewer probe copied the supplied leg-A fixture into scratch and invoked the unchanged built binary with `--metadata-backend redb --endpoints http://127.0.0.1:1 --ids 1 --failure-domains domain-1 --connect-timeout-secs 1 --reconcile-after-restore`. It exited 101 with the existing diagnostic, but the session changed from `Open@0` to `Aborting@1` (`reviewer-probe.log:6`). The reaper precedes the restore-mode check at `crates/server/src/cli.rs:1329`. Keep this new work on the ordinary-role path and add a regression asserting that refused restore invocations leave metadata unchanged.
- **The tests do not enforce their scheduling claims.** `run_until` starts up to six separate processes (`crates/server/tests/multipart_reaper_deployed.rs:234`). G2a could pass after one pass per startup followed by indefinite idling; G2c could pass after several passes in one startup. Require G2a to converge within one process lifetime and assert G2c's first-pass state/count or a reliable pass-count observation. The current implementation's one-pass ordering is visible at `crates/server/src/custodian.rs:572`, but that is not a regression oracle. Independently, one ordinary empty-fleet invocation left `Aborting@1`, count 1 (`reviewer-probe.log:3`), so the brief's full-transition-after-one-invocation requirement needs reconciliation with its exactly-one-pass limit.
- **The subprocess fixture is not isolated from backend configuration.** `role()` supplies only a data directory and interval, while `resolve_backend` consults the environment. Running the original tests with `WYRD_METADATA_BACKEND=pdca-reviewer-invalid-backend` produced 0 passed / 2 failed, with the backend-selection diagnostic (`reviewer-backend-isolation.log:15`). This safely demonstrates the selection leak without contacting a service. Pass `--metadata-backend redb` explicitly in the fixture command.
- **The 60-second timeout is cooperative, not an I/O watchdog.** The timed future calls `open_local_meta_redb` synchronously, which reaches synchronous `Database::create`; redb metadata operations likewise do synchronous work inside async methods (`crates/server/src/cli.rs:2251; crates/metadata-redb/src/lib.rs:119; crates/metadata-redb/src/lib.rs:200`). If those calls stall, the timer cannot regain control of that future. The no-endpoints loop also polls shutdown only after the pass (`crates/server/src/custodian.rs:559`). This is a source-grounded liveness defect; no disk stall was injected. Provide an effective bounded execution strategy without leaving detached work mutating the store after cancellation, and test the failure path.
