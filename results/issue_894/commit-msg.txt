core: create multipart sessions, admitted through the mpuctl ledger

Nothing on main could start a multipart upload: the multipart module only
defined the record types, and no code wrote a session. This adds
create_session in wyrd-core, the store side of CreateMultipartUpload. It
admits a new session through the fleet-wide session ledger (mpuctl) and
installs the session record and its segment-group marker in the same atomic
batch that bumps the ledger count, so every session that exists is counted
and can later be reclaimed.

Concurrent uploads are admitted, not refused. Losing the ledger
compare-and-swap to another create is contention, not a full ledger: the
create backs off and retries under the same identity, with a budget equal
to the profile's max_sessions. An earlier attempt refused 2-3 of 8, 10 or
16 concurrent creates; 10 is aws-cli's default concurrency.

The real limits answer in the existing vocabulary and write nothing: a full
ledger (SlowDown/SessionCap), a profile mismatch (ProfileSkew), a missing or
changed bucket (NoSuchBucket), spent contention (SlowDown/
AdmissionContention), and a session whose widest later state would exceed
the value-size limit (the new Refusal::SessionTooLarge).

When the store cannot say whether a commit applied, the create re-reads and
adopts the session only if it finds exactly the bytes it wrote; any other
record is someone else's. If a batch may still land, it ends InDoubt naming
its own upload id instead of minting a new one, and that error classifies
Indeterminate, so a generic retry will not re-run it.

There is no production caller yet; the S3 verb is #668. Abort is #895, and
the bucket deletion fence is #511. The new tests cover each rule in
crates/core/tests/multipart_create.rs, plus a seeded DST scenario in
crates/dst/tests/multipart_admission.rs.
