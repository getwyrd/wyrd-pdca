Add a networked S3 client that records real-time operation history

Wyrd's design guarantees that overwrites to a file take effect in a single
agreed order: once a newer version is committed, no read may still return an
older one, and no read may return a half-applied value. That guarantee could
be stated in the design docs but not checked against the running system --
the object API was reachable only in-process, and the one over-the-wire
exercise of it recorded nothing about when each operation actually happened.

This adds a reusable client that drives overwriting PUT / GET / DELETE against
the S3 HTTP endpoint (added in #448) over a real network connection and
records, per operation, the object key, the version written or read, the
status returned, and the wall-clock span the round trip was observed over.
Driving a v1 -> v2 -> v3 overwrite sequence with interleaved reads now yields
a non-vacuous, real-time-ordered history a consistency checker can consume --
the evidence that verification work was missing.

The client signs and speaks real HTTP over the socket and adds no new
production code path; it is the harness's real client, not a mock. The
consistency verdict engine and the multi-node partition testing that consume
this history are separate, later work tracked under #329.
