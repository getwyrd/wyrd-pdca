fix(custodian): resolve segmented maps in GC/scrub, fail closed

A segmented object stores its chunk list across separate `seg:` records
instead of inline on its root. `referenced_fragments` (the protected-set
builder GC and scrub both gate on) only ever read the inline list, so a
segmented object's chunks were simply absent from the set it builds. GC's
safety gate would then treat every one of that object's fragments as
unreferenced and eligible for deletion, and scrub would silently skip
verifying them while still reporting the store clean.

Separately, when a committed object's chunk map could not be read at all,
GC already refused to reclaim any fragment (`ReferenceSet::protects`
withholds everything while the set is incomplete), but the pass still
reported `Reconciled::Satisfied` — telling an operator the store had
converged while holding a reference set it knew was partial. Scrub already
refused to certify in the same situation; GC did not, so the two passes
disagreed about the same store.

This change routes the reference build through the shared chunk-map
resolver, so a segmented object's fragments are included. It also adds a
third `Reconciled::Blocked` outcome: whenever the reference set is
incomplete, GC and scrub both report `Blocked` instead of `Satisfied` or
`Changed`, reclaim nothing, and attribute the unreadable record on the
audit log. A single damaged or unreadable object no longer stops the walk
over the rest of the store — every other object is still protected and
verified — and a genuine store-access fault (as opposed to one object's
fault) still propagates as an error.

Fixes #650
