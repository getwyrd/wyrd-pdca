core: add repoint_chunk to move a chunk in flat or segment records

Repair can move a chunk to new servers only when the object's chunk map is
stored flat in its inode record. For a large object whose map is split into
segment records, no code path can rewrite a segment, so a lost fragment of
such an object can never be re-placed and its repair is refused on every pass.

This adds the missing write primitive in wyrd-core. `repoint_chunk` takes a
resolved generation, the chunk's byte offset, the chunk the caller planned
from and the new placement, and hands back an uncommitted compare-and-swap
batch that moves the placement in whichever record holds the chunk: the
inode (flat map, version advanced as commit_chunk_map does, metadata kept)
or the one segment record that covers the offset (segmented map, root left
byte-identical). The caller adds its own evidence and commits once.

The batch pins the root's bytes, the segment row's freshly read bytes, and
the planned chunk itself. A concurrent edit to a sibling chunk still merges;
an edit to the planned chunk, or a superseded root, makes the batch fail
with nothing written. The rewritten record is weighed against the full
MAX_VALUE_BYTES ceiling before anything is written, a live segment row
already over that ceiling is reported as corruption rather than rewritten,
and a replacement placement of the wrong length is refused as a caller
error.

Nothing calls the primitive yet; custodian behaviour is unchanged. Wiring it
into repair, the architecture-doc update and Tier-0 DST coverage follow in
#777.
