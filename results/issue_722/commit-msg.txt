custodian: let a drain move fragments held in segment records

Draining a D server that holds a fragment of a segmented object never
finished. Since 382909721e072124efb7c0704c7ea74ea37a16e6 the rebalance pass
no longer aborts on such an object, but it refused the move and wrote
nothing, on every pass. The drain was never certified, so the operator could
never retire the server.

The pass now moves the fragment through the shared placement primitive
added in 842f48ea49a235939336041e465277c3ad57c7b5, the same way the repair
pass does. It rewrites whichever record holds the chunk (the flat inode
record or a seg: record) and puts the orphan marks for the vacated
positions in the same commit. The size-ceiling check now lives only in the
primitive. Each move pins the root generation the resolve answered from.

Objects are still planned per object and per chunk, so when two objects
share a chunk, both are repointed and neither keeps naming the drained
server. Corrupt maps (chunk lengths that overflow the object's byte range,
a segmented root under a non-canonical key) are contained and named once
per object instead of retried as conflicts. The refused-segmented audit
line and the rebalance_refused_records counter go away with the refusal.

A move that loses its compare-and-swap still leaves the copied fragment in
place, unreferenced. The flat path already does this; it is tracked in
#723 and not changed here.

Fixes #722
