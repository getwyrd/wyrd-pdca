# Adversarial review — issue 1084 (committed-move destination pre-mark)

I tried to refute the fix: the red→green evidence, the pre-mark / gate / adoption design in `premark.rs`, and the fixtures around it. ## Findings

- NEEDS-HUMAN [impl] — **The old committed-repair suites stay green only because their store doubles ignore the write deadline.** `crates/custodian/tests/reconstruction.rs:372`, and the 14 other context literals in that file, still pass `staged_write_window_millis: 0`. After this patch that field sets every committed repair's deadline (`crates/custodian/src/premark.rs:447-448`, `crates/custodian/src/reconstruction.rs:1275-1281`). So each repair these tests drive is sent with `deadline == pre-mark stamp`. A real D server refuses that write: `FsChunkStore` calls `WriteDeadlineExpired::if_elapsed` (`crates/chunkstore-fs/src/lib.rs:286-288`), which refuses when `now >= deadline` (`crates/traits/src/lib.rs:925-926`). The tests pass only because `MemDServer::put_fragment` drops `_deadline_millis` (`crates/custodian/tests/reconstruction.rs:124`). **Reproduced** on a scratch copy of the patched tree. I made that double call `if_elapsed(id, d, 600)`, matching the fixed `ManualClock` of 500/600 the contexts use. Result: 11 of 15 tests go red, every one with `left: Satisfied, right: Changed` (for example `kills_a_d_server_and_reconstructs_to_full_redundancy_through_reconcile_step`, assertion at `reconstruction.rs:382`). Then I set the window to `W_WRITE_MILLIS` with the same enforcing double, and all 15 pass. Other fixtures have the same shape: `segmented_map_repoint.rs:171`/`:445`, `segmented_map_reconstruction.rs:141`/`:422`, `staged_protection.rs:411`/`:542`, and `crates/server/tests/custodian_day_one.rs:147`/`:628`, which also uses fixed `|| 500` loop clocks at `:1190`, `:1250` and `:1360`. The patch already fixed this for `placement_ceiling.rs` (an `FsChunkStore` on a `ManualClock`), `closed_write_path.rs` (wall clock) and the DST fixtures (iteration-2 item 4). These remaining suites are what's left. Right now they would not catch a regression in the deadline, and they model a configuration production never runs. Fix: give these literals `W_WRITE_MILLIS` and have their doubles judge the deadline on the context clock (rubric, *Test fidelity*).

- NEEDS-HUMAN [impl] — **A reproduction for T4's `reconstruction.rs:1284` blocker: a deadline-refused repair returns `Satisfied`.** The red run above is direct evidence. When a pass's only committed repair is refused at its deadline, the pass returns `Reconciled::Satisfied` while the fragment is still missing. All `RepairOutcome::Aborted` results go to `emit_aborted(.., "unplaced")` (`reconstruction.rs:469`), and an aborted repair is not a hole, so the pass answers `Satisfied` (`reconstruction.rs:516-531`). On the base, `Aborted` could only happen when the chosen target was outside the fleet view. This patch adds three routine, transient causes to the same arm: `pre-mark-stale`, `write-deadline-expired` and `write-unverified` (`reconstruction.rs:1275-1285`). All three are also counted under the wrong reason, "unplaced". The obligation does stay queued, so nothing is lost. But an operator reading `Satisfied` is told redundancy is restored (the comment at `:518-523` says exactly that). This is the same class T4 raised, not a new one. My contribution is the concrete repro: 11 tests, a refused write, and `Satisfied`.

- NEEDS-HUMAN [impl] — **The patch makes the GC write-ordering comments false.** `crates/custodian/src/gc.rs:255-263` says "the staged re-place is the one such writer on `main`" (a writer that marks before it writes) and that "reconstruction and rebalance write first, and mark only the positions they vacate … So the sweep is sound against today's tree." After this patch both committed movers pre-mark before they write. The sweep is still sound, but only because their pre-mark is a *structured* mark (`premark.rs:403`), which the sweep keeps (`event-may-await-write`, `gc.rs:925-928`). That dependency is now unstated. Separately, `gc.rs:862-865` argues that the drain-mark sweep is safe because "a fragment lands at a committed record's position before that record commits". An in-place repair (`premark.rs:417-422`) breaks that premise: it writes to a position the committed record already names, after the record committed. I checked the bound by hand and it still holds. The in-place write's deadline is `t_premark + W_write`, and a drain mark there can only be stamped after a supersede that beat the pre-mark's root pin. So `t_drain + D` is later than the write's deadline, and an accepted write cannot outlive its drain mark. This is drift in comments that state the rules, not a bug. Changing GC behaviour is child-1's job, but the comment's claim about reconstruction and rebalance is this diff's to correct. Otherwise whoever settles #825 (adding pre-mark events to the swept set) will be reading a wrong premise. The audit text at `reconstruction.rs:1577` ("every fragment it wrote stays under its pre-mark") has the same problem: it is false for in-place destinations.

## Refutation attempts that failed
