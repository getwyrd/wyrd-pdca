custodian: mark a repair or evacuation's destination before writing

When the custodian repaired a lost fragment, or moved one off a draining
server, it wrote the new copy and then updated the chunk's placement,
marking only the position it left. It never looked at the mark already
sitting at the position it wrote to. That left four ways to lose or leak
bytes:

- A fragment moved back onto a server it left recently stayed
  referenced under that server's old reclaim mark. Once the object was
  superseded, GC could delete it on the old stamp before the new
  reclaim mark was written.
- A destination already carrying an expired mark could have the fresh
  copy reclaimed by GC before the move committed, and the move then
  published a placement over missing bytes.
- A move that lost its commit left its written copy unreferenced and
  unmarked, which GC keeps for ever.
- Destination writes carried no deadline, so a slow write could land
  after GC had already reclaimed the evidence that covered it.

Both committed movers now follow the rule the staged re-place already
keeps (proposal 0016, X47 and the write gate). A shared module commits a
pre-mark at each destination before any write, carrying a per-move
nonce. Writes go out only while that pre-mark is younger than the
re-point window, each with a deadline the storage server enforces. The
commit that adopts the new placement requires and deletes the pre-mark,
and re-marks the vacated position under a precondition on what it read
there. A destination whose mark is being reclaimed, or cannot be read,
is never written; the move picks another position or stops.

A fragment rebuilt in place, on the server the placement already names,
gets no pre-mark: any stale mark there is deleted before the write. One
narrow race there is deferred to #1100 (bytes kept, never lost).

A repair that is refused, blocked for capacity, or loses its race now
leaves the pass non-certifying (Blocked) and keeps the obligation
queued, instead of reporting Satisfied while the fragment is still
missing. RebalanceContext gains clock and write_window_millis fields,
matching ReconstructionContext.
