gateway-s3: refuse object keys over S3's 1,024-byte limit on PUT

The S3 gateway stored an object under a key of any length. S3 allows at
most 1,024 bytes of UTF-8 per key, so a client could create objects that
real S3 would refuse, and that other S3 tools may not be able to handle.

An object PUT whose decoded key is longer than 1,024 bytes now answers
400 KeyTooLongError before any body byte is read. The limit counts UTF-8
bytes of the percent-decoded key alone: not characters, not the encoded
wire form, not the stored "bucket/key" name. It holds for every payload
form: a single-shot signed body, an aws-chunked stream (the AWS SDK
default) and UNSIGNED-PAYLOAD.

A PUT whose decoded bucket segment contains "/" is now refused 400
InvalidBucketName. Without that, "PUT /b%2Fa/<1,023 bytes>" stored the
same object as "/b/a/<1,023 bytes>" and moved two bytes of the key past
the length check. S3 bucket names cannot contain "/" anyway.

Only creation is limited. GET, HEAD, single-object DELETE and bulk
DeleteObjects take any key they took before, so an over-limit object
stored earlier, or written by "wyrd put --key", stays removable. Bulk
delete in particular gets no per-key bound: a key longer than the
65,534-byte request-target limit cannot be named in a DELETE URL (hyper
answers 414), so bulk delete is its only way out. Such a key is bounded
only by the existing 8 MiB DeleteObjects body cap, whose doc comment now
says so. A key too large for that cap can only be written through the
in-process Gateway::put_object; it had no S3 way out before this change
and still has none.

The architecture doc records where the limit applies and why bulk delete
is left open.
