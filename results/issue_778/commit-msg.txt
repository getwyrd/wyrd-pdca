server: bake the build identity into wyrd and log it at s3 startup

A running wyrd binary could not say which checkout it was built from. The
operator tarball has a VERSION file, but the binary inside it knew nothing,
and the image build that compiles it cannot see .git, so there was no way to
check that a deployed gateway is the build you think it is.

The binary now carries a build identity, and every `wyrd s3` process records
it as the `version` field of its `role started` log event. The identity is
resolved in this order:

1. WYRD_VERSION from the build environment, used as-is after validation.
   `cargo xtask dist` passes the exact string it writes to the tarball's
   VERSION into the image build (and the --host build), so a released binary
   and its tarball carry the same version, `.dirty` suffix included.
2. Otherwise `git describe --tags --always` of the workspace's own
   repository, without --dirty: a hand-built binary names the commit it was
   built from, and makes no claim about uncommitted edits.
3. Otherwise 0.0.0+git.unknown, with a build warning.

The describe normalizer and the validator live in one file,
crates/server/src/version/derivation.rs, compiled by both the server's build
script and xtask, so dist and the binary cannot drift apart. A value that
would not be a legal Docker tag, or is not UTF-8, fails the build instead of
silently turning into a different identity. The build script re-runs only
when HEAD, the refs or the shallow boundary change, never on an edit or a
`git status`, so the normal edit-test loop does not relink.

The identity is exposed as wyrd_server::version::BUILD_IDENTITY for a
follow-up that puts it on the S3 wire.

Fixes #778
