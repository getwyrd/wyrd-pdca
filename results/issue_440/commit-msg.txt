server: let operators select the FoundationDB metadata backend

The FoundationDB metadata backend shipped in
22d39b6035573d9b999a95430e62ae68a859bd29, but nothing could reach it: `wyrd
--metadata-backend fdb` was rejected as an unknown value, so the only way to
run the backend was to not run it. Operators had a driver they could not turn
on.

`fdb` is now a selectable metadata backend everywhere `redb` and `tikv` are,
behind a new OFF-by-default `fdb` feature on `wyrd-server`. A default build is
unchanged: it compiles no FoundationDB code, links no `libfdb_c`, and now
rejects `fdb` with the same actionable hint TiKV gives — naming the build flag
that enables it, instead of pretending the backend does not exist. The usage
text lists all three backends.

Selecting a backend stays "pass a different concrete behind the unchanged
`MetadataStore` seam". No consumer changed: the new arms sit only at the
composition root, alongside the existing TiKV arms. The `fdb` arm calls the
driver's own `connect()` rather than pre-checking `WYRD_FDB_CLUSTER_FILE`; the
driver deliberately falls back to `/etc/foundationdb/fdb.cluster` when that
variable is unset, so a pre-check would break a stock FoundationDB install. The
variable is surfaced as error context when the connect fails.

Fixes #440
