# Adversarial review — #772 (multipart owned staging entry)

I had a working toolchain. I re-ran `cargo test -p wyrd-core --test multipart_owned_staging`
(14/14 green) and the new custodian GC leg (green). Then I applied the brief's negations by hand
in a scratch copy and ran each against the tests.

## Findings

- NEEDS-HUMAN [impl] — The GC half of S5 doesn't prove "the sweep completes for every other entry" (`crates/custodian/tests/gc.rs:926`). Negation: change `continue;` to `break;` in the skip arm at `crates/custodian/src/gc.rs:506`, so the scan stops at the first unreadable entry. The test still **passed 16 of 40 runs**. Control run: the unmodified test passed 40/40 alone and 20/20 alongside its siblings. The mutant is caught only when the `HashMap`-backed `MemMeta` (`crates/custodian/tests/gc.rs:56`) happens to yield `pending:226` (the misfiled entry, `:948`) before `pending:225` (the ordinary lease, `:934`). A failing run shows why: `left: Satisfied, right: Changed` at `:982`. On any key-ordered store (redb, FDB, TiKV), 225 always comes first, so the mutant would pass every time. The `scan` contract leaves order unspecified (`crates/traits/src/lib.rs:1352-1355`), so the fix needs a witness that doesn't depend on order. For example: give this leg a key-ordered store and add a second ordinary expired lease whose key sorts after the misfiled one, then assert it was reclaimed. The core half doesn't have this gap: `crates/core/tests/multipart_owned_staging.rs:560` runs on ordered redb and asserts the full skipped-key list, which catches `break`. C5's pass (`gate-logs/C5-mutants.log`: 9 caught, 29 unviable) doesn't cover this, because cargo-mutants never generates a `continue`→`break` mutant.

- NEEDS-HUMAN [human] — T4 is a gating check and it is still red, with two blockers (`gate-logs/T4-batch-review.log`): no seeded Tier-0 DST (deterministic simulation test) coverage for the changed sweep at `crates/core/src/write.rs:654` or the GC skip at `crates/custodian/src/gc.rs:502`. The finding is accurate. Before the patch, one unreadable `pending:` value aborted the whole pass. Now both sweeps keep going and delete other entries, and the rubric's *Test fidelity* rule asks for seeded DST coverage of that kind of change. The brief rules it out, though: `crates/dst/tests/custodian.rs` may only get the mechanical initializer, and a 14th file means STOP. The existing DST leg (`crates/dst/tests/custodian.rs:883`) seeds only ordinary leases. A rebuild can't clear this without breaking the brief. A human has to choose: record a rejection reason (the rubric's "Definition of done"), or widen scope, e.g. a follow-up issue for a seeded leg with misfiled, torn and garbage `pending:` values.

- NEEDS-HUMAN [human] — The brief's S8 negation can't work as written. "Remove ONE `skip_serializing_if` … on the owned witness" has no effect on an owned value, because both fields are `Some`. I removed the attribute from `owner` (`crates/core/src/metadata.rs:1601`): S7 (`crates/core/tests/multipart_owned_staging.rs:638`) failed and S8 (`:662`) **passed**. What S8 actually guards is the `sidx:` canonical-bytes check: dropping `require_canonical` at `crates/core/src/multipart.rs:3627` fails S8 and only S8. So the eight-negation evidence holds with that swap. But `build-notes.md` (withheld from me) should record the canonical-gate negation for S8. If it says the briefed negation failed S8, that claim is wrong.

- NEEDS-HUMAN [impl] — The docs overstate the operator signal. `docs/design/architecture/05-building-block-view.md:202` says "the two `pending:` expiry sweeps skip it … and name it for an operator", and the module header `crates/core/src/multipart.rs:103-104` says the same. In a default deployment, GC's expired-lease input runs under `ExpiredPendingPolicy::Defer` unless `--gc-expired-pending` is passed (`crates/server/src/cli.rs:975-979`, `crates/custodian/src/gc.rs:172-175`), so GC never reads `pending:` there. `write::sweep_expired_leases` has no production caller, only tests. So by default nothing names a misfiled entry to an operator. The only visible effect is a boxed error from `renew_pending` / `live_lease_guards` on a write that touches that chunk. Fix: qualify the clause (e.g. "when GC's expired-lease input is armed"), keeping S10's length limit.

- Out of scope here, a note for #656–#659: `OwnedEntry`'s doc (`crates/core/src/multipart.rs:3503`) calls the checked path "public end to end", but the **key** isn't part of that path. An outside writer can store `OwnedEntry::new(a1, ..).to_pending()` under `sidx_key(&b2, ..)`. Every call there is public and type-checks, and `decode_owned_entry` then refuses those bytes forever (`OwnedEntryOwnerMismatch`). That's the same "bytes nothing can read back" problem S9 was about. But S9 only required the owner/staged pairing, and `sidx:` writers are out of scope for this child, so this belongs with the first `sidx:` writer rather than being a defect in this diff.

## What I tried to refute and couldn't

- **The negations isolate.** Against `multipart_owned_staging`, each of these failed exactly one test:
  - S1: drop the `supported(k, m)` check.
  - S2: drop the key/owner comparison.
  - S3: make the pairing check always `Ok`.
  - S4, three separate runs: put `renew_pending`, `live_lease_guards` and the core sweep reader each back on the generic `decode`.
  - S5: make the sweep `?`-abort; separately, make it skip silently and return `Ok`.
  - S6, inverted: reject a length-mismatched placement.

  On the GC side, going back to the generic decode fails the custodian leg ("GC reclaimed bytes…"), and so does a `?`-abort ("must not fail the pass").
- **No `pending:` reader was missed.** No other production code decodes a `pending:` value. A grep over `crates/*/src` finds only the four readers, plus `crates/custodian/src/restore.rs:731`, which reads keys only and treats the entry as an in-flight write. That fails safe.
- **Edge inputs.** A value with one field spelled `null` is refused as torn. One with both fields `null` reads as an ordinary lease, which is harmless and matches the old open wire format. `UploadId` validates on decode (`crates/core/src/multipart.rs:780-784`). Unknown fields inside `staged` are refused, because `StagedPlacementWire` is closed. A misfiled owned entry is refused before `renew_pending` writes anything, so its ownership fields can't be erased. GC's skip keeps the chunk out of `expired_pending`, so no path deletes its fragments or its `pending:` key (`crates/custodian/src/gc.rs:204-229`).
