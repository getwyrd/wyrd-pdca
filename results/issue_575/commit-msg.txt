Emit S3 request RED and d-server admission/capacity metrics

A live deployment could watch its storage health (the custodian's
durability plane) but not its service health: nothing reported a failing
or slow S3 request, and a d-server driven past its admission bound shed
load silently — visible only as a client-side RESOURCE_EXHAUSTED, which
is to say visible only to whoever kept the client's logs.

The S3 gateway now records a per-op latency histogram and an error
counter keyed by op and by the typed failure class. The class is
consumed from the shared wyrd_traits::classify seam, never re-derived
locally, and both the latency sample and the error verdict are taken
when the transfer actually ends rather than when the response head is
built. That timing is what makes the class truthful on streaming reads:
a GET whose 200 head is already out when the fleet dies mid-body is
counted under the class of the error that actually ended the transfer,
so a transient mid-stream fault reads "transient" (retry and it may
pass) instead of the head-time "terminal" default (retrying cannot
help) — the exact distinction the counter exists to carry, on exactly
the long transfers a real fleet fails on.

The d-server emits admission events — admitted, shed, timed out,
cancelled — and an in-flight request gauge that rises while requests are
held and returns to zero when they finish. The observers are positioned
around the existing admission stack; nothing about what is admitted or
shed changes.

The s3 and d-server role entries gain the metrics provider they were
missing (previously only the custodian role built one), with the export
surface selected the same way: Prometheus always, plus OTLP push when
--otlp-endpoint names a collector. Error and capacity series are
pre-registered at zero, so a dashboard can tell "no errors" from
"no metric".

Depends on the typed ErrorClass/classify seam introduced for #577.
