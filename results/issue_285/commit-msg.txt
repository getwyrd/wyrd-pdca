Reject invalid stored EC schemes at read time instead of panicking

A read of an object whose stored erasure-coding scheme was corrupted or
tampered — for example an inode recording zero data shards — crashed the
process instead of failing the read. The parameters read back from inode
metadata were trusted verbatim: a zero data-shard count slipped past the
"too few shards" guard and reconstruction then indexed an empty shard
list, panicking. A scheme with zero parity shards was worse still — one
no valid write could ever have produced — yet with all data shards
present it returned bytes as if nothing were wrong.

Stored scheme parameters are now validated at the read and reconstruct
boundaries before they drive any shard fetch or indexing, using the same
support check the erasure coder itself applies. Any scheme the coder
could not have encoded is refused as a typed read error, so a corrupt or
tampered record surfaces as a clean failure rather than a crash or a
silently wrong result. The command-line parser already rejected these
schemes on input; this closes the matching gap on the untrusted values
read back from metadata.
