deploy: add the small multi-node production bring-up stack

Operators standing up the single-zone "Small multi-node Production"
tier had no recipe to follow: the only thing under deploy/ was the
throwaway single-node TiKV pair used by the conformance suite, so there
was nothing that composed the production topology end to end.

This adds deploy/small-multi-node/ — a docker-compose stack that brings
up the profile's four component roles: a 3-node PD ensemble, one
TiKV-small store, a separate 3-node etcd ensemble for L5 Coordination,
and local-disk D servers. Because it has multiple replicas of the same
role, it uses the default bridge network with per-service DNS names and
distinct published host ports rather than the single-node stack's host
networking. The D servers reuse the existing wyrd-dserver:local image
and the `wyrd d-server` role, so this is a fresh stack, not an edit to
the repo-root dev docker-compose.yml. A `cargo xtask deploy-small-multi-node`
runner brings the stack up, waits for the external components to accept
connections, and tears it down — docker-gated exactly like
tikv-conformance, so a Docker-less machine is never blocked and it is
not part of `cargo xtask ci`.

Deployment keeps its substrate pluggable: this stack lives outside the
Cargo workspace, and a new `cargo xtask ci` guard (deploy-guard) fails
the build if any workspace crate imports a Kubernetes/orchestrator
client API, so orchestrator coupling can no longer sneak into a
component. The stack stands up on static endpoints today; live peer
discovery through L5 is gated on the etcd-backed Coordination backend
and the runnable gateway/custodian process roles, which land
separately.
