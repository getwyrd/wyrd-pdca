feat(gateway): serve S3 PUT/GET/DELETE over an HTTP endpoint

Until now the gateway could only be driven in-process: PUT and GET were
Rust methods on the gateway type and the CLI spoke to them as a library,
so nothing could store or fetch an object over the network. A deployment
had no client-facing door, and the day-one "PUT an object, GET it back
byte-identical" round-trip could not run over the wire.

This adds an S3-compatible HTTP listener in the gateway role. It serves
bucket-scoped object PUT, GET, and DELETE, authenticates every request
with AWS SigV4 — an unsigned or wrong-signature request is refused, there
is no anonymous access — and streams request and response bodies so a
large object is never buffered whole in the gateway's heap. A signed
PUT -> GET -> DELETE round-trips byte-identical, verified against a real
aws-sdk-s3 client whose own signer and framer, not the gateway's, drive
the listener.

The wire layer lives in its own crate over a neutral object-gateway seam,
so it stays out of the server's composition root and future gateways can
reuse the seam; concretes are still wired only at the composition root.
DELETE and overwrite leave the superseded fragments under a durable
orphan grace record for the custodian to reclaim once its reader-safe
window elapses, so a concurrent read is never torn mid-stream and a crash
never strands bytes; startup recovery resumes the id allocators above
every id still live on disk, including those the orphan ledger still
holds, so a restart cannot re-mint a chunk id whose bytes are still
present.

At review the listener is exercised over plaintext loopback. Serving
public S3 over TLS on a deployed host depends on the first-deployment
work and is out of scope here.
