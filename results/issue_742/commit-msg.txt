dist: ship wyrd-validate in the image and operator tarball

Operators are meant to run wyrd-validate against their own deployment to
check that their hardware and configuration are sound. Until now it could
not reach them: the image built only wyrd, cargo xtask dist extracted only
that one binary, and install.sh installed and removed only bin/wyrd.

The production image now builds and carries both binaries, and dist
extracts both into the tarball under bin/. install.sh installs and
uninstalls both. The validator gets no systemd unit, no config file and no
entry in ROLES: it is run by hand, not supervised. ENTRYPOINT stays wyrd,
so nothing about how the image is run changes. The --host build path builds
both binaries too, so a host-built tarball has the same contents as an
image-built one. The README describes the validator beside the roles
binary, including that it needs no libfdb_c.

The shipped set is now one table in xtask::dist (shipped_binaries), and
the extraction, the --host build and the staging step all read it. The
Dockerfile, installer, release smoke step and README cannot read Rust, so
each keeps its own spelling of the binary names, and a new container-free
test pins every one of them to the table. Adding a third binary without
updating one of those files fails cargo xtask ci and names the file.

The release smoke step and the fdb-image workflow now also run the
validator, before the FoundationDB client is installed, and check it is
gone after uninstall. Those two workflows are where a real image build and
a real install are exercised; nothing in cargo xtask ci can build one.

Fixes #742
