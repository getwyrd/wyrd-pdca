scrub: repair a placed fragment that is missing, not just corrupt

Scrub is the background pass that protects committed data from silent
loss: for every fragment a committed chunk map references, it is meant to
guarantee the fragment is either present and intact or scheduled for
rebuild. Until now that guarantee had a hole. Scrub only ever looked at
the fragments each storage server actually reported holding, so it could
catch a fragment that was present but corrupt — yet a fragment that had
gone entirely missing from its server was never even looked at, and the
chunk was left silently under-durable with no rebuild ever queued. A
later disk loss could then turn recoverable data into permanent loss.

Scrub now drives its pass off the committed reference set itself,
grouped by the server each fragment is placed on, and asks that server
for exactly the fragments the chunk map says it holds. A fragment that
comes back absent is treated as the same durable loss as a corrupt one:
the chunk is enqueued on the shared repair queue for reconstruction.

The reference set is the same one garbage collection uses as its safety
gate, so the new detection cannot fire on fragments that are legitimately
not-yet-present: an in-flight write's provisional placement and an
orphan/unreferenced fragment are both excluded, and a transient fetch
error still propagates to the retry policy rather than being mistaken for
a loss.
