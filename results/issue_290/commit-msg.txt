Fix panic reading a corrupt inode with an oversized size

Reading a committed inode whose recorded size is corrupt or tampered — for
example a huge value like u64::MAX with an empty or short chunk map — could
crash the read with a capacity-overflow panic, or attempt an allocation
proportional to that untrusted size (up to an out-of-memory abort), instead of
returning a clean read error.

The read path preallocated its output buffer from the inode's recorded size
before checking whether the chunk map could actually back that many bytes. That
recorded size is untrusted metadata decoded straight from stored JSON, so it
must not size an allocation ahead of validation. The buffer now grows only from
bytes each chunk read has already fetched and checksum-verified, and the
existing size check then surfaces the discrepancy as a typed error. A corrupt
oversized inode reads through to that check and fails cleanly — no panic, and
no allocation that scales with the untrusted size.
