custodian: record GC's reclaim intent before deleting a fragment

GC used to delete a fragment's bytes before it recorded that decision
anywhere, and could read an orphan-ledger mark only as a bare decimal
timestamp. Two problems followed. A mover could commit an adoption
compare-and-swap against a pre-mark's original bytes after GC had
already destroyed the fragment those bytes described, landing a
placement that names deleted bytes. And any mark written in one of
proposal 0016's newer JSON shapes (an unreference event, or GC's own
"reclaiming" decision) was unreadable, so its fragment was kept
forever and its mark reported as damaged.

This adds one shared codec for the three `orphan:` mark shapes
(legacy bare decimal, structured with an event, and reclaiming) in
crates/core/src/metadata.rs, and changes GC's sweep in
crates/custodian/src/gc.rs to commit an exact-value swap of a mark to
"reclaiming" before it deletes any fragment bytes, batched at most
CLEANUP_BATCH marks per commit. A mark that changed underneath the
swap keeps its fragment instead of being reclaimed on stale evidence.
A mark whose event names a retirement obligation that is still
draining is left alone until that obligation is gone. A mark already
"reclaiming" from an earlier, unfinished pass is resumed with no
second grace test. Restore's own handling of marks is unchanged.

Fixes #804
