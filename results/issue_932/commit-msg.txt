core: stage a multipart part's bytes safely before its commit

Multipart sessions can be created and aborted, but nothing could yet store
a part's bytes. This adds the staging half of UploadPart as wyrd-core
functions, reserve_slot and stage_part, with no production caller yet. The
S3 verb arrives later, once the commit, Complete and the reaper exist.

Staging is built so that no part's bytes can become untracked garbage:

- It claims one in-flight slot per attempt. An ambiguous reserve retries
  only the index it may already hold, so one attempt never ends up holding
  two slots, and a full range answers SlowDown, never NoSuchUpload.
- Each chunk is registered as an owned sidx: entry before any of its
  fragments is written. That batch fails once the session has left Open or
  a chosen D server has a drain recorded. Placement skips draining servers,
  and a drain that lands mid-stage makes the chunk re-plan, not fail.
- Every fragment write carries a deadline fixed at authorization time, and
  staging waits no longer than that. A write whose effect is unknown is
  never counted as written, and never reported as "nothing landed".
- Every body read is bounded by a caller-supplied idle limit, and only a
  non-empty piece counts as progress.
- Unknown commit outcomes are settled by re-reading exact bytes, never
  guessed, and every retry loop has a fixed bound.

The drain key desired:dserver:<id> now has one home in core, which the
custodian reuses with unchanged bytes. Proposal 0016's reserve rule is
corrected to match: after an ambiguous reserve, never probe onward. Leases
are written but not renewed during staging; in-flight renewal follows in a
separate change.
