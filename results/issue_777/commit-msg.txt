custodian: repair chunks in segmented objects instead of refusing

An object published by multipart upload stores its chunk map in segment
(`seg:`) records. When one of its fragments was lost, the reconstruction
pass refused the repair every pass: nothing was rebuilt, the obligation
stayed queued, and the object's redundancy kept decaying with no way out.
#697 stopped that case from aborting the whole pass, but deliberately wrote
nothing, because there was no safe way to move a placement inside a segment
record. Commit 842f48ea49a235939336041e465277c3ad57c7b5 (#776) added that
move, `metadata::repoint_chunk`, but nothing called it.

The repair now goes through `repoint_chunk` for flat and segmented objects
alike. The custodian adds the obligation's delete and the orphan marks for
the displaced fragments to the batch the move hands back, so the placement
change, the drain and the orphan evidence still commit as one atomic,
version-conditional write. The segmented root is never rewritten.

Under concurrency the move merges a racing edit to a sibling chunk in the
same segment record, and loses (counted as a conflict, obligation kept for
the next pass) if the planned chunk itself or the root generation changed
under it. A record the move cannot rewrite is contained per object and the
pass does not certify; a record past the value ceiling is refused before
any fragment is written. When the resolver restarts onto a newer root, the
move pins the root it actually answered from.

The old refusal path and its audit event are removed. The existing #697
test that asserted the refusal now asserts that the repair lands. The
runtime view (section 6.3) and crosscutting concepts (section 8.7) describe
the write side.

Fixes #777
