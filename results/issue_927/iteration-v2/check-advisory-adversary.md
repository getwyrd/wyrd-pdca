## Implementation findings (route back to Do)

- NEEDS-HUMAN [impl] — `crates/core/src/multipart/commit.rs:857` (with the `Same` arm at `:939`): a damaged `part:` record seen on the re-read is treated as a same-number rival, and is never decoded. Case: a commit answers `Conflict` with `b"not a part record"` at the part key. Result: `Ok(Refused(OperationAborted))`, one compensation sent, slot released. A held commit takes the same path. The brief's table says a damaged record gets `Stop::Record` and no compensation, and ADR-0045 says structural damage surfaces as an error. `g_a_slot_lost_or_a_damaged_record_at_a_re_read_stops_without_a_release` (test file:3150) damages the slot and session at the re-read, and the prior only at the first read, so it misses this. Fix: decode `part_now` when it differs from `required`, return a decode failure through `torn`, and add this leg.
- NEEDS-HUMAN [impl] — `commit.rs:788`: no test can fail if `can_recur` is wrong, and it guards the rule "an empty prior's bytes can come back". With `can_recur` forced to `false`, all 34 tests still pass. The existing leg (test file:1975) uses an empty rival with identical bytes, so `part_now != required` is never true there. A test that fails under the edit: an empty prior; the commit is held; a **non-empty** rival lands; when a compensation is sent, an empty rival in the same millisecond restores the prior's bytes, the held commit lands, and the compensation answers unknown. The patch returns the in-doubt error with no compensation. Under the edit it answers `Refused(OperationAborted)` for a commit that landed, which is the exact defect the brief set out to rule out.
- NEEDS-HUMAN [impl] — `commit.rs:620`: nothing tests that the ceiling leaves out the part's own prior. With that exclusion disabled, all 34 tests pass. A test that fails under the edit: `psum:` planted at `MAX_STAGED_CHUNKS - 1`, a committed one-chunk part 1, then a one-chunk re-upload of part 1. The patch answers `Committed`. The edit answers `EntityTooLarge { chunks: 80897, limit: 80896 }`.
- NEEDS-HUMAN [impl] — `commit.rs:646-648`: nothing tests the commit's `require_absent` on its obligation key, which the brief requires. With it removed, all 34 tests pass. A test that fails under the edit: plant other bytes at the key, then re-upload over a non-empty prior. The patch keeps those bytes and the prior, and ends in `ObligationKeyTaken`. The edit overwrites both and answers `Committed`.
- NEEDS-HUMAN [impl] — `commit.rs:523-527`: nothing tests that the doubt report keeps the batch that may still land. Replacing the search with `.last()` passes all 34 tests. A test that fails under the edit: round 1 held, round 2 `Unknown { may_still_commit: false }`, then the next read faults. The patch reports `may_still_commit: true`. ## Decisions for a human

- NEEDS-HUMAN [human] — `commit.rs:736` and `:950`, `crates/core/src/multipart.rs:4936`: a Complete fence that does not last can fill a live session's slots. An attempt that sees a non-`Open` session leaves its slot for the reaper, as `0016:1602-1606` and the brief's table say. If the fence then rolls back, the session is `Open` and the reaper will not walk it (`0016:1609-1612`). Probe: 16 staged attempts commit during the fence and all answer `NoSuchUpload`; the session returns at `Open@E+2` with all 16 slots held, no compensation sent, and the next upload answers `SlowDown(InflightParts)`. My probe used `Aborting` bytes in place of `Completing`, because `upload_part_answer` treats the two the same, and it restored the session by hand. The cost is availability, which `0016:2809-2813` allows, but it is the outcome (G) exists to prevent, and clients are told `NoSuchUpload` about a session that comes back. Decide whether to accept this until `W_session` or to take it up in 0016.
- NEEDS-HUMAN [human] — `crates/core/src/multipart/stage.rs:1817-1823`: the brief's rollback rule is wider than what the code and test do. (B) says a rollback "between the last intent and the commit" compensates and is "never `Committed`". A rollback before the quiesce renewal is adopted by that renewal instead. Probe result: `Committed`, part `session_epoch` 2, no compensation. The test comment narrows the window to "between the last renewal and the commit" (test file:1692-1702). This looks safe to me, since the attempt commits under the live epoch. Confirm it and correct the brief's wording, or decide the code should compensate.
- NEEDS-HUMAN [human] — `check-gates.json:3` and `:34`: `overall` says `pass`, but the gating `C4-ci` row is `unverifiable` because it hit its 7200 s limit. fmt, clippy, build and the new test file passed inside that run (`gate-logs/C4-ci.log`). `cargo test` then stalled in `custodian_gc`, so later test binaries and machete, deny and conformance never ran.
