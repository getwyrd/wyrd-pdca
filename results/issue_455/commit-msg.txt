custodian: scan placement each pass so lost data is repaired

The deployable custodian role (`wyrd custodian`) only drained the shared
repair queue on each pass — it never scanned the committed object
placement to find work of its own. A custodian brought up over a cluster
metadata store therefore computed zero repair obligations even when a
D-server had lost data, so under-replicated objects a gateway had written
were never detected or rebuilt. The durability loop's write half and
repair half were each proven in isolation but never actually joined, so a
freshly deployed custodian could report "nothing to repair" while data was
genuinely at risk.

Each reconstruction pass now scrubs the live fleet first, deriving repair
obligations directly from the placement the gateway recorded, then
reconstructs them in the same pass. A gateway-written object that loses a
fragment is now a custodian-visible repair obligation: the under-replicated
backlog rises, the custodian rebuilds the fragment, the backlog returns to
zero, and a later read reconstructs the object byte-for-byte.

This composes the existing scrub and reconstruction loops inside the server
role; the custodian library and the gateway write path are unchanged. It
builds on 99889ba89473501f1422d20e85d96360f9d34144, which proved the gateway
PUT/GET fan-out across D-servers.
