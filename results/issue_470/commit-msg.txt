Add a production FoundationDB container image for wyrd

Operators running Wyrd's FoundationDB metadata backend (ADR-0042) had no
image to deploy. The only Dockerfile that built the wyrd binary lived
under a crate's tests/ directory as a fixture; it could not build the fdb
feature at all and its runtime carried no libfdb_c or fdbcli, so there
was no supported way to run the production backend in a container.

This adds deploy/docker/wyrd/Dockerfile, a parameterized multi-stage
image that installs the pinned FoundationDB client (C headers, libfdb_c,
and fdbcli) in both the build and runtime stages, runs as a non-root
user, and records the baked client version in OCI labels. The
FoundationDB version is a single source of truth pinned in the Dockerfile
and mechanically checked to match the cluster the repo deploys and the
crate the binary links, so a silent client/cluster version drift fails a
test instead of failing in production. A CI workflow builds and
smoke-tests the image on pull requests that touch the FoundationDB
surface.

The image relies on the multi-version external-client support added in
f23848d8c9e30c44bbc38da56f1f2d2365d9e0d4: the baked external-client
directory is left empty in steady state so the linked client connects
normally, and a lockstep cluster upgrade becomes an image rebuild rather
than a code change.

Fixes #470
