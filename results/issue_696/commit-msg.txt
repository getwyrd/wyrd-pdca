custodian: contain per-object rebalance faults instead of aborting

Rebalance's evacuation scan read each committed object's chunk map
inline and propagated the first failure with `?`, so a single
multipart (segmented) object anywhere in the store, or a single
undecodable record, ended the whole pass. No fragment moved for any
other object either, so an operator could not decommission a drain
server while even one such object existed in the store.

Route both reads through `metadata::resolve_chunk_map`, the resolver
GC and restore already share, and contain a fault to the object that
owns it: an unreadable record is named on the audit seam and skipped,
the walk continues, and evacuation of every other (flat) chunk
proceeds unaffected. An evacuation this pass cannot yet perform
because the chunk's bytes live in a segmented record is refused
without writing anything; the refusal is logged once per object. A
store-level fault (as opposed to a fault of one object's map) still
ends the pass, since that is not one object's problem to contain.

The pass no longer reports a drain satisfied over a refusal or an
object it could not read: it now answers `Reconciled::Blocked` in
either case, `Reconciled::Changed` when other work converged, and
`Reconciled::Satisfied` only when nothing was withheld. A healthy
segmented object that holds nothing on the draining server does not,
by itself, cost the drain its certification.

Writing a segmented (`seg:`) chunk's evacuation is left to a follow-up
that builds that write path; this change only stops it from wrongly
blocking or silently discarding work on the rest of the store.

Fixes #696
