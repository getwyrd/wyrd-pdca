gc: sweep orphan marks whose position never gets a fragment

GC's ledger walk only ever visits an `orphan:` mark while it is looking
at a fragment that a D server currently lists. A mark whose position
holds no fragment is therefore never visited and never deleted. On
main this already happens in practice: repairing a missing fragment
marks the fragment's old position, which by definition holds nothing.
As more producers of such marks land, the orphan ledger grows without
bound, since nothing ever consumes them.

This adds a second phase to each GC pass: after the fragment walk, it
sweeps every mark in the pass's window whose position no listing from
this same pass reported. A mark is only swept once it is at least the
late-write deadline old (named `D`, and derived from a fragment write
deadline, a repoint pre-mark deadline, and a clock-skew budget, each a
named constant with its own derivation). That deadline guarantees the
listing was taken after the last instant a fragment could still land
under the mark, so the sweep is deleting on an observation, never on
the mark's age alone. A mark on a D server outside this pass's fleet,
at a protected position, holding a value of unknown shape, or younger
than the deadline is left alone. Deletes are conditioned on the exact
bytes read and go out in bounded batches, so a mark rewritten after
the pass read it survives, and a delete is only counted once its
commit is durable.

A compile-time assertion ties the new deadline to the deployed grace
window, so the two constants can never drift past each other without
failing the build. The runtime view doc is updated to describe the
new sweep step.

Fixes #800
