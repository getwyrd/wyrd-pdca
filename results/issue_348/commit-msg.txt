custodian: reject malformed placement in maintenance loops

When a committed chunk's placement record is truncated or corrupted —
non-empty but of the wrong length — the durability maintenance loops
previously ran it through the deliberately liberal fragment-expansion
helper, which invents identity placement for the missing entries. So a
corrupt record was silently treated as if it were a normal one: garbage
collection and scrub built their reference set over fabricated locations
(and could reclaim a real fragment the corruption had displaced), while
reconstruction and rebalance acted on — and rewrote the record over — an
invented placement. The corruption was masked as an ordinary resolution
instead of surfacing to an operator.

Each maintenance loop now classifies the committed placement before
expanding it, through a single shared classifier in wyrd-core. A
wrong-length vector is rejected rather than expanded:

  - GC and scrub fail safe — the chunk is treated as fully referenced,
    none of its fragments is ever reclaimed, and an audit signal is
    emitted on the durability seam;
  - reconstruction and rebalance skip the chunk and flag it for a human,
    never rewriting the corrupt record;
  - a drain or decommission that stalls on such a chunk now reports the
    blocking chunk ids in its status, instead of an unexplained pending.

The read path is unchanged: it still resolves the same chunk via the
per-index identity fallback, so object availability is preserved.

This builds on the shared placement helper introduced in
