  **(A) Payload determinism.** For a fixed set of `(seed, key, size, generation)` inputs, the
  SHA-256 of the generated bytes equals a **pinned hex constant** in the test (a known-answer
  test). Because the constants were produced by a different process (the one Do ran to compute
  them), this is the cross-process check resumability rests on: any input the generator takes from
  process state (a hasher seed, an address, a clock) breaks it.
  **(B) Every input matters, at sizes where it can.** For named non-empty vectors (sizes 4 KiB and
  100,003 B, the second not a multiple of any block size), changing any one of seed, key, size or
  generation changes the bytes; in particular two generations of one key **at the same size**
  differ (0017 §4: without the generation an overwrite re-sends identical bytes, so a stale read
  would look correct). This is **not** promised for every size: at 0 B every input gives the same
  (empty) bytes, and a 1-byte payload has only 256 values, so below one block two generations can
  coincide. The module docs state that limit, for the oracle slice (#746) to account for: at those
  sizes the bytes alone cannot tell a stale generation from the current one, and the ETag is no
  help, since the gateway derives it from the body (`crates/server/src/lib.rs:274-275`).
  **(C) Exact length and random access.** The generator yields exactly `size` bytes (including 0
  and 1); for several split points, the pieces concatenate to the whole; and the bytes of any range
  `[a, b)` produced directly equal the same range cut from the whole.
  **(C′) Bounded state, direct access.** Every piece the streaming generator yields is at most a
  documented bound (e.g. 64 KiB) whatever the total size. A 64-byte range ending at the last byte
  of the `10 GiB + 1` class, and one ending at the last byte of a 1 TiB payload, are each produced
  directly within 5 s of wall time (honest work is a few hash blocks; regenerating the prefix is
  minutes to hours, and materializing the object exhausts memory). Each equals a pinned hex
  constant, as in (A), and equals the concatenation of its two halves produced directly.
  **(D) Size classes come from the tuning.** At the default tuning the classes, ascending and
  without duplicates, are: 0 B, 1 B, 4 KiB, 64 KiB, `C−1`, `C`, `C+1`, 5 MiB, 8 MiB, `64×C`,

  segmentation threshold, each class labelled with the boundary it straddles. With a different
  `--chunk-size` the `C`-, `64×C`- and (derived) `T`-classes move and the fixed ones do not.

## Motivation

A months-long run cannot store what it wrote, and it cannot re-send the same bytes when it
overwrites a key, or a stale read passes as correct (for any payload big enough to differ; see
(B) for the tiny sizes where no generator can make two generations differ). And a size table copied from today's constants
goes stale the day a constant moves, after which the run reports coverage of a boundary it never
crossed. Both are fixed by deriving: bytes from inputs the run records, sizes from tuning the
operator passes (0017 §4, `0017:336-370`).

## Design

**Payload module** (`src/payload.rs` or similar, pure). Inputs: the seed (the `--seed` value's exact
UTF-8 bytes), the object key, the size, and a generation number. Output: a generator that yields
the bytes in bounded pieces and can produce any `[a, b)` range directly in work proportional to
`b − a`, holding state that does not grow with the size. Any keyed construction that meets
(A)–(C′) is acceptable; SHA-256 in counter mode over an unambiguous encoding of the inputs and the
block index is the obvious one, since block `i` is computed from `i` alone. Document the
construction in the module docs exactly enough that it can be reimplemented, because a change to it
silently invalidates every checkpoint ever written; the known-answer constants are what make such a
change visible. Also provide the streaming SHA-256 digest of a payload, which the oracle and
checkpoints will key on.

**Size module** (pure). A `Tuning { chunk_size, max_root_value_bytes, segment_threshold_bytes }`
resolved from the flags, and a function from it to the ordered, de-duplicated list of
`(size, labels)` in (D). Checked arithmetic throughout; a tuning that cannot produce a valid table
is refused, not clamped. The `10 GiB + 1` class stands for the > 10 GiB launch requirement
(`0016:220-227`); 0017's table names "beyond 5 GiB" without a value.

**Flags.** Optional, `--flag value` like the rest, parsed strictly, and resolved into the echo with
their source: `(given)`, `(default)` or `(derived)`. A default is a value the operator did not
choose, which the crate's docs currently forbid for its ten flags (`args.rs:15-18`); 0017 settles
that these three are different ("Defaults mirror today's values ... the verdict records what was
used", `0017:348-350`), so the echo saying where each came from is what keeps that honest. Update
the crate docs to state the distinction.

**Docs currency** (`AGENTS.md:154-157`, a CLI flag): extend the `validate` paragraph at
`docs/design/architecture/05-building-block-view.md:297`: the three optional tuning flags and their
defaults, and that payloads are derived from seed, key, size and generation rather than stored.

## Alternatives considered

- **`f(seed, key, size)` as #744's issue text says.** Identical bytes on a same-size overwrite, so
  a read returning the prior generation is invisible (0017 §4, `0017:361-370`). Rejected; 0017 is
  the plan of record.
- **A stateful PRNG seeded per object.** Fine for whole objects, but a range in the middle of a
  5 GiB object would need the whole prefix generated first. Rejected for random access.
- **Import the constants from `wyrd-core`.** Breaks the blackbox property (0017 §9). Rejected;
  mirror them, and check the mirror in a dev-only test.
- **Make the tuning flags required.** Every invocation would have to restate today's defaults.
  Rejected; 0017 asks for defaults that are recorded.
