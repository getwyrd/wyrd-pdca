# Result — issue 744 / validate-payloads-and-size-classes

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect: `wyrd-validate` has an argument surface and an S3 client, but nothing yet decides what
  bytes it sends or at which sizes. This slice adds two pure modules to `crates/validate` and three
  optional flags:
  - **derived payloads:** `bytes = f(seed, key, size, generation)`, generated as a stream, any
    byte range computable on its own, identical in every process for the same inputs, so a run
    never stores an object body and a resumed run can re-derive what it wrote;
  - **size classes** that straddle S3's boundaries and Wyrd's own, **computed from the deployment's
    tuning**, never from a hardcoded table;
  - the tuning as input: `--chunk-size`, `--max-root-value-bytes`, `--segment-threshold-bytes`,
    each optional with a default that mirrors today's value, and echoed with where its value came
    from.
- Success criterion: A NEW test file `crates/validate/tests/payload_and_sizes.rs` shows all of
  the following through the library's public API.
  **(A) Payload determinism.** For a fixed set of `(seed, key, size, generation)` inputs, the
  SHA-256 of the generated bytes equals a **pinned hex constant** in the test (a known-answer
  test). Because the constants were produced by a different process (the one Do ran to compute
  them), this is the cross-process check resumability rests on: any input the generator takes from
  process state (a hasher seed, an address, a clock) breaks it.
  **(B) Every input matters, at sizes where it can.** For named non-empty vectors (sizes 4 KiB and
  100,003 B, the second not a multiple of any block size), changing any one of seed, key, size or
  generation changes the bytes; in particular two generations of one key **at the same size**
  differ (0017 §4: without the generation an overwrite re-sends identical bytes, so a stale read
  would look correct). This is **not** promised for every size: at 0 B every input gives the same
  (empty) bytes, and a 1-byte payload has only 256 values, so below one block two generations can
  coincide. The module docs state that limit, for the oracle slice (#746) to account for: at those
  sizes the bytes alone cannot tell a stale generation from the current one, and the ETag is no
  help, since the gateway derives it from the body (`crates/server/src/lib.rs:274-275`).
  **(C) Exact length and random access.** The generator yields exactly `size` bytes (including 0
  and 1); for several split points, the pieces concatenate to the whole; and the bytes of any range
  `[a, b)` produced directly equal the same range cut from the whole.
  **(C′) Bounded state, direct access.** Every piece the streaming generator yields is at most a
  documented bound (e.g. 64 KiB) whatever the total size. A 64-byte range ending at the last byte
  of the `10 GiB + 1` class, and one ending at the last byte of a 1 TiB payload, are each produced
  directly within 5 s of wall time (honest work is a few hash blocks; regenerating the prefix is
  minutes to hours, and materializing the object exhausts memory). Each equals a pinned hex
  constant, as in (A), and equals the concatenation of its two halves produced directly.
  **(D) Size classes come from the tuning.** At the default tuning the classes, ascending and
  without duplicates, are: 0 B, 1 B, 4 KiB, 64 KiB, `C−1`, `C`, `C+1`, 5 MiB, 8 MiB, `64×C`,
  `T−1`, `T`, `T+1`, 5 GiB, 5 GiB + 1 and 10 GiB + 1, where `C` is the chunk size and `T` the
  segmentation threshold, each class labelled with the boundary it straddles. With a different
  `--chunk-size` the `C`-, `64×C`- and (derived) `T`-classes move and the fixed ones do not.
  **With only `--max-root-value-bytes` changed** (`C` = 1 MiB, budget 31,500, below today's
  50,000 so no ceiling question arises): the derived `T` moves from 158 MiB to 100 MiB
  (⌊31,500 / 315⌋ = 100, the rule `crates/core/src/multipart.rs:4940-4949` applies), and the
  fixed, `C` and `64×C` classes do not move. With `--segment-threshold-bytes` given, `T` is exactly that value, whatever the root
  budget. Two classes that coincide appear once, carrying both labels.
  **(E) The tuning flags.** Absent, each flag resolves to its default and the resolved-configuration
  echo says so (e.g. `--chunk-size = 1048576 (default)`; the threshold `(derived)`); given, it is
  used and echoed as given. A zero, a non-integer, an overflowing value, a repeated flag and a
  flag with no value are each refused by name, exactly as the existing flags are. The ten existing
  flags stay required, and `crates/validate/tests/cli_surface.rs` passes **unmodified**.
  **(F) The defaults have not drifted.** A dev-only check compares the mirrored literals with the
  constants they mirror: the root budget 50,000 with `wyrd_core::metadata::MAX_ROOT_VALUE_BYTES`
  (`crates/core/src/metadata.rs:574`), the per-chunk record width 315 with
  `wyrd_core::multipart::MAX_CHUNKREF_BYTES` (`crates/core/src/multipart.rs:4908`), and the
  derived default threshold at a 1 MiB chunk with `wyrd_core::multipart::max_single_put_bytes`
  (`:4992`). `wyrd-core` is already a dev-dependency of `crates/validate`; the binary still links no
  `wyrd-*` crate (`cargo xtask blackbox-guard`, run by `cargo xtask ci`).
- Repo + branch target: getwyrd/wyrd @ main
- Scope: the payload module, the size-class module, the three optional tuning flags with their
  defaults and echo, the dev-only drift check, the docs paragraph, and the new test file. /
  out of scope:

  - checkpoints, the journal and resumability (0017 §12, a later slice);
  - the oracle and the verdict artifact (#746, and the slice that adds `verdict.rs`);
  - making the chunk-map budgets deployment configuration on the server side (#739);
  - any change to `crates/validate/src/s3.rs` or `src/s3/` (#853 is rewriting them);
  - any `wyrd-*` crate in `[dependencies]`; `Cargo.lock` beyond what adding `sha2` to this crate
    records; `deny*.toml`.

# Adversarial review — #744 (derived payloads, size classes, tuning flags)

I tried to refute the fix and mostly could not. Each bullet below is either a refutation that held up only partly, or the evidence that held.

## What I attacked and could not break

- **The (A) and (C′) known answers are real cross-process checks.** I rebuilt the construction in Python from the module docs alone (`crates/validate/src/payload.rs:11-31`): SHA-256 over the length-prefixed seed, key, size and generation, then a big-endian block counter. So the docs describe the code exactly, and the constants do not come from the code checking itself. The non-ASCII `seed-ü` vector also catches a char-count/byte-count mix-up, and the 1 TiB tail (2^35 blocks) catches a counter truncated to 32 bits, which the 10 GiB + 1 tail would miss.
- **Last round's (C′) hang is fixed.** I applied the brief's "regenerate the prefix" mutant myself: hash blocks `0..offset/32` at the top of `fill_inside` (`payload.rs:170`). `the_last_bytes_of_a_huge_payload_are_produced_directly` fails at exactly 5.0 s, and the whole file exits in 5.9 s wall time with 24 passed and 1 failed. ## Findings

- NEEDS-HUMAN [impl] — The living architecture doc overstates the generation guarantee for two of the size classes this patch adds. `docs/design/architecture/05-building-block-view.md:297` says, with no condition, that "an overwrite at the same size still sends different bytes". At 0 B, which is a size class (`sizes.rs:228`), every generation sends identical (empty) bytes. At 1 B, also a class, two generations match with probability 1/256. The module docs state this limit correctly (`payload.rs:34-44`), and the brief's (B) requires it to be stated for #746. But the architecture doc is the one an oracle author reads first, and it says the opposite. Fix: add "except at the smallest sizes (0 B always, below 32 B with probability 2^(-8n)), see `payload.rs`". Secondary point in the same sentence: "from 0 B to 10 GiB + 1" holds only for chunk sizes near the default. `--chunk-size 1099511627776` is accepted and derives a 158 TiB `T` (I ran the binary).
- NEEDS-HUMAN [human] — Nothing checks that the tuning values make sense together, so a given `T` can label sizes that cross no segmentation boundary. That is the "reports coverage of a boundary it never crossed" problem the brief's Motivation exists to prevent. Concrete cases, all accepted with exit 3 by the real binary:
  - `--segment-threshold-bytes 3` with the default 1 MiB chunk. The table then labels 2-, 3- and 4-byte objects "the chunk-map segmentation threshold" (`sizes.rs:181-187`, `:247-256`).
  - The test's own vector, `T = 123,456,789` at `C = 1 MiB` (`payload_and_sizes.rs:726`, `:942`). `T − 1`, `T` and `T + 1` all come to ⌈x / C⌉ = 118 chunks. The server segments by chunk count, past 158 (`multipart.rs:4954-4959`), so none of the three straddles anything.

  The brief's (D) does say a given `T` is used "exactly", and 0017 §4 keeps the flag because the tool can't know the server's rule. So whether to refuse, or just print a warning in the echo, when `T < C` or `T` is not a multiple of `C` is a scope decision, not a build slip. The echo does show `(given)`, so this is not silent.
- NEEDS-HUMAN [impl] — The only changed line diff-coverage reports as never run is `TuningError::Zero`'s `Display` text (`sizes.rs:115`; `gate-logs/C4-diff-cov.log`, "MISS crates/validate/src/sizes.rs:115"). The test checks the variant, not the message (`payload_and_sizes.rs:853`). Last round's sign-off asked for exactly this kind of one-line pin (label, `generation()`) and it was added elsewhere. Add `assert_eq!(err.to_string(), "flag `--chunk-size` must be a positive integer, not 0")`. Low severity: the CLI can never reach this path, because the parser refuses 0 first.

This also contradicts “Any keyed construction that meets (A)–(C) is acceptable” (`brief.md:139`). Add an explicit acceptance check for bounded retained state and computation starting at the requested block, with sparse reads near the 10 GiB class and reviewer evidence or a mutation check that rejects whole-object buffering/prefix traversal.
- [ ] **The size-class discriminator leaves the root-budget input unbound.** (D) varies chunk size and the explicit threshold, but never varies `--max-root-value-bytes` (`brief.md:37-43`); (E) checks flag resolution/echo and (F) checks defaults (`brief.md:44-54`). An implementation that records the supplied budget but always derives `T` using 50,000 can pass those specified size assertions. The tracker explicitly requires “Size classes are computed from the tuning parameters, not hardcoded” (`notes.json`, Definition of done), and the target capacity actually divides the root budget by the record width (`crates/core/src/multipart.rs:4940-4949`). Require a case changing only the root budget: at `C = 1 MiB`, a budget of 63,000 must move derived `T` from 158 MiB to 200 MiB, while fixed/C classes stay unchanged; also check that an explicit threshold still overrides that derivation. Require the hardcoded-root-budget mutant to fail.
- [ ] **(F) cannot catch a drifted chunk-size default, and the brief's reason for skipping it is wrong.** `payload_and_sizes.rs:825` is `assert_eq!(DEFAULT_CHUNK_SIZE, MIB)`, which compares the copied value with a literal and can never go red. I changed the server's `DEFAULT_CHUNK_SIZE` (`crates/server/src/lib.rs:59`) to `4 << 20` and re-ran: **22 passed**. The tool would then still put C at 1 MiB and T at 158 MiB by default, against a server whose single-PUT ceiling is 632 MiB. That is the "stale table" failure the brief's Motivation names. The brief says the constant is "private, so not checkable from a test", but its effect can be observed. `wyrd-server` is already a dev-dependency (`crates/validate/Cargo.toml:53`), and `Gateway::new` uses that default (`crates/server/src/lib.rs:163-168`). A single PUT declared one byte over the limit is refused `EntityTooLarge { declared, limit }` from its headers, before the body is read (`:284-296`, `:417`). `s3_client_roundtrip.rs:326` already starts that gateway in-process. Whether to add a behavioural check here is a scope call.
- [ ] **Tunings no server can have are accepted, and their labels then claim boundaries the sizes don't straddle.** Units are refused, so an operator who means "158 MiB" may type `--segment-threshold-bytes 158`. I ran that on the built binary: it is accepted, echoed `= 158 (given)`, and the table puts "the chunk-map segmentation threshold (T)" at 157/158/159 B. Those sizes are smaller than one 1 MiB chunk and can never segment. The run would report coverage of a boundary it never crossed, which is the exact failure the brief's Motivation says this slice prevents. `--chunk-size 4294967296 --segment-threshold-bytes 1024` (T < C) is also accepted. The same gap applies to C: with any `--chunk-size` ≤ 64 KiB, the 64 KiB class keeps the `SubChunk` label, "inside one chunk" (`crates/validate/src/sizes.rs:263-264`), though it spans 16 or more chunks. The server refuses C < 1 MiB (`crates/server/src/lib.rs:104`) and its T is always a whole multiple of C (`crates/core/src/multipart.rs:4992-5002`). The brief says both "a tuning that cannot produce a valid table is refused" and "T is exactly that value"; whether T < C, a T that is not a multiple of C, or C ≤ 64 KiB counts as "cannot produce a valid table" needs a decision (`Tuning::resolve`, `sizes.rs:142-181`).
