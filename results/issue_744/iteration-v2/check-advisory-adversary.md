# Adversarial review — #744 (derived payloads, size classes, tuning flags)

I tried to refute the fix and mostly could not. Each bullet below is either a refutation that held up only partly, or the evidence that held.

## What I attacked and could not break

- **The (A) and (C′) known answers are real cross-process checks.** I rebuilt the construction in Python from the module docs alone (`crates/validate/src/payload.rs:11-31`): SHA-256 over the length-prefixed seed, key, size and generation, then a big-endian block counter. All 6 whole-payload digests and both 64-byte tails (10 GiB + 1 and 1 TiB) match the pinned constants (`crates/validate/tests/payload_and_sizes.rs:147-190`, `:460-473`). So the docs describe the code exactly, and the constants do not come from the code checking itself. The non-ASCII `seed-ü` vector also catches a char-count/byte-count mix-up, and the 1 TiB tail (2^35 blocks) catches a counter truncated to 32 bits, which the 10 GiB + 1 tail would miss.
- **Last round's (C′) hang is fixed.** I applied the brief's "regenerate the prefix" mutant myself: hash blocks `0..offset/32` at the top of `fill_inside` (`payload.rs:170`). `the_last_bytes_of_a_huge_payload_are_produced_directly` fails at exactly 5.0 s, and the whole file exits in 5.9 s wall time with 24 passed and 1 failed. The huge-size check in `no_piece_exceeds_the_documented_bound_whatever_the_size` now only calls `size_hint`, which hashes nothing (`payload_and_sizes.rs:437-455`).
- **The tests pass on the patched tree** (25/25 new, 21/21 in `cli_surface.rs`), and `cli_surface.rs` has no diff. The C4-ci log shows the new test binary running, plus typos, docs lint/render and `blackbox-guard` all running rather than skipped (`gate-logs/C4-ci.log:11-28`, `:3109`).
- **The derived-threshold rule matches the server.** `MAX_MAP_CHUNKS = VALUE_CHUNK_CAPACITY = ⌊MAX_ROOT_VALUE_BYTES / 315⌋` and `max_single_put_bytes = 158 × chunk_size` (`crates/core/src/multipart.rs:4940-4959`, `:4992-5002`). That is the same formula as `derived_segment_threshold` (`crates/validate/src/sizes.rs:138-152`), and the (F) test ties all three together.
- **The parser holds up.** Full-width digits (`８`), `+5`, `-5`, `--chunk-size=4096`, `--chunk-size 4096 --chunk-size abc`, `u64::MAX` and `u64::MAX + 1` are each refused, and every refusal names its flag. `007` is accepted as 7. That is harmless, though the echo then prints the normalized `7 (given)`, not the typed text.
- **Settled items I did not re-raise:** C4-verify UNVERIFIABLE (declared in the brief and accepted at the round-1 sign-off), and the server's private `DEFAULT_CHUNK_SIZE` not being drift-checkable (brief, "Citations expected").

## Findings

- NEEDS-HUMAN [impl] — The living architecture doc overstates the generation guarantee for two of the size classes this patch adds. `docs/design/architecture/05-building-block-view.md:297` says, with no condition, that "an overwrite at the same size still sends different bytes". At 0 B, which is a size class (`sizes.rs:228`), every generation sends identical (empty) bytes. At 1 B, also a class, two generations match with probability 1/256. The module docs state this limit correctly (`payload.rs:34-44`), and the brief's (B) requires it to be stated for #746. But the architecture doc is the one an oracle author reads first, and it says the opposite. Fix: add "except at the smallest sizes (0 B always, below 32 B with probability 2^(-8n)), see `payload.rs`". Secondary point in the same sentence: "from 0 B to 10 GiB + 1" holds only for chunk sizes near the default. `--chunk-size 1099511627776` is accepted and derives a 158 TiB `T` (I ran the binary).
- NEEDS-HUMAN [human] — Nothing checks that the tuning values make sense together, so a given `T` can label sizes that cross no segmentation boundary. That is the "reports coverage of a boundary it never crossed" problem the brief's Motivation exists to prevent. Concrete cases, all accepted with exit 3 by the real binary:
  - `--segment-threshold-bytes 3` with the default 1 MiB chunk. The table then labels 2-, 3- and 4-byte objects "the chunk-map segmentation threshold" (`sizes.rs:181-187`, `:247-256`).
  - The test's own vector, `T = 123,456,789` at `C = 1 MiB` (`payload_and_sizes.rs:726`, `:942`). `T − 1`, `T` and `T + 1` all come to ⌈x / C⌉ = 118 chunks. The server segments by chunk count, past 158 (`multipart.rs:4954-4959`), so none of the three straddles anything.

  The brief's (D) does say a given `T` is used "exactly", and 0017 §4 keeps the flag because the tool can't know the server's rule. So whether to refuse, or just print a warning in the echo, when `T < C` or `T` is not a multiple of `C` is a scope decision, not a build slip. The echo does show `(given)`, so this is not silent.
- NEEDS-HUMAN [impl] — The only changed line diff-coverage reports as never run is `TuningError::Zero`'s `Display` text (`sizes.rs:115`; `gate-logs/C4-diff-cov.log`, "MISS crates/validate/src/sizes.rs:115"). The test checks the variant, not the message (`payload_and_sizes.rs:853`). Last round's sign-off asked for exactly this kind of one-line pin (label, `generation()`) and it was added elsewhere. Add `assert_eq!(err.to_string(), "flag `--chunk-size` must be a positive integer, not 0")`. Low severity: the CLI can never reach this path, because the parser refuses 0 first.
- NEEDS-HUMAN [human] — I could not check the T4-batch-review claim in `check-gates.json` ("3x codex, union, triaged … 0 blocking, 0 recorded-rejected, 0 noise-dropped") from the frozen evidence. `gate-logs/T4-batch-review.log` holds only the summary line, and the gate took 25.8 s for three passes over a ~92 KB diff, with not even a noise-dropped finding. That may be fine, but if the rubric review is the "one deep, multi-pass review" that AGENTS.md's definition of done relies on, someone should open `results/issue_744/review-batch.md` and confirm the three passes ran on this round's diff rather than a cached result. This is about the evidence, not a defect in the patch.

Net: I attempted to refute (A) determinism, (B) input sensitivity, (C)/(C′) direct access and bounded time, (D) the derivation, (E) strict parsing and (F) drift, and could not break any of them. The one refutation with substance is the tuning sanity question above, and it is a scope call.
