The two implementation findings are narrow and reproducible:

- **C5: preserve the public API's nonzero-budget contract.** `Tuning::resolve(&TuningFlags { max_root_value_bytes: Some(0), segment_threshold_bytes: Some(1_048_576), ..Default::default() })` returns `Ok`, and its size table succeeds. Supplying the threshold bypasses `derived_segment_threshold`, while `Tuning::check` validates only the chunk size and threshold (`crates/validate/src/sizes.rs:246`, `crates/validate/src/sizes.rs:277`). This contradicts the explicit promise that hand-built flags reject zero (`crates/validate/src/sizes.rs:95`). Add a budget-positivity check shared by resolution and hand-built tuning, plus this regression case. The CLI already rejects zero correctly; the impact is confined to the public library boundary (`reviewer-probe.log:1`, `reviewer-cli-probes.log:21`). Keep the intentional positive-budget override behavior intact: the existing test accepts a budget of 200 with an explicit threshold (`crates/validate/tests/payload_and_sizes.rs:770`).
- **T5: qualify the architecture's size ceiling.** The sentence claiming that every accepted chunk size with a derived threshold tops out at `10 GiB + 1`, and that only an explicit threshold can exceed it, is false. With the default chunk size and only `--max-root-value-bytes 5000000`, the real binary accepts and echoes a derived `T = 16,644,046,848`; the table's largest class is `16,644,046,849` (`reviewer-cli-probes.log:1`, `reviewer-probe.log:3`). Limit the ceiling statement to the default root budget, or describe the maximum as the largest fixed or tuning-derived class. No behavior change is needed.
