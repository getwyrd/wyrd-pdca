# Result — issue 744 / validate-payloads-and-size-classes

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect: `wyrd-validate` has an argument surface and an S3 client, but nothing yet decides what
  bytes it sends or at which sizes. This slice adds two pure modules to `crates/validate` and three
  optional flags:
  - **derived payloads:** `bytes = f(seed, key, size, generation)`, generated as a stream, any
    byte range computable on its own, identical in every process for the same inputs, so a run
    never stores an object body and a resumed run can re-derive what it wrote;
  - **size classes** that straddle S3's boundaries and Wyrd's own, **computed from the deployment's
    tuning**, never from a hardcoded table;
  - the tuning as input: `--chunk-size`, `--max-root-value-bytes`, `--segment-threshold-bytes`,
    each optional with a default that mirrors today's value, and echoed with where its value came
    from.
- Success criterion: A NEW test file `crates/validate/tests/payload_and_sizes.rs` shows all of
  the following through the library's public API.
  **(A) Payload determinism.** For a fixed set of `(seed, key, size, generation)` inputs, the
  SHA-256 of the generated bytes equals a **pinned hex constant** in the test (a known-answer
  test). Because the constants were produced by a different process (the one Do ran to compute
  them), this is the cross-process check resumability rests on: any input the generator takes from
  process state (a hasher seed, an address, a clock) breaks it.
  **(B) Every input matters, at sizes where it can.** For named non-empty vectors (sizes 4 KiB and
  100,003 B, the second not a multiple of any block size), changing any one of seed, key, size or
  generation changes the bytes; in particular two generations of one key **at the same size**
  differ (0017 §4: without the generation an overwrite re-sends identical bytes, so a stale read
  would look correct). This is **not** promised for every size: at 0 B every input gives the same
  (empty) bytes, and a 1-byte payload has only 256 values, so below one block two generations can
  coincide. The module docs state that limit, for the oracle slice (#746) to account for: at those
  sizes the bytes alone cannot tell a stale generation from the current one, and the ETag is no
  help, since the gateway derives it from the body (`crates/server/src/lib.rs:274-275`).
  **(C) Exact length and random access.** The generator yields exactly `size` bytes (including 0
  and 1); for several split points, the pieces concatenate to the whole; and the bytes of any range
  `[a, b)` produced directly equal the same range cut from the whole.
  **(C′) Bounded state, direct access.** Every piece the streaming generator yields is at most a
  documented bound (e.g. 64 KiB) whatever the total size. A 64-byte range ending at the last byte
  of the `10 GiB + 1` class, and one ending at the last byte of a 1 TiB payload, are each produced
  directly within 5 s of wall time (honest work is a few hash blocks; regenerating the prefix is
  minutes to hours, and materializing the object exhausts memory). Each equals a pinned hex
  constant, as in (A), and equals the concatenation of its two halves produced directly.
  **(D) Size classes come from the tuning.** At the default tuning the classes, ascending and
  without duplicates, are: 0 B, 1 B, 4 KiB, 64 KiB, `C−1`, `C`, `C+1`, 5 MiB, 8 MiB, `64×C`,
  `T−1`, `T`, `T+1`, 5 GiB, 5 GiB + 1 and 10 GiB + 1, where `C` is the chunk size and `T` the
  segmentation threshold, each class labelled with the boundary it straddles. With a different
  `--chunk-size` the `C`-, `64×C`- and (derived) `T`-classes move and the fixed ones do not.
  **With only `--max-root-value-bytes` changed** (`C` = 1 MiB, budget 31,500, below today's
  50,000 so no ceiling question arises): the derived `T` moves from 158 MiB to 100 MiB
  (⌊31,500 / 315⌋ = 100, the rule `crates/core/src/multipart.rs:4940-4949` applies), and the
  fixed, `C` and `64×C` classes do not move. With `--segment-threshold-bytes` given, `T` is exactly that value, whatever the root
  budget. Two classes that coincide appear once, carrying both labels.
  **(E) The tuning flags.** Absent, each flag resolves to its default and the resolved-configuration
  echo says so (e.g. `--chunk-size = 1048576 (default)`; the threshold `(derived)`); given, it is
  used and echoed as given. A zero, a non-integer, an overflowing value, a repeated flag and a
  flag with no value are each refused by name, exactly as the existing flags are. The ten existing
  flags stay required, and `crates/validate/tests/cli_surface.rs` passes **unmodified**.
  **(F) The defaults have not drifted.** A dev-only check compares the mirrored literals with the
  constants they mirror: the root budget 50,000 with `wyrd_core::metadata::MAX_ROOT_VALUE_BYTES`
  (`crates/core/src/metadata.rs:574`), the per-chunk record width 315 with
  `wyrd_core::multipart::MAX_CHUNKREF_BYTES` (`crates/core/src/multipart.rs:4908`), and the
  derived default threshold at a 1 MiB chunk with `wyrd_core::multipart::max_single_put_bytes`
  (`:4992`). `wyrd-core` is already a dev-dependency of `crates/validate`; the binary still links no
  `wyrd-*` crate (`cargo xtask blackbox-guard`, run by `cargo xtask ci`).
- Repo + branch target: getwyrd/wyrd @ main
- Scope: the payload module, the size-class module, the three optional tuning flags with their
  defaults and echo, the dev-only drift check, the docs paragraph, and the new test file. /
  out of scope:
  - which verb a class is driven through, and what each class is expected to answer (the
    capability matrix and `smoke`, #743; 0017 §4 says the segmentation and > 5 GiB classes are
    multipart-only, which is the matrix's business);
  - checkpoints, the journal and resumability (0017 §12, a later slice);

  - making the chunk-map budgets deployment configuration on the server side (#739);

  - any `wyrd-*` crate in `[dependencies]`; `Cargo.lock` beyond what adding `sha2` to this crate

# Adversarial review — #744 (derived payloads, size classes, tuning flags)

Summary: I could not break the code. The payload construction, the size table, the parser and the drift checks held up against every attack below. ## Findings

- NEEDS-HUMAN [impl] — `docs/design/architecture/05-building-block-view.md:297` makes two claims the code does not back.
  - (1) "At any accepted chunk size with a derived threshold they run from 0 B to 10 GiB + 1; only a given `--segment-threshold-bytes` above 10 GiB moves the `T` classes past that." This is false. `--max-root-value-bytes` has no ceiling (`crates/validate/src/sizes.rs:200-214`), so a large budget pushes a *derived* `T` past 10 GiB. I ran the built binary with `--chunk-size 16777216 --max-root-value-bytes 250000`. It exits 3 and echoes `--segment-threshold-bytes = 13304332288 (derived)` (12.4 GiB).
  - (2) The same sentence lists "a budget too small to hold one chunk record" as refused, without conditions. But `--max-root-value-bytes 200 --segment-threshold-bytes 1048576` is accepted (exit 3; it echoes `--max-root-value-bytes = 200 (given)`), and the test pins that acceptance (`crates/validate/tests/payload_and_sizes.rs:770`, `Some(200)`). The module doc (`sizes.rs:16`, "too small to derive a threshold from") is accurate; the architecture doc is not.
  - Fix: limit the 10 GiB sentence to the default root budget, and say the budget is refused only when the threshold is derived from it.
- NEEDS-HUMAN [human] — `crates/validate/src/sizes.rs:13-14` says "A tuning no deployment can have is refused by flag name, never clamped", but `--max-root-value-bytes` has no upper bound. `--max-root-value-bytes 99999999999` is accepted and derives `T = 332881269358592` (about 303 TiB), so the table's `T − 1`/`T`/`T + 1` classes become 303 TiB objects that #743 would be asked to write. - NEEDS-HUMAN [human] — the T4 claim in `check-gates.json` ("0 blocking … pass") rests on a one-line log (`gate-logs/T4-batch-review.log:10`) from a 26.23 s run of what is labelled "3x codex" over a 116 KB diff.
