# Adversarial review — #744 (derived payloads, size classes, tuning flags)

Summary: I could not break the code. The payload construction, the size table, the parser and the drift checks held up against every attack below. What's left: two false statements in the living architecture doc (one confirmed by running the binary), one scope question about the root budget having no upper limit, and one process gap in the T4 gate evidence.

## Findings

- NEEDS-HUMAN [impl] — `docs/design/architecture/05-building-block-view.md:297` makes two claims the code does not back.
  - (1) "At any accepted chunk size with a derived threshold they run from 0 B to 10 GiB + 1; only a given `--segment-threshold-bytes` above 10 GiB moves the `T` classes past that." This is false. `--max-root-value-bytes` has no ceiling (`crates/validate/src/sizes.rs:200-214`), so a large budget pushes a *derived* `T` past 10 GiB. I ran the built binary with `--chunk-size 16777216 --max-root-value-bytes 250000`. It exits 3 and echoes `--segment-threshold-bytes = 13304332288 (derived)` (12.4 GiB).
  - (2) The same sentence lists "a budget too small to hold one chunk record" as refused, without conditions. But `--max-root-value-bytes 200 --segment-threshold-bytes 1048576` is accepted (exit 3; it echoes `--max-root-value-bytes = 200 (given)`), and the test pins that acceptance (`crates/validate/tests/payload_and_sizes.rs:770`, `Some(200)`). The module doc (`sizes.rs:16`, "too small to derive a threshold from") is accurate; the architecture doc is not.
  - Fix: limit the 10 GiB sentence to the default root budget, and say the budget is refused only when the threshold is derived from it.
- NEEDS-HUMAN [human] — `crates/validate/src/sizes.rs:13-14` says "A tuning no deployment can have is refused by flag name, never clamped", but `--max-root-value-bytes` has no upper bound. `--max-root-value-bytes 99999999999` is accepted and derives `T = 332881269358592` (about 303 TiB), so the table's `T − 1`/`T`/`T + 1` classes become 303 TiB objects that #743 would be asked to write. Core ties `MAX_ROOT_VALUE_BYTES * 2 <= MAX_VALUE_BYTES = 100_000` (`crates/core/src/metadata.rs:549`, `:576`), so any budget above 50,000 needs FoundationDB's value limit raised, which is exactly "a tuning no deployment can have". The brief deliberately avoided the ceiling question (brief.md:54-55, "so no ceiling question arises"), so where to set a cap (50,000? 100,000? none until #739?) is a scope decision, not a build fix.
- NEEDS-HUMAN [human] — the T4 claim in `check-gates.json` ("0 blocking … pass") rests on a one-line log (`gate-logs/T4-batch-review.log:10`) from a 26.23 s run of what is labelled "3x codex" over a 116 KB diff. The round-4 sign-off asked for exactly this to change: per-pass evidence in the gate log, "not just a summary line" (brief.md:246). From the evidence I was given, I cannot tell whether three passes actually reviewed this round's diff. Separately, `patch.diff` is now 116,439 bytes, against the 100 KB backstop that sign-off said to watch (brief.md:247). Both are harness or process calls, not code defects.
- Note for #743, not a fix request: `sizes.rs:112-114` defines `T` as "the largest object size whose chunk map is still flat". That holds when every chunk but the last is full (a single PUT). It does not hold for multipart with part sizes that aren't a multiple of `C`, because each part is chunked on its own (`MAX_PART_CHUNKS`, `crates/core/src/multipart.rs:4972`). Example: `--chunk-size 3145728` (accepted) gives `T = 474 MiB`. A `T − 1` object sent as stock 8 MiB parts names 59 × 3 + 1 = 178 chunk refs, which is more than 158, so it segments. Multipart is `NotImplemented` in the server today (`crates/server/src/lib.rs:823-839`), and which verb drives a class is #743's job (brief.md:98-100), so this is only recorded here.

## What I tried and could not break

- **Green re-run.** Built and ran `cargo test -p wyrd-validate --test payload_and_sizes` in a scratch copy of `$PDCA_TARGET`: 26 passed in 0.22 s, matching `gate-logs/C4-verify.log`. The C4-verify result UNVERIFIABLE (exit 77) is the net-new posture the brief declared in advance (brief.md:111-113), not a refutation.
- **Known-answer constants (A, C′).** I wrote an independent Python version of the construction from the module docs alone (`crates/validate/src/payload.rs:17-27`), run as a separate process. It reproduces all six `KNOWN_ANSWERS` digests and both 64-byte `TAIL_ANSWERS` (10 GiB + 1 and 1 TiB) exactly. So the docs describe the construction exactly, and the constants depend on no process state. 300 one-byte generations gave 174 distinct values, which matches the documented 1/256 limit (`payload.rs:38-44`).
- **Bounded failure.** I injected the brief's "regenerate the prefix" fault into `fill_inside` (`payload.rs:170`). The suite now fails in 5 s, naming `the_last_bytes_of_a_huge_payload_are_produced_directly` (25 passed, 1 failed, 6 s wall time). The round-1 hang is fixed.
- **Parser (E).** A full-width digit `５`, an invalid value on a repeated flag (`--chunk-size 4194304 --chunk-size abc`), and `u64::MAX` as a threshold at the default chunk size are each refused with the flag named (`crates/validate/src/args.rs:239-255`, `sizes.rs:177-185`). `cli_surface.rs` is unchanged and passes (`gate-logs/C4-ci.log:3077`).
- **Drift checks (F).** The server's default chunk size and its 1–16 MiB range are read through public behaviour, not copied. The single-PUT refusal (`crates/server/src/lib.rs:291-296`) and the `s3` role's chunk-size check run before anything is opened (`crates/server/src/cli.rs:2477-2478`), so the probe has no side effects. Mutation testing caught every mutant (`gate-logs/C5-mutants.log:13`: 106 tested, 95 caught, 11 unviable, 0 missed). The blackbox guard and the all-features advisory step passed (`gate-logs/C4-ci.log:27-28`, `:3671-3672`).
