validate: derive payloads and size classes from the deployment tuning

wyrd-validate could parse its flags and talk S3, but nothing decided which
bytes it writes or at which sizes. Both have to be derived, not stored or
copied. A run that lasts months cannot keep every body it wrote, and an
overwrite that re-sends the same bytes lets a stale read pass as correct. A
size table copied from today's constants goes stale the day one moves, and
the run then claims coverage of a boundary it never crossed.

Object bodies are now a pure function of the seed, the key, the size and
the write's generation: SHA-256 in counter mode, so the same inputs give the
same bytes in every process, any byte range is computed on its own, and the
generator's state does not grow with the size. A resumed run or a read-back
check can re-derive what was written. The construction is documented
exactly in payload.rs, and known-answer digests in the test pin it. Two
generations of one key differ at any size from a few bytes up; at 0 B and
below one 32-byte block they can coincide, and the docs say so for the
read-back oracle.

The size classes (0 B, 1 B, 4 KiB, 64 KiB, C-1/C/C+1, 5 MiB, 8 MiB, 64xC,
T-1/T/T+1, 5 GiB, 5 GiB + 1, 10 GiB + 1) are computed from three new
optional flags: --chunk-size, --max-root-value-bytes and
--segment-threshold-bytes. Absent, each takes today's server value, or for
the threshold is derived as floor(root budget / 315) x chunk size, 158 MiB
at the defaults. The configuration echo marks each value as given, default
or derived. A tuning no deployment can have is refused by flag name, never
clamped. A dev-only test compares the mirrored defaults and limits with the
wyrd-core constants and the server's behaviour, so they cannot drift
silently; the binary still links no wyrd-* crate.

The ten required flags are unchanged and the binary still exits without
issuing a request.
