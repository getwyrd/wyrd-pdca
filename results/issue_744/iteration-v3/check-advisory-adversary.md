# Adversarial review: issue 744 (derived payloads, size classes, tuning flags)

I rebuilt the patched tree in a scratch copy. `cargo test -p wyrd-validate --test payload_and_sizes` passes (25 tests, 0.21 s). The failed refutations are listed first; then three findings.

## What I tried and could not break

- **(A) known answers.** I wrote a separate Python version of the construction, working only from the module docs (`crates/validate/src/payload.rs:17-27`). It reproduces all six digests (`crates/validate/tests/payload_and_sizes.rs:149-192`) and both 64-byte tails at 10 GiB + 1 and 1 TiB (`:468-481`). The constants really were produced by a different process, and the docs are exact enough to reimplement the construction.
- **The brief's required reds (brief.md:116-123).** I applied each fault myself. Each one fails the suite:
  - generation dropped (`payload.rs:128`): fails at `:253`, `:200`, `:503`;
  - chunk size hardcoded (`sizes.rs:213`): fails at `:712` and `:793`;
  - root budget hardcoded (`sizes.rs:142`): fails at `:736`, `:825`, `:1042`, `:1177`;
  - range start shifted, in `range()` and in `fill()`: both fail;
  - a default echoed as given, and a derived value echoed as a default: both fail at `:990`, `:1015`, `:1177`.
- **Last round's hang is fixed.** Regenerating the prefix inside `fill_inside` (`payload.rs:170`) fails in 5.0 s. Regenerating it inside the `range()` constructor (`payload.rs:186`) fails in 10.0 s through `bounded` (`payload_and_sizes.rs:81`, `:445-460`). Neither hangs the suite.
- **CLI edge cases on the real binary.** Leading zeros, a repeated flag with a bad second value, `u64::MAX`, and `--max-root-value-bytes 315` (so `T = C`, and the two classes merge) all behave as documented. Each refusal names its flag. The gates check out too: CI ran typos, the docs render and blackbox-guard (`gate-logs/C4-ci.log:11-28`), and C5 shows 0 missed mutants. C4-verify's UNVERIFIABLE result is the net-new exception the brief declared in advance (brief.md:111-113). The reds above support accepting it.

## Findings

- NEEDS-HUMAN [impl] — **(F) does not check the chunk-size default, though it can.** `crates/validate/tests/payload_and_sizes.rs:1210` compares the tool's `DEFAULT_CHUNK_SIZE` with the test's own literal `MIB`, so that assertion can never fail. The brief says the server's value is "private, so not checkable from a test" (brief.md:129-130). That is wrong. A default `wyrd_server::Gateway::new(..)` (server `crates/server/src/lib.rs:57-59`; `wyrd-server` is already a dev-dependency) refuses `ObjectGateway::put_object_streaming(.., u64::MAX, ..)` with the public `GatewayError::EntityTooLarge { limit }` (`crates/gateway-core/src/lib.rs:270-275`, server `lib.rs:291-296`), and `limit` is 158 × the server's default chunk size. I tested this. I changed server `lib.rs:59` to `2 << 20`: all 25 tests in this patch still pass, while the tool's default chunk size and derived `T` silently drift from the server's. A 25-line probe test (it adds a `wyrd-gateway-core` dev-dependency) goes red: `left: 331350016, right: 165675008`. The server's own unit test (`lib.rs:1042`) would be updated in the same change, so nothing on the tool side would catch the drift. Fix: add that assertion to the (F) test.
- NEEDS-HUMAN [impl] — **The doc for `T` is off by one.** `crates/validate/src/sizes.rs:82` says ``T`: the object size at which the chunk map must segment``. At `T = ⌊budget / 315⌋ × C` the map holds exactly `MAX_MAP_CHUNKS` chunks, and that map is still flat (`crates/core/src/multipart.rs:4955-4959`). `T + 1` is the first size that segments (multipart) or is refused (single PUT, `multipart.rs:4987-4992`). The architecture doc gets this right ("the size past which a chunk map no longer fits one value"), so the code and the living doc disagree, and #743 will build its expected answers on this field. Fix: reword `:82` to say "the largest object size whose chunk map is still flat; `T + 1` is the first that is not."
- NEEDS-HUMAN [human] — **Tunings no deployment can have are accepted, and the table then labels boundaries that are not there.** I ran the binary with `--segment-threshold-bytes 158`, an easy slip for "158 chunks". It is accepted and echoed as `158 (given)`, so the `T` classes sit at 157, 158 and 159 bytes, below one chunk. On this server `T` is always `MAX_MAP_CHUNKS × C`. The tool also accepts `--chunk-size 1` and `--chunk-size 4096`, though the server takes only 1 MiB to 16 MiB (server `lib.rs:77`, `:104`). At `C = 4 KiB` the fixed 64 KiB class is still labelled "sub-chunk" (`sizes.rs:231`, `:320`) although it spans 16 chunks. The 4 KiB class is labelled both "sub-chunk" and "the chunk size (C)", and the test pins that contradiction (`payload_and_sizes.rs:793`). The echo shows every value, so none of this is silent, and the brief only asks for checked arithmetic (brief.md:169). This is the risk the brief's Motivation names ("reports coverage of a boundary it never crossed"), now caused by operator input. Scope call for you: refuse `T < C` (or a `T` that is not a multiple of `C`), make the "sub-chunk" label depend on `size < C`, or leave it to the operator.
