feat(metadata-tikv): skeleton + shared conformance suite (M4.1, #252)

Until now Wyrd could only keep its metadata in the embedded, single-node
redb store — there was no way to run the metadata layer on a distributed
backend, so a deployment could not scale metadata beyond one machine.

This stands up a TiKV-backed metadata store as a first, deliberately small
skeleton: the basic get / scan / commit shapes over TiKV's transactional
API, enough to prove that the distributed backend honours the same
MetadataStore contract the embedded one already does. The trait itself is
unchanged — swapping backends stays a composition choice, not a rewrite.

To keep the two backends from drifting, the generic trait-contract tests
that previously lived only with redb are lifted verbatim into a single
shared suite that both backends now drive; redb keeps its own model and
property tests. One suite, two implementations, one pinned contract.

The TiKV client is a heavy, pre-1.0 dependency, so it sits behind an
off-by-default `tikv` feature. A build with no TiKV — a laptop or a CI
worker without a cluster — never compiles that dependency tree and the
TiKV conformance test skips cleanly, so the standard build and checks stay
green. A dedicated `cargo xtask tikv-conformance` job brings up a throwaway
single-node TiKV under deploy/, turns the feature on, and runs the shared
suite against a real cluster.

Fixes #252
