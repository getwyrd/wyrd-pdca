deploy: add FoundationDB recipes at all three fixture tiers

FoundationDB is the chosen production metadata backend, but the deploy
recipes only covered it at the single-node testbed tier. TiKV — the
retained fallback — had a stack at every tier, so operators had no way to
stand FoundationDB up at the topologies that are meant to prove it: there
was no replicated cluster to run the fault battery against, and the
canonical single-zone stack was wired to TiKV with no FoundationDB peer.
The single-zone stack also read as "the" stack rather than one of a pair,
quietly implying its backend was the production track.

This adds the two missing FoundationDB recipes so it reaches parity with
TiKV:

- deploy/fdb-multi-replica/ — a three-process cluster in double redundancy
  with a fault sidecar that can partition and kill a process mid-commit,
  on a bridge network with one netns per node so an injected partition is
  genuinely bidirectional (the same iteration-13 topology fix the TiKV
  peer records). The sidecar is reused as-is from the TiKV recipe.
- deploy/small-multi-node-fdb/ — the identical single-zone role topology
  to deploy/small-multi-node/ (3 etcd + 9 D servers + 3 custodians + 3 S3
  gateways) with the metadata tier swapped to FoundationDB; every role
  that opens a metadata store now opens --metadata-backend fdb.

deploy/README.md gains a profile matrix naming all six recipes and which
suite drives which tier, and states plainly that deploy/small-multi-node/
is the TiKV peer of deploy/small-multi-node-fdb/ and stays canonical until
the fault battery clears FoundationDB — so the unqualified name is no
longer read as "the" stack. The rename to small-multi-node-tikv/ is left
for a follow-up to avoid churning landed paths; the pairing is recorded in
prose instead.

The wyrd roles run the wyrd:fdb image built by the FoundationDB Dockerfile
added in commit c233380dac23f7867f38582994aa9c7d2121588f, which installs
the FoundationDB client so the feature build can link libfdb_c.

A new guard, xtask/tests/fdb_deploy_profiles.rs, pins both recipes exist,
that every single-zone metadata role names fdb and none names tikv, and
that the README documents the matrix and the pairing; where Docker is
present it also parses each stack with docker compose config and checks
the declared roles.
