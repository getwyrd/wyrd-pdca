feat(506): serve HeadObject with GET's metadata headers, no body

HTTP HEAD /bucket/key returned 405 MethodNotAllowed: the object dispatch
matched only PUT, GET, and DELETE, so every HEAD fell through to the
method-not-allowed arm. That broke the ubiquitous HEAD-before-GET/PUT
pattern -- `aws s3 cp` downloads failed on their HeadObject preflight,
and most SDK existence checks got a 405 instead of a yes/no answer.

A signed HEAD of a stored object now returns 200 with no body and the
same metadata headers a GET of that object carries: Content-Length (the
object's real size, not 0), plus the ETag, Content-Type, and
Last-Modified introduced by the object-metadata model in commit
76dd913109db98a628dd24fac76bed3b25dfc780, with the same fallbacks GET
uses. A HEAD of an absent key returns 404 NoSuchKey, headers only. PUT,
GET, and DELETE behaviour is unchanged.

The lookup is metadata-only by construction: a new head_object seam
method resolves the key's committed inode -- the same resolution GET
performs before it streams -- and answers from a body-less ObjectMeta
type. No fragment stream is opened and no reader task is spawned, so a
HEAD of a large object costs a metadata round-trip, not data reads.

Fixes #506
