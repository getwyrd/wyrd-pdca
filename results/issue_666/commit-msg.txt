gateway-core: add a MultipartGateway seam that answers not implemented

S3 multipart upload is how clients like the AWS CLI send large objects.
Wyrd refuses all of it today with 501 NotImplemented, and there is no place
in the gateway layer where multipart support could be added. This change
adds that place without changing anything a client sees.

MultipartGateway is a new companion trait in wyrd-gateway-core, built like
ContainerGateway (ADR-0046 decision 6). ObjectGateway stays object-only. The
trait carries the six multipart verbs (create, upload part, complete, abort,
list parts, list uploads) in plain container/object terms, with typed answers
that mirror wyrd_core::multipart's outcomes. Every answer is a value the
caller matches on. "Not implemented" is one of those values, not a panic or
an untyped error. NamedParts holds the part list for Complete and cannot be
empty, so an empty list is refused before the seam is ever called.

wyrd-server's Gateway implements the trait at the composition root. Each
verb is written out and answers NotImplemented, so the slices that wire in
wyrd_core::multipart (#668, #669, #670) replace only a body. The S3 crate now
requires MultipartGateway on its gateway type. Its test doubles and the ones
in request_capacity_planes.rs get empty impls that use the trait defaults.

Routing does not change. The S3 subresource denylist and both guards are
untouched, so every multipart form still answers 501, and no request reaches
the new trait yet. The new test multipart_gateway_seam.rs checks this with a
sentinel gateway that counts calls: after all six forms, the count is zero.

This is the first of the slices that split #508.

Fixes #666
