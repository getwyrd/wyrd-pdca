- NEEDS-HUMAN — **Create omits the bucket deletion fence.** `brief.md:162-170` enumerates the Create batch with only the bucket record required present and classifies only a gone bucket as `NoSuchBucket`; leg B (`brief.md:33-37`) tests only absence. On the target, `docs/design/proposals/draft/0016-multipart-commit-protocol.md:657` requires ADR-0046 §4's bucket-existence contract, and `docs/design/adr/0046-bucket-model-real-namespace.md:93-95` requires both exact marker bytes and absence of the deletion fence. The marker remains present while deletion is fenced (`:104-117`), so the proposed batch can admit into a deleting bucket. Specify both preconditions and add a deleting-bucket refusal/race case with no session, marker or counter writes.

- NEEDS-HUMAN — **Unknown Create outcomes lack a recoverable identity contract.** `brief.md:172` stops at “an unknown commit outcome is an `Err`,” while `:169` treats a taken upload id as a collision requiring re-minting. The normative proposal explicitly says unknown Create outcomes must recover with the **original upload id**, rebuilding the ledger precondition; erroring out or minting another id can strand an admitted session (`docs/design/proposals/draft/0016-multipart-commit-protocol.md:2010-2027`). `crates/traits/src/lib.rs:240-247` confirms that an absent re-read cannot settle a commit that may still land. Define how the core API preserves/exposes the attempt identity and distinguishes recovery from a fresh-id collision, even if the gateway drives recovery later. Add a late-commit recovery scenario asserting one session and one increment; ordinary error propagation currently satisfies the brief without proving this property.

- NEEDS-HUMAN — **The required contention red is scheduler-dependent.** `brief.md:23-32,53-59,100-103` relies on multithreaded Tokio plus redb to demonstrate refusals when the contention budget is shortened. Target `crates/metadata-redb/src/lib.rs:113-117,208-234` implements reads and commits synchronously, without an internal await. Spawning 8/10/16 tasks does not ensure shared ledger reads, much less repeated losses by one task: a valid schedule can serialize them and let the shortened-budget mutant pass. Require a controlled read/commit schedule and assertions that a creator actually exceeds the collision-sized CAS budget, retaining the real-store checks. Include reproducible seeded coverage: target `AGENTS.md:188-190` requires it for new concurrent paths, but the brief specifies only the ordinary-runtime test.

- NEEDS-HUMAN — **The claimed shared fence batch builder is only a record builder.** `brief.md:117-118,206-207` says #841 already supplied the shared builder requested by the tracker. The first comment in `notes.json` says the client Abort and restore should use “one batch builder, not two.” Target `crates/core/src/multipart.rs:2360-2372,2426-2442` produces only a session/obligation pair; `crates/custodian/src/restore.rs:1050-1057` separately constructs the `WriteBatch`, including its preconditions. Reusing `open_teardown` alone therefore still duplicates transaction construction. Revise the scope to identify the shared batch-construction seam and the restore callsite change needed to use it, or explicitly surface the narrower record-builder interpretation for adjudication instead of claiming the tracker requirement is already implemented.
