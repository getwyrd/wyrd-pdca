## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect: The first store-I/O slice of the multipart protocol: `CreateMultipartUpload`'s
  admission through the serialized fleet counter (`mpuctl`) plus session creation, and
  `AbortMultipartUpload`'s teardown fence, as `wyrd-core` functions over `MetadataStore`. They
  answer in the typed vocabulary already on `main` (`CreateOutcome`, `AbortOutcome`, `Refusal`,
  `Backpressure`: `crates/core/src/multipart.rs:4277-4452`). Today the module is deliberately
  pure (`crates/core/src/multipart.rs:5-7`, `:104-118`): nothing creates a session, and nothing
  but the restore pass fences one.
- Success criterion: A NEW test over `RedbMetadataStore::in_memory()` on a multi-thread
  tokio runtime shows all of the following.
  **(A) Admission under real contention.** On a fresh empty store, **8, 10 and 16** concurrent
  creates (each level on its own fresh store; all three asserted, not one) all answer
  `CreateOutcome::Created`. Their upload ids are pairwise distinct. Exactly N `mpu:` records
  exist (scan `MPU_PREFIX`), each decoding through `decode_session_record` as an `Open` session
  for the requested bucket inode and object name. Exactly N `seggrp:` markers exist, one per
  session's nonce. `mpuctl` decodes through `decode_admission_record` with `count() == N`
  exactly. These are the levels #508's rejected attempts measured as falsely refused (8 → 2
  refused, 10 → 3, 16 → 3; aws-cli's default `max_concurrent_requests` is 10). These free-running
  levels stay, but they are not the red (see A′): redb's `get` and `commit` never await inside
  (`crates/metadata-redb/src/lib.rs:113-117`, `:208-234`), so a valid schedule can serialize them.
  **(A′) Admission under a forced schedule.** The same test drives N = 8 creates through a
  test-local `MetadataStore` wrapper over `RedbMetadataStore` that controls the order: every
  creator's `mpuctl` read is held until all live creators have read it, before any of them may
  commit, so each round has one winner and the rest lose the CAS. The wrapper counts each
  creator's `mpuctl` CAS losses (it can tell creators apart by the `mpu:<id>` key in each batch).
  Assert that all 8 answer `Created`, that `mpuctl.count() == 8`, and that at least one creator
  lost the `mpuctl` CAS **more than `MAX_UPLOAD_ID_ATTEMPTS` (= 2, `:4983`) times** and still
  succeeded. That last assertion is what a shared, collision-sized budget fails on every run.
  **(B) The real bounds, each writing nothing.** With the ledger at its stored `max_sessions`, a
  create answers `Refused(SlowDown { pressure: SessionCap { .. } })`. A create whose local
  `Budget` differs from the profile stored in `mpuctl` answers `Refused(ProfileSkew { .. })`. A
  create for a bucket with no `bucket:` record answers `Refused(NoSuchBucket)`. A create whose
  bucket marker is **deleted or rewritten between Create's read and its commit** (the same
  wrapper, acting at commit) answers `Refused(NoSuchBucket)`. After each, the store is
  byte-identical to before: no `mpu:`, no `seggrp:`, and no `mpuctl` write.
  **(C) Two separate retry budgets.** When the first minted upload id collides with an existing
  `mpu:` record, the create re-mints and succeeds. When every one of `MAX_UPLOAD_ID_ATTEMPTS`
  mints collides, it refuses. Losing the `mpuctl` CAS never spends the collision budget, and a
  collision never spends the contention budget (`MAX_ADMISSION_CAS_ATTEMPTS`).
  **(D) Abort per decision 3 (`0016:977`).** On `Open@E` it answers `Fenced`; afterwards the
  session decodes as `Aborting@E+1`, and `retire:bytes:s:<id>:<E>` holds exactly the
  `{session, all}` obligation `SessionRecord::open_teardown` mints, committed in the **same**
  batch as the fence. A second Abort answers `AlreadyAborting`. **Two concurrent Aborts** of one
  `Open` session answer one `Fenced` and one `AlreadyAborting`, never `OperationAborted`. Abort
  of a `Completing` session answers `Refused(OperationAborted)` and leaves the store unchanged.
  Abort of a `Completed` session, or of an upload id with no record, answers
  `Refused(NoSuchUpload)`.
  **(E) Abort never moves the counter.** `mpuctl.count()` is identical before and after every
  leg of (D), and a `Completed` tombstone stays counted. The decrement belongs only to the
  terminal delete (#659).
  **(F) An unknown Create outcome is recovered under the original upload id (`0016:2009-2027`).**
  Through the wrapper, the first Create commit returns `CommitUnknownResult { may_still_commit:
  true }` (`crates/traits/src/lib.rs:230-248`) in three variants: (F1) the batch was applied
  before the error; (F2) it was not applied; (F3) it is held and applied **after** the recovery
  re-drive has committed (a late commit, which must then lose its own `require_absent(mpu:<id>)`).
  In each, recovery re-drives with the **same** upload id and nonce, rebuilds the `mpuctl`
  precondition from a fresh read, and answers `Created`. Afterwards there is exactly one `mpu:`
  record, for that upload id, exactly one `seggrp:` marker, and `mpuctl.count()` rose by exactly
  one. No second upload id is ever minted.
  **(G) Seeded coverage** (`AGENTS.md:188-190`: a new concurrent path lands with seeded Tier-0
  DST coverage). A NEW madsim scenario `crates/dst/tests/multipart_admission.rs` runs concurrent
  Creates and Aborts with the commit-ambiguity nemesis armed, mirroring
  `crates/dst/tests/commit_ambiguity.rs`'s 1021/1031 legs. After every seed: the number of `mpu:`
  records equals `mpuctl.count()`, every `mpu:` record has its `seggrp:` marker, and every
  `Aborting` session has its `retire:bytes:` obligation. `cargo xtask ci` sweeps it (it includes
  `cargo xtask dst`, 50 seeds), so C4-ci runs it.
- Repo + branch target: getwyrd/wyrd @ main
- Scope: `CreateMultipartUpload`'s admission and session creation (including recovery of an

Four distinct defects remain. All source citations below resolve against the supplied `$PDCA_TARGET` (`target/`); evidence and brief citations resolve in the review directory. The target is readable and matches the patch: its synthetic base identifies `7bf7eb9`, and `git apply --reverse --check patch.diff` succeeds. No stale-target compilation failure is attributed to the patch.

1. **F1 — Ordinary collisions can return another request’s upload ID (P2).** At `crates/core/src/multipart/store.rs:441`, `lost()` recognizes a matching nonce/parent/object as success without checking whether this invocation ever had an unknown commit. Two ordinary creates for the same object with scripted identity pairs `(10,11)` then `(10,11),(20,21)` both return upload ID `0a`; the second never mints the available replacement. The independent assertion fails at `reviewer-evidence/probes.log:8`. This violates collision handling even though the counter remains internally consistent. Permit recovery-as-success only when this invocation has an outstanding ambiguous attempt; otherwise classify the existing identity as a collision. The current collision test changes both object and nonce (`crates/core/tests/multipart_create_abort.rs:893`), so it misses this case.

2. **F2 — Create abandons the final unknown result without a settling read (P2).** At `crates/core/src/multipart/store.rs:310`, reaching the contention limit returns through `refuse()` before the recovery read at `crates/core/src/multipart/store.rs:334`. A real-redb wrapper drops the first 45 commits with `CommitUnknownResult { may_still_commit: false }`, applies commit 46, and returns the same error class. The store contains exactly one session and a count of one, but Create returns `Unsettled` with `AdmissionContention` instead of `Created` (`reviewer-evidence/probes.log:19`). A settling read would resolve this outcome; proposal 0016 explicitly requires that distinction at `docs/design/proposals/draft/0016-multipart-commit-protocol.md:2025`. Budget exhaustion must still allow settlement of the last attempt, without authorizing another write.

3. **F3 — Abort discards its final settling read (P2).** At `crates/core/src/multipart/store.rs:595`, Abort re-reads the session after an unknown commit, but on round four exits at `crates/core/src/multipart/store.rs:601` before interpreting that read. The wrapper drops the first three commits and applies the fourth before returning an out-of-flight unknown result. The session is `Aborting`, its retirement obligation exists, and the read establishes the required `AlreadyAborting` answer; the function nevertheless returns the unknown error (`reviewer-evidence/probes.log:15`). Interpret the final read before applying the retry limit. Cover the corresponding final-conflict state transition too. The existing ambiguity test injects only the first commit’s unknown outcome (`crates/core/tests/multipart_create_abort.rs:578`), and the DST scenario uses only three strikes (`crates/dst/tests/multipart_admission.rs:59`).

4. **F4 — The contention budget ignores the accepted capacity profile (P2).** At `crates/core/src/multipart/store.rs:310`, every profile receives the shipped profile’s 46-attempt ceiling. The public API accepts another validated `Budget`, and admission stores that profile’s capacity (`crates/core/src/multipart/store.rs:355`). With `W_REF * 2` and the other shipped values, capacity is 93. Forcing one real rival admission before each of 46 attempts produces `SlowDown(AdmissionContention)` at count 46, without churn (`reviewer-evidence/probes.log:23`). This contradicts the capacity-derived guarantee documented at `crates/core/src/multipart.rs:5060`. Derive the operational retry allowance from the accepted profile, and test a larger valid profile under a forced schedule.

# Adversarial review — issue 656 (multipart Create admission + Abort fence)

Paths are in the target tree (`$PDCA_TARGET`); `store.rs` means `crates/core/src/multipart/store.rs`.
I ran each probe as a scratch test against the real `RedbMetadataStore`, using a small test-local
`MetadataStore` wrapper (the same approach the patch's own `Interposer` uses). Four of the seven
blocking T4 findings hold up as concrete failures. One gap is new: the test for the `owns()` guard
is weak. I dispute one T4 finding (await bounds).

- NEEDS-HUMAN [impl] — `store.rs:308-314`: a CommitUnknownResult on the **last** contention attempt is never settled, even when `may_still_commit == false`. Probe: a rival is admitted before each of the target's commits 1–45. Commit 46 lands and then answers `CommitUnknownResult { may_still_commit: false }`. Result: `Err(Unsettled { ended: Refused(SlowDown { AdmissionContention { attempts: 46 } }) })`, while `mpu:<id>` exists and the ledger reads 46/46. The brief's contract (Design, "with `may_still_commit == false`, one re-read settles it") means one `get(mpu:<id>)` would have answered `Created`. Instead the session is admitted and counted, and no client can name it. Here it also takes the last ledger slot, so every later create gets `SessionCap` until the reaper (#625, not landed) reclaims it. The `Unsettled` message ("may still be admitted … if it lands") is also wrong in this case. Fix: before returning on budget exhaustion with `doubt` set, run the same settling read the doubt branch at `store.rs:334-349` does.
- NEEDS-HUMAN [impl] — `store.rs:570-605`: Abort throws away its last round's re-read. Probe: the session is moved to `Open@E+2` before rounds 1–3 (what a Complete fence plus rollback leaves behind). Round 4's fence lands, then answers CommitUnknownResult. `abort_session` returns the raw unknown error, while the session is already `Aborting` with its `retire:` obligation in place. The same path turns a round-4 `Conflict` lost to a concurrent Abort into `RoundsExhausted`, where the right answer is `AlreadyAborting`. That breaks leg (D)'s rule that two Aborts never end in an error. Without #658, four ambiguous outcomes in a row (1021/1031) reach this today. The DST is set up just below the failing case: `STRIKES = 3`, "Below abort_session's four rounds, so no single Abort can be struck on every round" (`crates/dst/tests/multipart_admission.rs:59-62`). Fix: after the loop, answer from `read` through `abort_answer` unless it is still `Open`, and add a test for that path.
- NEEDS-HUMAN [impl] — `store.rs:439-446` (and `owns`, `store.rs:196-202`): `lost()` accepts "this is my own session" even when no unknown outcome is outstanding, and `owns()` never checks the session's state. Probe: a create of `photos/same` with identity (a1, b1), then Abort (now `Aborting`), then a second create of `photos/same` whose host repeats (a1, b1). It answers `Created { a1 }` for the `Aborting` session, writes nothing, and leaves the ledger at 1 → 1. The module itself treats a repeating identity source as something to detect (`CreateFault::IdentitiesExhausted`, "the identity source is broken"). Here the result is a silent success, which the rubric's *Absent or unsupported entries* class forbids. The comment at `store.rs:440` says the only legitimate cause is a late in-doubt batch, so pass `doubt` into `lost()` and accept ownership only while a batch that may still land exists.
- NEEDS-HUMAN [impl] — `store.rs:199-200`: the two surviving `owns()` mutants (C5 log: `&&`→`||` at 199:17 and 200:17) show that leg (C) cannot tell the real check from a loose one. Every collision in `c_a_colliding_identity_is_re_minted_…` targets a session for a *different* object. Probe: collide on `mpu:a1` held by a session for the **same** object with a different nonce. The real code re-mints to `a2` (correct). With the 200:17 mutant applied, it answers `Created { a1 }`, which is another client's upload. Several uploads to the same key is the normal case, so add this case to (C). The same C5 run shows two smaller gaps. The guard→`true` mutant at `store.rs:594` survives because no test sends a plain (non-unknown) store fault into an Abort commit. The `contended - 1` mutants at `store.rs:317` survive because (A′) only checks that waits fall between BASE and CAP, never that the window grows.
- NEEDS-HUMAN [impl] — `store.rs:310`: the contention budget is the fixed `MAX_ADMISSION_CAS_ATTEMPTS` (46, the shipped `MAX_SESSIONS`), whatever limit the stored ledger has. `create_session` accepts any `local: &Budget` (the patch's own tests pass a non-shipped one). The landed knob validator rejects exactly this pairing: `ensure(contention >= sessions, AdmissionCasBelowSessions)` (`crates/core/src/multipart.rs:5300-5301`). Probe: a valid profile with `w_ref = 2 × W_REF` (`max_sessions` 93) and a rival admitted before each of the target's commits. Result: `Refused(SlowDown { AdmissionContention { attempts: 46 } })` with the ledger at 46/93. That is #508's false-503 class, on a host with more RAM. Fix: size the budget from the stored ledger's `max_sessions` (already read at `store.rs:353-357`), or take it from the caller's knob set.
- NEEDS-HUMAN [human] — C4-ci (a gating check) is UNVERIFIABLE. It hit its 7200 s timeout in `crates/server/tests/custodian_gc.rs` deployed-role GC tests ("running for over 60 seconds"). Those tests don't touch the patched code; only their comments mention restore.
