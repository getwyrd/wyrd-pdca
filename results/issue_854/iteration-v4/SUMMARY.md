# Result — issue 854 / validate-s3-client-upload-against-misbehaving-peers

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect: #852's client is expected to trust the SDK's outcome for an upload. Each case
  below is a **hypothesis for #852 until Do reproduces it on #852's folded commit** (see
  Falsifiability). Each was seen on one of #741's attempts, whose client #852 rebuilds, and
  the cause sits in hyper, which #852 keeps. The records are in this harness repo under
  `results/issue_741/`:
  - **Early acknowledgement (round 2), reproduced.** A server that reads only the request
    head and answers `200` gets a receipt. With a declared 64 MiB body, only 2.8 MiB had been
    produced. With a 10-byte body whose source fails after the ack, a receipt came back too.
    hyper returns the response as soon as its head arrives and keeps polling the body in the
    background. `iteration-v2/SUMMARY.md:138`.
  - **Upload retained under backpressure (round 3), disputed.** The setup: a 512 MiB
    generated upload in 32 MiB pieces, and a peer that stops reading, lets the socket buffers
    fill, then sends an early `200`. The PUT returned, but the source stayed alive four
    seconds past a three-second operation limit, and was released only when the peer closed.
    `iteration-v3/SUMMARY.md:112` (F2) and `:251`. A second reviewer could NOT reproduce it
    in three setups with smaller pieces (`iteration-v3/SUMMARY.md:178-193`).
- Success criterion: BINDING. The production client runs against a scripted loopback peer.
  **One lifetime contract, with fixed bounds, applies to every scenario below.** The test
  sets the operation timeout to `T_op = 3 s` and wraps each call in a `T_op + 1 s` timeout of
  its own:
  - the call returns within `T_op + 1 s`; not returning is a test failure with a message,
    never a hang;
  - at return, the source has **already been dropped**, observed through the test's own
    source type (a drop flag, not a new API), checked right after the call returns, with
    no grace period;
  - the peer sees its connection **closed** (EOF or reset on its next read) within 1 s
    after the call returns.
  The scenarios:
  1. **No receipt while the source still had bytes.** A PUT acknowledged while its source
     still has data to produce fails with the body error, carrying the acknowledgement's
     request id. So does a source that fails after the acknowledgement.
  2. **Early acknowledgement under backpressure.** The peer reads the head, waits until the
     client's writes back up, sends `200`, keeps the socket open and never reads again; the
     source yields pieces of 32 MiB or more. Outcome: the body error, plus the lifetime
     contract.
  3. **Stops reading, never answers.** The peer reads the head, stops reading, never sends a
     response and keeps the socket open; the source yields pieces of 32 MiB or more.
     Outcome: the typed operation timeout, plus the lifetime contract.
  **The inherent limit, narrowed and stated, not left implicit.** The client can see only
  what it handed to the HTTP stack, not what the peer read. So the rule is: a receipt
  requires that the source gave up its **whole declared length** before the response
  arrived. If it did, the outcome is a **receipt**, even if some of those bytes were still in
  the client's or the kernel's buffers when the peer answered. That includes the case of a
  large final piece taken but not yet written. Nothing on the client side can tell those
  bytes from bytes the peer read and threw away. Do documents this rule on `put_object`, and
  one test pins its simple form (a 10-byte source fully taken, then an early `200` →
  receipt, as observed in `iteration-v3/SUMMARY.md:241-245`) so the boundary cannot move
  silently.
- Repo + branch target: getwyrd/wyrd @ main
- Scope: the PUT path's outcome and its resource lifetime against a peer that acknowledges
  early or stops reading, with or without answering. Remove #852's `// deferred:` markers
  for this issue as each case lands. **If releasing a connection blocked mid-write cannot be
  done through the SDK's public connector or runtime API without forking it, STOP and report
  with the evidence.** Choosing a different HTTP seam is a Plan question, not something to
  paper over.
  **/ out of scope:** response classification and byte budgets (#853); GET; the 5 GiB
  property (#761); TLS; any edit outside `crates/validate/`.

### Advisory — adversary

# Adversarial review — #854 (validate: S3 client PUT against misbehaving peers)

The core fix holds. I could not break the main ordering claim (the body takes nothing between hyper handing over the response and the SDK hook recording it). The tests do catch each part of the fix being removed. What I did break is one edge of the receipt rule, which the builder pinned with its own test, plus one fitness cost of the lifetime mechanism. Both come down to how the brief's rule is read, so they are tagged `[human]`.

- NEEDS-HUMAN [human] — **The "held its end" receipt is a PUT the server got none of.** `crates/validate/tests/s3_client_upload_peers.rs:1137-1151` (`a_source_that_gave_its_whole_length_but_held_its_end_is_a_receipt`) requires `Ok(PutOutcome)`. I re-ran it with the run printed: the peer drained **0** bytes after the call (`closed: Eof { drained: 0 }`), against 207 in the fully-taken receipt test (`:1121-1132`). A standalone probe read everything the peer received for 300 ms before answering, and it was **0 body bytes**. A complete 10-byte PUT is 303 wire bytes: `content-encoding: aws-chunked`, `x-amz-decoded-content-length: 10`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER`, then a CRC32 trailer and trailer signature. The SDK's signed chunk layer holds data until it has a full 64 KiB chunk or the source ends (`aws-runtime-1.10.0/src/content_encoding/body.rs:137-170`). So the 10 "given" bytes never reached hyper, and the last chunk and checksum trailer were never even produced. That makes the rationale at `crates/validate/src/s3.rs:155-161` false for this edge: "nothing on the client side can tell those bytes from bytes the server read and threw away". The client *can* tell: hyper had written 0 of its declared 303-byte `Content-Length`, and a conforming S3 server cannot answer before the trailer. This config always uses aws-chunked (the config builder reads no env, and checksums default to on for PutObject), and a conforming server only answers after the source has ended. So one stricter rule would cost well-behaved servers nothing: require the source's end (`ended`, `crates/validate/src/s3/body.rs:265,323`) before a receipt. The brief's literal rule ("gave its whole declared length") allows the current behaviour, so this is the human's call on the rule, not a build slip.

- NEEDS-HUMAN [human] — **Regression against #852: a source that overruns its declared length now gets a receipt.** The probe uses only the public API: declared 10, the source gives 10 bytes, holds until the peer has written `200 OK / x-amz-request-id: early`, then would give 1 more byte. On the base (`git show HEAD:crates/validate/src/s3{.rs,/body.rs,/error.rs}`) the result is `Err(Body(SourceLength { declared: 10, produced: 11 }))`. With the patch it is `Ok(PutOutcome { etag: None })`, because the source is never polled again once the answer is recorded (`crates/validate/src/s3/body.rs:289-291`). The overrun check documented at `body.rs:247-249` is skipped. The brief's goal says "never as a receipt while the caller's source still had bytes to give", and this source had one. The same fix as the bullet above (no receipt until the source has ended) closes it. Tagged `[human]` because the fix depends on that rule decision.

- NEEDS-HUMAN [human] — **A fresh thread and TCP connection per PUT puts a ceiling on the load proposal 0017 asks for.** I ran 1000 sequential 10-byte PUTs against a keep-alive loopback server that reads the whole aws-chunked body before answering (debug build). Patched: **462 PUT/s, 1000 client sockets left in `TIME_WAIT`**. Base: **731 PUT/s, 0 in `TIME_WAIT`**. This host uses Linux defaults: `ip_local_port_range` 32768–60999 (28,232 ports), a 60 s `TIME_WAIT`, and `tcp_tw_reuse=2`, which helps loopback only. So over a real network, sustained PUTs to one gateway address cap at about 470/s. Past that, connects fail with `EADDRNOTAVAIL`, and the tool's failure taxonomy would charge those to the gateway as `availability` failures (`docs/design/proposals/draft/0017-blackbox-validation-tool.md:489`). Proposal 0017 wants `churn` at a "very high delete and overwrite rate" (`:534`) and says the tool "must sustain [the load] without becoming the bottleneck" (`:474-476`). `crates/validate/src/s3.rs:175-177` states the cost but not this ceiling. The brief's invariant asks for the close on *every* return. The open question is whether to close only after an abnormal end (early answer, timeout, drop) and keep the pool for clean receipts.

- NEEDS-HUMAN [human] — **T4's only gating blocker (Tier-0 DST coverage for `crates/validate/src/s3.rs:351`) looks inapplicable.** DST here means seeded deterministic simulation under madsim. `crates/validate` has no madsim build at all, it depends on no `wyrd-*` crate (`docs/design/architecture/05-building-block-view.md:255`), and the mechanism is a real OS thread, a real tokio runtime and a real socket, none of which madsim models. No rebuild can satisfy this. A human should record a rejection reason (or a deferral) so the gate stops blocking on it.

- The `check-gates.json` C4-verify row says "11 test(s) ran red", which is wrong. `gate-logs/C4-verify.log` shows "1 passed; 10 failed": `a_put_dropped_while_blocked_mid_write_releases_the_upload` (`s3_client_upload_peers.rs:1065`) is green on the base, because hyper already releases a dropped request through its callback-cancel path. It still guards the patch: I swapped the abandon signal at `crates/validate/src/s3.rs:365` for a never-resolving future, and that test alone went red. No action needed.

- **Attempted to refute, could not:**
  - **The ordering claim.** `aws-smithy-runtime-1.15.0/src/client/orchestrator.rs:504-511` has no await between the connector resolving and `read_after_transmit`. The throughput-check wrapper passes straight through when stalled-stream protection is off. `aws-smithy-http-client-1.4.2/src/client.rs:615-625` and `hyper-util-0.1.20/src/client/legacy/client.rs:324-365` hand the response over without yielding. hyper's poll loop reads before it writes.
  - **The tests catch each part of the fix.**
    - Turning off `body_waits` (`body.rs:294`) turns 5 tests red.
    - Turning off the answer check (`body.rs:289`) turns the 3 late-body tests red.
    - Ignoring abandonment turns the drop test red.
  - **The previous rounds' flakiness.** 300 runs of the 7 small tests at 30-way parallel load had 0 failures. 36 runs of the 4 large tests at 12-way had 0 failures.
  - **Removing `tokio::task::unconstrained` (`body.rs:109`) survives, as expected.** tokio's cooperative budget is 128 operations per task poll, and the request spends about 2 per poll. So the guard can't be exercised; it isn't wrong. Not a finding.

### Advisory — code-review

- NEEDS-HUMAN [impl] — `crates/validate/tests/s3_client_upload_peers.rs:606`: **The connection-close oracle can accept a close outside the required one-second bound.** The peer starts a fresh deadline when it receives the completion signal, rather than using the call's return/drop timestamp. If it resumes 1.3 seconds after return and the client closed at 1.2 seconds, it can report success within `after_call`'s two-second watchdog. Also, `wait_client_close` checks socket state before expiry (`:683`), and the assertion accepts `After(_)` without checking its duration (`:820`). Send the actual completion timestamp through the channel, derive one absolute deadline from it, and reject closure observations beyond that deadline, including EOF/reset observations.

- NEEDS-HUMAN [impl] — `crates/validate/src/s3/body.rs:230`, `crates/validate/src/s3.rs:351`: **The new concurrent lifecycle lacks the required seeded Tier-0 coverage.** `RequestFirst` introduces wake-count coordination and the worker introduces cancellation and shutdown ordering, but the added tests exercise only real threads, loopback sockets and wall-clock scheduling. The `--seed` argument in the fixture does not control those schedules. Add seeded coverage of response-wake/body-poll ordering and cancellation cleanup using the production coordination logic. This corroborates the unresolved finding in the frozen `T4-batch-review` log; the rubric explicitly requires such coverage for new concurrent paths.
