The acknowledgement fixture needs an ordering repair; the observed failure does not establish a remaining production race. The production changes address response/body scheduling and ownership of the blocked connection task. The remaining evidence gap is whether the held-source tests actually exercise their claimed ordering, rather than a valid source-before-response execution.

- **The new final-piece test is intermittently red on the unchanged patch.** Running the two held-source tests repeatedly produced `Ok(PutOutcome { etag: None })` on iteration 105, with all ten source bytes handed over and normal cleanup (`pdca-reviewer-854-evidence/held-stress.log:14`). The fixture releases the source at `crates/validate/tests/s3_client_upload_peers.rs:467` before writing the acknowledgement at `crates/validate/tests/s3_client_upload_peers.rs:426`. Not retaining a source waker does not prove that no other event can repoll the connection. A separate scratch copy added only an atomic observation flag and an optional 20 ms scheduling gap between those existing events. It reproduced the same failure while recording that the source advanced **before the peer even began writing the acknowledgement** (`pdca-reviewer-854-evidence/held-instrumented.log:36`). The instrumented copy also reproduced an undelayed failure on iteration 304, whose exact transport ordering remains undetermined. Repair the fixture to establish or observe the relevant ordering, and distinguish legally completed sources from post-response production; do not change the receipt rule merely to make this assertion pass. The shared premise also affects the failing-source case at `crates/validate/tests/s3_client_upload_peers.rs:708`.
- **Cancellation works in the independent probe but is missing from the submitted regression suite.** The additional scratch test waits for a nonempty, stationary client send queue, drops the PUT future before its operation timeout, checks source destruction within 500 ms, then checks socket closure without draining first and EOF within one second. All ten attempts passed (`pdca-reviewer-854-evidence/cancellation.log:3`). None of the patch's tests drops an in-flight PUT: their common helper awaits the operation at `crates/validate/tests/s3_client_upload_peers.rs:589`. Keep a regression for the abandonment branch at `crates/validate/src/s3.rs:367`; current runtime success does not protect that distinct cleanup path from future regressions.
- **Documentation needs a scope decision.** `AGENTS.md:154` requires the architecture description to accompany an altered API operation. `docs/design/architecture/05-building-block-view.md:255` still describes the baseline client without the receipt boundary or new resource cost. This is the same convention issue identified by the frozen review; it conflicts with `brief.md:97`, so it belongs in Plan/scope resolution rather than an unapproved edit outside the brief.
