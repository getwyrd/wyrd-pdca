validate: never count an early S3 answer as a stored upload

wyrd-validate's S3 client took the SDK's word for how a PUT ended. A server
that answered 200 before it had the whole object, for example after reading
only the request head, got a receipt: 3 MiB of a declared 64 MiB had been
sent. A validator that believes that cannot catch the servers it exists to
catch. A server that stopped reading could also leave the caller's source
and the connection alive after put_object had returned.

A PUT is now a receipt only if the caller's source had ended (given its
whole declared length and then reported its end) when the client read the
answer off the socket. Any success that arrives sooner is the new
BodyError::AcknowledgedEarly, carrying the answer's request id. Having given
every byte is not enough: until the source reports its end, the SDK has not
written the body's last chunk and checksum trailer, and the source could
still run past its declared length. Once the answer has arrived the source
is not polled again.

When put_object returns, the source has been dropped and the connection
closed, whatever the server did. The request runs on a small runtime of its
own, which is shut down before the outcome is handed back; that is the only
way to release a connection blocked on a server that stopped reading, since
the SDK's connector exposes neither the socket nor its task. A dropped PUT
future releases both within a fixed bound too.

The cost is one thread and one fresh TCP connection per PUT. Each leaves a
socket in TIME_WAIT, which caps sustained PUTs per client and gateway
address pair at about 470 a second with Linux defaults. The put_object doc
and the architecture overview state that cap, how an operator raises it,
and the one case the client still cannot see: an answer already in the
kernel's receive buffer that hyper has not read yet.

A new loopback test file runs the real client against a scripted peer that
answers early, stops reading, or both, in twelve cases.
