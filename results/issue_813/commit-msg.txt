custodian: scrub and reconstruct staged multipart uploads too

Two of the background loops that keep stored data healthy only ever
looked at data that had already been fully committed. A file being
uploaded in parts (a multipart upload) can sit "staged" — written but
not yet committed — for hours. During that window, neither loop
noticed if one of its pieces went missing or got corrupted:

- Scrub (the loop that checks stored copies for damage) skipped
  staged pieces entirely, so a flipped bit or a lost fragment never
  turned into a repair job.
- Reconstruction (the loop that rebuilds redundancy after a loss)
  would find no committed record for a staged piece and conclude it
  had been deleted, quietly dropping the one record saying a copy was
  missing — so the store could later claim everything was fine.

Scrub now also reads a staged upload's committed part records and
checks the fragments they name, using the error-correction scheme
each record carries, before falling back to the fully-committed data
(crates/custodian/src/scrub.rs). Reconstruction now reads the same
staged records first and keeps an obligation queued — rather than
discarding it — for any chunk a staged record still names but no
committed map does (crates/custodian/src/reconstruction.rs). Once a
chunk is committed, its committed record decides everything, exactly
as before; this only closes the gap for pieces still in flight.
Rebuilding those staged pieces directly is left to a follow-up
change; this fix is about not losing track of the problem.

A malformed staged placement (empty or wrong-length) is now reported
rather than silently treated as fine, and the operator-facing log
lines now name the actual damaged record so it can be found. New
tests also cover scrub's paging through more than one page of staged
upload sessions, and confirm staged damage is still reported even
when a later, unrelated read fails.
