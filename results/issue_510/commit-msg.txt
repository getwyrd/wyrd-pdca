feat(510): honor Range and conditional headers on S3 GET/HEAD

GetObject and HeadObject now honor the standard HTTP range and conditional
headers, so downloads and caching behave the way S3 clients expect. A
`Range: bytes=a-b` request returns 206 Partial Content with a correct
`Content-Range`, a `Content-Length` of just the requested span, and only
that slice of bytes; the suffix (`bytes=-N`) and open (`bytes=a-`) forms
work too, and an unsatisfiable range returns 416. Every object GET and HEAD
now advertises `Accept-Ranges: bytes`.

GET and HEAD also evaluate the conditional preconditions against the stored
ETag and modification time: `If-None-Match` and `If-Modified-Since` answer
304 Not Modified, while `If-Match` and `If-Unmodified-Since` answer 412
Precondition Failed, following RFC 9110 precedence with S3's exact-ETag
comparison semantics. This unblocks resumable downloads, media seeking,
range-based tooling, HTTP caching, and optimistic-concurrency workflows,
all of which previously received a full 200 regardless of the headers they
sent.

The gateway serves only the chunks overlapping the requested span rather
than streaming the whole object and discarding bytes, so a narrow range of
a large object stays cheap. A ranged read resolves its metadata and its
bytes from a single object snapshot, so a 206's headers can never name a
different version than the bytes it carries, even under a racing overwrite.

c2af90796f047bf734982a0b3829441df1ba3da6 and the stored object metadata
from 68403eb3f61e42fa5fe12a37d495519abce179d2.
