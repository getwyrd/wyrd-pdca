### Advisory — adversary

# Adversarial review — issue 1014 (orphan-identity migration gate + retirement routing)

Toolchain was available. I copied the patched tree to scratch, ran `cargo test -p wyrd-custodian --test retirement_routing` (24/24 green), re-ran the brief's demonstrated reds as one-line mutants, and added three probe tests (X1–X3, scratch only). Two probes break the fix. One finding questions the design premise.

## Refutations

- NEEDS-HUMAN [impl] — **A damaged walk cursor writes the marker without judging a single mark.** `crates/core/src/orphan_identity.rs:235-239` accepts any lowercase hex as `after`. `crates/custodian/src/orphan_identity.rs:265` pages `orphan:` from that cursor, and `:281-287` writes the marker when the page comes back empty. Failing case (probe X1): a committed 100-chunk RS(6,3) object, one ANCIENT legacy mark on a live fragment, and `custodian:orphan-identity-walk` = `{"after":"ff"}` (0xff sorts after every `orphan:` key). One repair pass returns `Changed` and the status reads `Complete`, with the stale mark still in place. The routed `unlink` then installs `g:70:1`, and three GC passes run *before any drain* reclaim that fragment (the fleet no longer holds it). That is the premature reclaim the gate exists to prevent. The module doc's claim at `crates/core/src/orphan_identity.rs:119-120` ("whatever it holds, the walk only judges marks from there") is wrong for this value. Fix: refuse at decode any `after` that does not start with `orphan:` (the ADR-0045 decode boundary), and add the test. It needs damage to the custodian's own record, so it is unlikely, but the result is a safety failure, not a lost lap. T4 flagged the decode. X1 confirms it end to end.

- NEEDS-HUMAN [impl] — **A placement the cleanup can't trust names the chunk whole, and the cleanup *drops* marks on that basis.** For GC, "named whole" is the safe direction because it protects. For the cleanup it deletes evidence. Code: `names` returns true for every server when the placement is refused (`crates/custodian/src/orphan_identity.rs:454-461`). `place` files it under `whole_chunks` (`:571-577`), and `judge` turns Committed/Staged into `Drop` (`:1038-1039`). `verified` agrees (`:1066-1069`; and `:1121-1124` for an undecodable `sidx:` value, placed whole at `:676-679`). Failing case (probe X2): an RS(2,1) chunk 80000 committed with placement `[0,1]` (wrong length), plus the old copy of fragment 0 on server 5 with its legacy mark, as a repoint leaves it. The cleanup drops the (5, 80000/0) mark. After the placement is repaired to `[0,1,2]` and GC runs past 10× grace, server 5 still holds the copy, unmarked. That fragment is named by no record and no mark (C-1), and GC keeps it forever ("no evidence → keep"). Left alone, the mark would have let GC reclaim it after the repair. Fix: a whole-chunk namer should give Leave (or Block), never Drop. T4 flagged `:1038`. X2 confirms the leak.

- NEEDS-HUMAN [impl] — **The segmented-obligation drop path is untested, and a bug there would keep the gate shut forever.** `crates/custodian/src/orphan_identity.rs:1090-1098`. With `if !in_group(seg, group)` flipped at `:1091` (C5 also lists it MISSED), all 24 shipped tests still pass. Probe X3 fails with that change: a routed unlink of a 180-chunk segmented Complete object, its obligation held undrained, the marker removed, and one ANCIENT mark on one of its fragments. `verified` returns `None` every pass, `visit` answers `Stale` (`:984-985`), the window stops before the mark (`:956`), the lap never ends, and with the gate closed GC reclaims no marked fragment anywhere. The real code passes X3 (the mark is dropped in one pass), so this is a test gap, not a live bug. Add X3's case to `retirement_routing.rs`.

- NEEDS-HUMAN [human] — **Committed repair can create new stale marks on live fragments after the marker is written, so the gate's premise fails in steady state.** The design (`0016:1253-1256`) and the brief's invariant ("no mark that a later routed unreference could be judged by survives the walk") assume that marks on referenced fragments come only from rollout skew and restores, both one-time. But `select_distinct_domains_excluding` (`crates/custodian/src/reconstruction.rs:1122`; `crates/core/src/placement.rs:273-279`) excludes only the survivors' domains, so a fragment can be rebuilt onto the server it was displaced from earlier. The repair marks only the displaced server (`reconstruction.rs:1156-1158`, `:1235`). Nothing in the move or in `repoint_chunk` touches a mark already at the target, and GC skips a referenced fragment without touching its mark (`crates/custodian/src/gc.rs:702-707`). Sequence: repair 1 moves C/i from D to E and marks (D, C/i) at t1. E later loses C/i, and repair 2 rebuilds it onto D. Now (D, C/i) is live and carries the t1 mark, after the marker exists. A later routed `unlink` of that object leaves the fragment unreferenced with a legacy t1 mark. The keyed lookup finds no token, judges by t1, and reclaims before the drain re-stamps (the outcome X1 reproduced). On the base, the inline unlink's blind put overwrote that mark in the same commit, so the exposure is new with the routing. Rebalance moves look the same. I did not drive this through production repair (the rig's fleet holds fake fragment bytes that reconstruction can't decode), so the source is reasoned from code and only the consequence is reproduced. A human needs to choose: fix the repoint paths (clear or re-stamp a target's mark in the move batch), keep the cleanup running after the marker, or record a tracked deferral.

## Attempted, could not refute

Instead I re-ran the brief's required reds on the scratch tree, and each holds: drain dispatch removed from `reconcile_step` → five A tests fail; preconditions left out of `fits_one_batch` → `a2_the_boundary_counts_preconditions` fails; `fits_one_batch` → `true` → A2/A3 fail; flat routing without reading the gate → F/F6/F7 fail; drop pinned only on the mark → F5 fails; `read_gate` ignoring the generation → F7 fails. The tests drive the production path (`reconcile_step` with the deployed contexts, production `unlink` / `commit_overwrite` / Complete).
- **Routing race with a restore.** The routed batch pins the marker bytes and the fence bytes (`crates/core/src/orphan_identity.rs:321-327`), so a new generation landing between the read and the commit fails the unlink.
