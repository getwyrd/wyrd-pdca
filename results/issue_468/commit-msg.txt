Simulate the FoundationDB backend's commit ambiguity in DST

FoundationDB is the metadata backend Wyrd has chosen for production, yet it
was the only backend never exercised against its worst failure: a commit the
database reports it may or may not have applied. redb and the simulated-TiKV
model both live inside the deterministic simulator, so the metadata contract
was pinned by two implementations; the FoundationDB backend could not join
them, because its client library spins up its own network thread and does
real, non-deterministic I/O that would break the simulator's seed replay. A
real cluster is no substitute — a healthy fdbserver cannot be made to emit
the ambiguous-commit error on demand, so a fault battery can only sample that
outcome, never search it.

This gives the backend a simulation of the same strength as the ones it
replaces. A seed-driven model reproduces FoundationDB's two undeterminable
commit outcomes — the out-of-flight 1021 and the weaker 1031 that "promises
nothing" — as a distinguishable error the caller must settle with a re-read,
exactly as the production driver already classifies them. Concurrent writers
race the version check-and-set with that failure injected across a seed
sweep, and the invariants hold at every seed: an ambiguous commit is never
counted a winner or a loser without a settling re-read; once settled, exactly
one writer wins and the version bumps at most once; no torn write is
observable. Each property ships a demonstrated failing observer so none rests
on a tautology. A companion guard resolves the simulator's dependency graph
and fails if the real FoundationDB library could ever be linked into it,
keeping the simulator deterministic by construction.

The change is test-only: nothing under the shipped crates changes, and no new
dependency is added. It parametrizes the simulated-store skeleton that landed
in 9374758933dec30b56efbdbdb7304ec1375a9f9c rather than building a second
framework.
